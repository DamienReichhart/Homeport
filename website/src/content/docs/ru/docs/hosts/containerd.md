**containerd** работает под k3s, nerdctl, BuildKit и на многих серверах, где нет Docker. Homeport подключается к нему напрямую, через его собственный API gRPC, как решено в [ADR 0020](https://github.com/DamienReichhart/Homeport/blob/main/docs/adr/0020-containerd-over-grpc.md). Хост containerd получает в боковой панели собственные страницы: **Контейнеры**, **Образы**, **Снимки** и **Пространства имён**. Страницы Docker, стеки и Доска для него не предлагаются.

## Добавление хоста containerd

Выберите **containerd** в поле **Движок** формы. К containerd подключаются только через его сокет, поэтому подключение — **Локальный сокет** или **SSH**; TCP и TLS неактивны, потому что containerd не предоставляет свой API по сети.

| containerd                           | Сокет                                                                          |
| ------------------------------------ | ------------------------------------------------------------------------------ |
| Собственная служба containerd        | `/run/containerd/containerd.sock`                                              |
| k3s                                  | `/run/k3s/containerd/containerd.sock`                                          |
| Собственный containerd Docker Engine | `/run/containerd/containerd.sock`, его контейнеры — в пространстве имён `moby` |

В Linux раздел **Найдено на этом компьютере** показывает containerd этого компьютера и containerd из k3s, если они отвечают. Сокет, который вам пока нельзя использовать, показывается вместе с тем, как это исправить.

### Доступ к сокету для вашего пользователя

Сокет containerd принадлежит root. Чтобы использовать его от имени другого пользователя, локально или по SSH, дайте доступ к нему группе в `/etc/containerd/config.toml` и добавьте пользователя в эту группу:

```bash
sudo groupadd -f containerd
sudo usermod -aG containerd "$USER"
getent group containerd | cut -d: -f3
```

Укажите выведенное число в секции `[grpc]` файла `/etc/containerd/config.toml`, перезапустите containerd и войдите снова:

```toml
[grpc]
  gid = 1001
```

```bash
sudo systemctl restart containerd
```

**Rootless containerd** (`containerd-rootless.sh`) держит свой сокет внутри пространства имён RootlessKit, куда ничто снаружи не может достучаться, даже Homeport. Обнаружив его, Homeport сообщает об этом; используйте вместо него системную службу containerd.

### Что позволяет каждая версия и каждое подключение

Homeport подключается к containerd **1.7** и новее. Скачивание идёт через службу Transfer containerd, стабильную начиная с **2.0**.

| Действие                                               | containerd  | Подключение                     |
| ------------------------------------------------------ | ----------- | ------------------------------- |
| Пространства имён, контейнеры и задачи, образы, снимки | 1.7 и новее | локальный сокет или SSH         |
| Скачивание образа                                      | 2.0 и новее | локальный сокет или SSH         |
| Журналы и терминал                                     | 1.7 и новее | SSH или локальный сокет в Linux |

Слишком старый для подключения containerd оставляет хост в состоянии **Ошибка настройки** с указанием версии; слишком старый для скачивания сообщает об этом при попытке скачать.

## Пространства имён

Каждый объект containerd находится в **пространстве имён**: nerdctl использует `default`, Kubernetes — `k8s.io`, Docker — `moby`, BuildKit — `buildkit`. Страницы показывают одно пространство имён за раз, выбранное под переключателем хостов, где у каждого указано, сколько в нём контейнеров и образов. Homeport запоминает выбор для каждого хоста между запусками. Пока вы ничего не выбрали, хост показывает `default` или, если `default` пусто, единственное непустое пространство имён, так что хост k3s открывается на `k8s.io`.

Страница **Пространства имён** создаёт пустые пространства имён и удаляет пустые. containerd отказывается удалять пространство имён, в котором ещё что-то есть, и Homeport сообщает, что именно: сначала удалите его контейнеры, образы и снимки.

## Контейнеры и задачи

В containerd **контейнер** — это только метаданные: его образ, его спецификация, его снимок. Работает его **задача**. Страница **Контейнеры** показывает контейнеры пространства имён с их задачей: **Работает**, **Приостановлен**, **Остановлен** с кодом выхода или **Нет задачи**. У каждого указано, каким инструментом он создан, — **Kubernetes** (с его Pod), **nerdctl**, **Docker** или **ctr или другой**, — а контейнеры pause у Pod скрыты, если вы не попросите их показать.

| Действие             | Что делает Homeport                                                                                                                                                                                                                                                       |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Запустить**        | Создаёт задачу на снимке контейнера с журналом там же, где его ведёт nerdctl, и запускает её. Остановленная задача заменяется, как того требует `ctr task start`.                                                                                                         |
| **Остановить**       | Отправляет сигнал остановки образа (SIGTERM, если образ не указывает другой), а через 10 секунд — SIGKILL. О задаче, которая и после этого жива, сообщается.                                                                                                              |
| **Приостановить**    | Замораживает задачу; **Возобновить** размораживает её.                                                                                                                                                                                                                    |
| **Отправить сигнал** | Отправляет любой сигнал, по имени (`SIGHUP`) или номеру, главному процессу задачи.                                                                                                                                                                                        |
| **Удалить**          | Сначала спрашивает; завершает работающую задачу, удаляет задачу и контейнер, а также его снимок с изменёнными файлами, если вы не снимете флажок **Также удалить**: сохранённый снимок помечается `containerd.io/gc.root`, чтобы сборщик мусора containerd его не трогал. |

Страница контейнера показывает его среду выполнения, снимок, метки и спецификацию OCI. Homeport не создаёт контейнеры в containerd: у containerd нет собственной сетевой подсистемы, её добавляют nerdctl и CNI.

Контейнерами Kubernetes управляет **kubelet**: он снова запускает их после остановки и снова создаёт после удаления. Их страницы сообщают об этом; вместо этого измените Pod в его кластере. Удаление контейнера nerdctl отсюда оставляет собственные записи nerdctl о нём (его имя и сеть), как и `ctr`; для таких контейнеров аккуратнее использовать `nerdctl rm`.

## Журналы

containerd не хранит журналов: куда пойдёт вывод задачи, решает инструмент, который её запускает. Вкладка **Журналы** читает вывод там, куда его записал этот инструмент:

| Кем создан             | Куда идёт вывод                                                                | Что показывает Homeport                             |
| ---------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------- |
| nerdctl                | файл журнала JSON в папке состояния nerdctl, указанный в его метках `nerdctl/` | этот файл, в режиме слежения                        |
| Kubernetes (`k8s.io`)  | `/var/log/pods/<pod>/<container>/N.log`, указанный в записи CRI о нём          | этот файл, в режиме слежения                        |
| `ctr` и другие клиенты | куда они его направили, обычно никуда                                          | **Вывод этого контейнера не записывается** и почему |

Контейнеры nerdctl, ведущие журнал через другой драйвер (journald, fluentd), вместо этого называют его. Homeport читает файл с помощью `tail` на машине хоста (см. [ниже](#что-запускается-на-хосте)); файлы журналов обычно принадлежат root, поэтому пользователю SSH должно быть разрешено их читать.

## Терминал в контейнере

Вкладка **Exec** открывает оболочку в работающем контейнере — bash, если он есть в образе, иначе sh — или заданную вами команду, от имени числового пользователя (`uid` или `uid:gid`) и в выбранной папке. **Открыть снова** запускает новый процесс с тем, что вы ввели.

containerd принимает ввод и вывод процесса как пути на своей машине. Поэтому Homeport запускает там короткий скрипт, который создаёт два FIFO во временной приватной папке и передаёт через них терминал; containerd запускает процесс на этих FIFO по спецификации процесса самого контейнера. Закрытие вкладки завершает процесс и удаляет папку.

## Образы

Страница **Образы** показывает образы пространства имён с их платформами, созданными из них контейнерами и размером для платформы хоста, как его считает `ctr images ls`.

**Скачать образ** получает образ через сам containerd, затем распаковывает его для платформы хоста в снапшоттер по умолчанию, чтобы `nerdctl run` мог сразу его использовать. Укажите полную ссылку (`ghcr.io/home/app:1.2`) или краткую (`nginx`, которая превращается в `docker.io/library/nginx:latest`). Образ из приватного реестра скачивается с входом из **Настройки → Реестры**, который передаётся containerd только тогда, когда его запрашивает реестр, и никогда не хранится на хосте.

Образ, из которого создан какой-либо контейнер пространства имён, удалить нельзя; сначала удалите контейнеры. containerd освобождает содержимое образа, как только его ничто не удерживает.

## Снимки

Снимки — это то, на что уходит диск containerd: слои распакованных образов и записываемый слой каждого контейнера. Страница **Снимки** показывает снимки одного снапшоттера (сначала `overlayfs` или любого другого, загруженного хостом) в виде дерева по родителям, начиная с самых больших, с их использованием диска, как его считает `ctr snapshot usage`, и итогом вверху.

У каждого указано, что его использует: контейнер — по своему снимку или образ — по своим слоям. Снимки, которые ничто не использует и на которых ничто не построено, — например, сохранённый при удалении его контейнера здесь, — можно показать отдельно через **Только неиспользуемые** и удалить. Остальные отсюда удалить нельзя. Снимок, на который ничто не ссылается и который ничто не помечает как корень, — например, оставленный `ctr containers rm --keep-snapshot`, — долго не живёт: сборщик мусора containerd удаляет его при следующем запуске.

## Что запускается на хосте

Всё описанное выше идёт через API containerd, кроме журналов и терминалов, которым нужны файлы машины containerd. Для них Homeport выполняет следующие команды — в уже открытом сеансе SSH или, для локального сокета в Linux, на этом компьютере — с правами пользователя SSH и никогда через `sudo`:

| Для чего | Команда                                                                                                            |
| -------- | ------------------------------------------------------------------------------------------------------------------ |
| Журналы  | `tail -n <lines> [-F] -- '<log file>'`; для контейнера Kubernetes без записи CRI — сначала `ls` его папки журналов |
| Терминал | `mktemp -d`, `mkfifo -m 600` для двух FIFO в этой папке, `cat` через них и `rm -rf` папки                          |

Локальный сокет в macOS или Windows не может их выполнить, и тогда журналы и терминалы сообщают, что им нужен SSH. На [странице безопасности](/docs/reference/security/#что-homeport-запускает-на-ваших-хостах) перечислены все команды, которые Homeport выполняет на хосте.

## События

Страницы обновляются по собственным событиям containerd во всех пространствах имён: запуск или завершение задачи, создание или удаление контейнера или образа, фиксация снимка. containerd не хранит их историю, поэтому то, что произошло, пока Homeport был закрыт, не восполняется.
