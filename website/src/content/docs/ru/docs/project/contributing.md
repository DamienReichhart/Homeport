Homeport разрабатывается открыто на [github.com/DamienReichhart/Homeport](https://github.com/DamienReichhart/Homeport). Вклад любого размера приветствуется.

## Сообщение об ошибке

[Создайте issue](https://github.com/DamienReichhart/Homeport/issues/new), указав:

- версию Homeport и платформу из раздела **Настройки** (например, `v0.2.0 · macos/aarch64`);
- тип хоста (локальный, SSH, TLS или TCP) и версию его движка;
- что вы сделали, чего ожидали и что произошло — точный текст сообщения помогает больше всего;
- всё существенное из [файла журнала](/docs/reference/security/#журналы).

О проблемах безопасности сообщайте, пожалуйста, конфиденциально, через [механизм сообщений об уязвимостях GitHub](https://github.com/DamienReichhart/Homeport/security/advisories/new).

## Предложение функции

Создайте issue с описанием проблемы, которую вы хотите решить, а не только решения. Понимание того, как вы работаете со своими движками, помогает найти для функции правильную форму.

## Участие кодом

1. Прочитайте [`docs/ARCHITECTURE.md`](https://github.com/DamienReichhart/Homeport/blob/main/docs/ARCHITECTURE.md). Функции — это самодостаточные вертикальные срезы, фронтенд обращается к Rust только через сгенерированные привязки IPC, а логика на Rust находится в сервисах, которые тестируются модульными тестами без Tauri.
2. Используйте словарь проекта из [`GLOSSARY.md`](https://github.com/DamienReichhart/Homeport/blob/main/GLOSSARY.md) — Host, Stack, Managed, External, Adopt — в коде, текстах интерфейса и коммитах. Основные решения записаны в [`docs/adr`](https://github.com/DamienReichhart/Homeport/tree/main/docs/adr).
3. Следуйте [руководству по бренду](https://github.com/DamienReichhart/Homeport/blob/main/docs/BRAND.md) в отношении цветов и стиля: просто, конкретно, спокойно, в британской орфографии.
4. Убедитесь, что проходят следующие проверки:

   ```sh
   bun run check
   bun run rust:lint
   bun run rust:test
   ```

5. Пишите сообщения коммитов в формате [Conventional Commits](https://www.conventionalcommits.org) — `feat(stacks): …`, `fix(hosts): …`. Из них формируются примечания к выпуску.
6. Откройте pull request в ветку `dev`. CI запускает проверки фронтенда и проверку лицензий в Linux, а `cargo clippy` и `cargo test` — в Linux, macOS и Windows, так что код под `#[cfg(windows)]` или `#[cfg(target_os = "macos")]` компилируется до слияния. Тест, которому нужен Docker Engine, помечается `#[ignore = "needs a local Docker Engine"]`; такие тесты запускает отдельное задание в Linux на движке исполнителя.

Чтобы подготовить окружение, см. [сборку из исходного кода](/docs/project/building/).

### Добавление текста в приложение

Тексты приложения хранятся в каталоге, никогда не встраиваются в код, чтобы их можно было перевести ([ADR 0011](https://github.com/DamienReichhart/Homeport/blob/main/docs/adr/0011-formatjs-catalogues-and-keyed-errors.md)). Чтобы добавить строку:

1. Добавьте ключ в файл функции в [`src/shared/i18n/en/`](https://github.com/DamienReichhart/Homeport/tree/main/src/shared/i18n/en) — `images.ts` для функции образов, `ui.ts` для набора компонентов UI, `common.ts` только для слов, которые везде значат одно и то же (Cancel, Close, Retry). Ключи начинаются с имени файла и говорят, для чего текст: `images.remove.title`, `images.column.size`.
2. Запишите значение как [сообщение ICU](https://formatjs.github.io/docs/core-concepts/icu-syntax/): `{name}` для значения, `{count, plural, one {# image} other {# images}}` вместо ручного построения форм множественного числа, `<strong>…</strong>` для выделения, отображаемого через `tRich`. Один ключ на предложение; не склеивайте фрагменты, потому что порядок слов в разных языках разный.
3. Используйте его через `t('images.remove.title', { name })` из `@/shared/i18n` — одинаково в компонентах, мутациях и уведомлениях. Ключи типизированы, так что опечатка не пройдёт проверку типов. Используйте литеральные ключи: если текст зависит от значения, сопоставьте значения с ключами (`{ start: 'containers.done.start', stop: 'containers.done.stop' }`), а не собирайте `` `containers.done.${action}` ``.

`bun run lint` завершается ошибкой, если компонент пишет текст прямо в коде: текст JSX, читаемые людьми свойства (`title`, `aria-label`, `placeholder`, `description`, `label`…) и текст уведомлений и подтверждений. Строки, которые читаются как код, а не как слова, — `tcp`, `nginx:latest`, `/dev/dri`, `max-size=10m`, — и имена собственные, такие как Docker или Podman, проходят. Чтобы намеренно оставить литерал, объясните причину строкой выше: `// eslint-disable-next-line homeport/no-literal-ui-string -- a shell command`. `bun run check` также завершается ошибкой при ключе, который используется в коде, но отсутствует в каталоге, при ключе, который нигде не используется, и при ключе, собираемом во время выполнения.

Сообщения об ошибках пишутся на Rust: каждый крейт объявляет свои ключи и английские шаблоны в блоке `messages!`, а `bun run bindings` записывает их в `src/shared/i18n/en/errors.json`. Не редактируйте этот файл вручную.

## Перевод Homeport

Приложение и сайт говорят на английском, французском, испанском, немецком, итальянском, бразильском португальском, русском, упрощённом китайском, японском, корейском, хинди и арабском. В каждом языке для каждого термина продукта используется одно слово: перед переводом найдите его в [`docs/i18n/`](https://github.com/DamienReichhart/Homeport/tree/main/docs/i18n), а выбрав новое, добавьте туда строку.

### Добавление или изменение строки

Какой бы ни была строка, `bun run check` (а значит, и CI) завершается ошибкой, пока она не появится во всех языках с теми же `{arguments}` и тегами и со всеми формами множественного числа, которые нужны этому языку.

- **Текст приложения**: добавьте ключ в `src/shared/i18n/en/<namespace>.ts` (см. [Добавление текста в приложение](#добавление-текста-в-приложение)), затем в одноимённый файл в папке каждого другого языка (`fr/`, `de/`, `zh-CN/`…). Переведите его, если можете. Если нет, скопируйте туда английский текст и укажите это в pull request, чтобы переводчик мог доделать; никогда не пропускайте ключ.
- **Сообщение об ошибке или подсказка**: объявите его в блоке `messages!` крейта и выполните `bun run bindings`, который записывает `en/errors.json`; затем добавьте ключ в `errors.json` каждого языка. Текст, который показывает операционная система, — меню трея и уведомления, — работает так же, с ключом `native.` и `native.json`.
- **Текст сайта** (главная, загрузка, список изменений, шапка и подвал): добавьте ключ в нужный файл `website/src/core/i18n/strings/en/` (`site`, `home`, `download` или `changelog`) и в тот же файл в папке каждого другого языка; `astro check` завершается ошибкой, если где-то его нет. Подпись в боковой панели документации добавляется в `website/src/app/config/sidebar/<code>.ts`.
- **Страница документации**: английская страница находится в `website/src/content/docs/docs/`. Изменяя её, обновите в том же pull request ту же страницу на каждом языке по тому же пути в `website/src/content/docs/<code>/docs/`; язык, страницу которого вы не можете обновить, показывает свой прежний перевод, пока это не сделает переводчик. Сохраняйте заголовки переведённых страниц в том же порядке и на тех же уровнях, что и в английском, а ссылки — в точности так, как их пишет английский, включая якоря: после `bun run build` команда `bun scripts/localize-anchors.ts <code>` направляет каждый якорь на переведённый заголовок, а проверка ссылок при второй сборке это подтверждает.

Проверить один язык можно командой `bun run i18n:check --locale fr`.

### Добавление языка

Файлы плюс одна строка для сайта:

1. **Приложение**: скопируйте `src/shared/i18n/en/` в `src/shared/i18n/<tag>/` (тег BCP 47, например `pl` или `zh-TW`), напишите его `meta.ts` (`{ name: 'Polski', dir: 'ltr' }` — собственное название языка; `rtl` для письма справа налево) и переведите каждый файл, сохраняя каждый ключ и превращая каждый `export default { … }` в `export default { … } satisfies Translation<typeof en>`, как в других языках. `bun run i18n:check --locale <tag>` перечисляет, чего не хватает. Настройки показывают новый язык, и язык ОС выбирает его без каких-либо других изменений.
2. **Сайт**: добавьте язык в `website/src/core/site/locales.ts`, затем его строки в копию `website/src/core/i18n/strings/en/` с именем `<code>/` (зарегистрированную в `TABLES` в `core/i18n/index.ts`), подписи боковой панели в `website/src/app/config/sidebar/<code>.ts` (зарегистрированный в `sidebar.ts`; эти две строки — единственный код, который нужен языку, потому что эти файлы загружаются вне Vite, а именно Vite находит папки) и примечание Starlight для непереведённых страниц в `website/src/content/i18n/<tag>.json`. Его страницы, URL, пункты переключателя языков, ссылки `hreflang` и альтернативы в карте сайта следуют из списка. Его документация размещается в `website/src/content/docs/<code>/docs/`: переведите там каждую страницу (вместо отсутствующей показывается английская с пометкой), затем после сборки запустите `bun scripts/localize-anchors.ts <code>`.
3. **Скриншоты**: `bun run screenshots` снимает все скриншоты на всех языках, включая новый, в `website/src/assets/screenshots/<tag>/`, так что каждая страница показывает приложение на языке своего читателя. `bun test` сайта падает, пока у какого-либо языка нет скриншота, который есть у английского.
4. **Термины**: добавьте `docs/i18n/terms-<tag>.md`.

Если тест не видит только что добавленный язык, удалите `node_modules/.vitest-cache`: Vitest может хранить старый список файлов каталогов.

## Улучшение этой документации

Внизу каждой страницы документации есть ссылка **Редактировать страницу**. Страницы — это файлы Markdown в [`website/src/content/docs`](https://github.com/DamienReichhart/Homeport/tree/main/website/src/content/docs).

## Как происходят выпуски

Каждая отправка в `main` с новым номером версии собирает установщики для всех платформ, запускает полный набор тестов и публикует релиз на GitHub с контрольными суммами и происхождением сборки. Процесс описан в [`docs/RELEASING.md`](https://github.com/DamienReichhart/Homeport/blob/main/docs/RELEASING.md).
