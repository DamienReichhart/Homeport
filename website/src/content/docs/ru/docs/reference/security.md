Homeport хранит учётные данные, открывающие доступ к вашим серверам. На этой странице точно объясняется, что он хранит и как это защищено. На странице [Ваши данные и резервные копии](/docs/reference/data-and-backups/) описано, что копировать для резервной копии и как её восстановить.

## Что хранит Homeport

Всё находится в одной базе данных SQLite, `homeport.db`, в папке данных приложений вашего пользователя:

| Система | Папка                                             |
| ------- | ------------------------------------------------- |
| Linux   | `~/.local/share/com.homeport.app/`                |
| macOS   | `~/Library/Application Support/com.homeport.app/` |
| Windows | `%APPDATA%\com.homeport.app\`                     |

В ней содержатся:

| Данные                                                              | Хранение         |
| ------------------------------------------------------------------- | ---------------- |
| Имена хостов, адреса, пользователи SSH и пути к сокетам             | Открытым текстом |
| Открытые ключи SSH и ключи серверов, которым вы доверились          | Открытым текстом |
| Закрытые ключи SSH и их парольные фразы                             | **Зашифрованы**  |
| Сертификаты ЦС TLS, клиентские сертификаты и ключи                  | **Зашифрованы**  |
| Клиентские ключи и закреплённые сертификаты хостов Incus            | **Зашифрованы**  |
| Compose-файлы управляемых стеков                                    | Открытым текстом |
| Окружения управляемых стеков                                        | **Зашифрованы**  |
| Папки связанных стеков и пути к compose-файлам                      | Открытым текстом |
| История развёртываний: compose-файлы и профили                      | Открытым текстом |
| История развёртываний: окружения                                    | **Зашифрованы**  |
| Адреса реестров и имена пользователей                               | Открытым текстом |
| Пароли и токены доступа к реестрам                                  | **Зашифрованы**  |
| URL репозиториев, открытые части ключей развёртывания               | Открытым текстом |
| Ключи серверов репозиториев, которым вы доверились                  | Открытым текстом |
| Ключи развёртывания и токены доступа репозиториев                   | **Зашифрованы**  |
| Имена кластеров, URL API-серверов и пространства имён               | Открытым текстом |
| Способ входа каждого кластера, его контекст kubeconfig              | Открытым текстом |
| ЦС, клиентские сертификаты и ключи кластеров                        | **Зашифрованы**  |
| Токены, пароли и токены OIDC кластеров                              | **Зашифрованы**  |
| Команды, аргументы и окружение плагинов exec                        | **Зашифрованы**  |
| Ваша тема, последний выбор и пространство имён для каждого кластера | Открытым текстом |
| События движка каждого хоста для страницы «События»                 | Открытым текстом |

Ничего другого Homeport из ваших движков не копирует: контейнеры, образы, тома и журналы читаются в реальном времени и никогда не сохраняются, кроме случаев, когда вы сами скачиваете журналы или файлы или делаете резервную копию тома. Хранимые им события движка — что произошло с каким контейнером, образом, томом или сетью, вместе с их метками — хранятся по умолчанию 30 дней ([Настройки → Данные](/docs/guides/settings/#данные)), не более 10 000 на хост, и удаляются вместе со своим хостом или кнопкой **Очистить историю**.

### Папки связанных стеков

Для [связанного стека](/docs/guides/stacks/#связанные-стеки) Homeport хранит только расположение его папки и compose-файлов, а также отпечаток файлов, чтобы замечать их изменения, — но никогда не их копию. Он читает compose-файлы, когда вы открываете стек, и записывает в них, только когда вы выбираете **Сохранить** на его вкладке **Определение**, заменяя каждый изменённый файл за один шаг и сохраняя его права доступа; он не перезапишет файл, изменившийся с момента открытия, если вы этого не подтвердите. Homeport никогда не читает и не записывает `.env` папки: его читает Compose при запуске. Если забыть связанный стек, папка никак не затрагивается.

### Репозитории

Для [синхронизируемых стеков](/docs/guides/synced-stacks/) Homeport хранит URL каждого репозитория и либо созданный им для этого репозитория ключ развёртывания (его закрытая часть зашифрована), либо ваше имя пользователя и токен доступа (зашифрованный). Содержимое репозитория не является секретом: его клон находится в папке `repositories` рядом с `homeport.db`.

### Swarm

Homeport ничего не хранит о [Swarm](/docs/guides/swarm/): он находит его через управляющие хосты при каждом подключении. Значения секретов Swarm уходят в Swarm и не хранятся в Homeport: значение, которое вы вводите или загружаете из файла, один раз отправляется движку, никогда не записывается в `homeport.db`, в файл или в журнал и удаляется из памяти при закрытии диалога. Движок никогда не возвращает значение секрета, поэтому Homeport тоже не может его показать. Токены присоединения запрашиваются у управляющего узла, когда они нужны, и никогда не хранятся и не записываются в журнал.

### Кластеры

Учётные данные [кластера](/docs/clusters/) берутся из вашего kubeconfig и хранятся только в зашифрованном виде, как ключи SSH; файлы, на которые ссылается kubeconfig, читаются один раз и встраиваются, вставленный kubeconfig никогда не записывается в файл, а ваш kubeconfig никогда не изменяется. [Плагин exec](/docs/clusters/exec-plugins/) запускается на этом компьютере от вашего имени, а выведенные им токен или сертификат хранятся только в памяти, пока не истечёт их срок. Больше ничего о том, что работает в кластере, Homeport не хранит: Pod, рабочие нагрузки и всё остальное читаются в реальном времени. [Пробросы портов](/docs/clusters/port-forward/) слушают только на интерфейсе loopback этого компьютера (`127.0.0.1` и `::1`), поэтому никто другой в вашей сети не может ими воспользоваться, и они завершаются при выходе из Homeport. Изменения, сделанные через [применение или изменение YAML](/docs/clusters/yaml/), записываются в кластере под менеджером полей `homeport`.

[Helm](/docs/clusters/helm/) запускает ваш CLI `helm` для кластера без вашего kubeconfig и без записи каких-либо учётных данных кластера на диск: для каждой команды Homeport открывает частное соединение на интерфейсе loopback этого компьютера (`127.0.0.1`, случайный порт), которое принимает только запросы со случайным токеном, и даёт helm временный kubeconfig, доступный для чтения только вам, содержащий этот токен и ничего больше. Homeport добавляет к каждому проходящему запросу собственные учётные данные кластера, а по завершении команды удаляет kubeconfig и закрывает соединение. Значения чарта передаются helm через стандартный ввод, никогда не в файле. Собственные репозитории чартов, входы в реестры и кэши helm остаются за helm, как в терминале; Homeport лишь добавляет публичные репозитории и не хранит паролей репозиториев.

Токен ACL, сертификат ЦС, клиентский сертификат и ключ [кластера Nomad](/docs/clusters/nomad/) хранятся только в зашифрованном виде, как ключи SSH; его адрес, регион и имя сервера TLS хранятся открыто. Токен передаётся в заголовке `X-Nomad-Token` каждого запроса, никогда в URL, в том числе в WebSocket оболочки. Homeport не хранит копию спецификации job: Nomad хранит её вместе с job.

**Значения Secret Kubernetes** запрашиваются, только когда вы выбираете **Показать** для одного ключа, по одному за раз: списки, страница Secret и его YAML содержат его ключи и размеры, но никогда не значения. Показанное значение остаётся в памяти этой страницы — ни в каком кэше, ни в `homeport.db`, ни в журнале — и снова скрывается, когда вы покидаете страницу.

## Как шифруются секреты

- Каждый секрет запечатывается отдельно с помощью **XChaCha20-Poly1305**, шифра с аутентификацией, так что не только предотвращается чтение, но и обнаруживается подделка.
- 256-битный ключ случаен, создаётся при первом запуске и хранится в **связке ключей ОС** — Связке ключей macOS, Диспетчере учётных данных Windows или Secret Service в Linux — под службой `com.homeport.app`. Он никогда не хранится рядом с данными.
- Мастер-пароля нет: связка ключей и так привязывает ключ к вашей учётной записи пользователя.

Тот, у кого есть только копия `homeport.db`, может прочитать имена и адреса хостов и кластеров, но не ваши ключи, сертификаты, токены, окружения стеков или пароли реестров.

### Без связки ключей

Homeport показывает баннер и не сохраняет секреты. Хосты с локальным сокетом, TCP и ssh-agent продолжают работать. См. [требования](/docs/requirements/#необязательно-связка-ключей-ос).

### Если ключ в связке ключей утерян

Сброс связки ключей или перенос `homeport.db` на другой компьютер или другому пользователю оставляет секреты, которые невозможно расшифровать. Homeport ничего не удаляет: затронутые хосты и кластеры показывают **Учётные данные утеряны**, пока вы не введёте их учётные данные заново; в разделе [Если секреты утеряны](/docs/reference/data-and-backups/#если-секреты-утеряны) перечислено, что и где ввести заново. Чтобы перенести данные, вместо этого [создайте резервную копию](#резервные-копии) или [экспортируйте хосты](#перенос-на-другой-компьютер).

### Перенос на другой компьютер

**Экспортировать** на странице «Хосты» записывает выбранные хосты в один файл вместе с их ключами, сертификатами и доверенными ключами серверов, зашифрованный выбранной вами парольной фразой:

- Весь файл зашифрован (XChaCha20-Poly1305 с ключом, полученным из парольной фразы через Argon2id), поэтому без парольной фразы он ничего не раскрывает — даже имён или адресов хостов. Любое изменение файла делает его нечитаемым.
- Парольная фраза должна содержать не менее 12 символов. Homeport никогда не хранит её и не записывает в журнал; если вы её потеряете, файл открыть не удастся.
- **Импортировать** на другом компьютере запрашивает парольную фразу, затем сохраняет секреты каждого хоста в зашифрованном виде под собственным ключом связки ключей этого компьютера, как любые другие.
- Хост, чьи учётные данные на этом компьютере уже утеряны, экспортируется без них, и экспорт сообщает, какой именно.

Обращайтесь с файлом как с ключами, которые в нём хранятся: удалите его после импорта. Формат описан в [ADR 0013](https://github.com/DamienReichhart/Homeport/blob/main/docs/adr/0013-passphrase-protected-export-bundles.md).

### Резервные копии

**Настройки → Данные → Создать резервную копию…** записывает всё перечисленное выше — хосты, кластеры, стеки, входы в реестры, репозитории и настройки вместе с их расшифрованными секретами — в один файл того же зашифрованного формата, с парольной фразой, которую вы вводите дважды. События движка и история развёртываний не включаются. Секрет, который на этом компьютере не удаётся открыть, пропускается, и резервная копия сообщает, какой именно.

**Восстановить…** запрашивает парольную фразу и показывает содержимое файла, прежде чем что-либо менять. Затем восстановление:

1. копирует текущую базу данных в `homeport.db.before-restore-<date and time>` рядом с `homeport.db`;
2. заменяет все хосты, кластеры, стеки, входы, репозитории и настройки за один шаг, так что при сбое ваши данные остаются прежними;
3. заново шифрует каждый секрет ключом связки ключей этого компьютера.

Резервная копия, созданная более новой версией Homeport, отклоняется; созданная более старой — восстанавливается. Резервная копия содержит все секреты Homeport: храните её и её парольную фразу так же надёжно, как сами ключи. На странице [Ваши данные и резервные копии](/docs/reference/data-and-backups/) описаны шаги, что входит в резервную копию и что нет, и как скопировать базу данных самостоятельно.

## Ключи никогда не попадают на диск в открытом виде

У Homeport свой клиент SSH, поэтому он никогда не записывает закрытый ключ в файл, чтобы его прочитал `ssh`, и никогда не изменяет `~/.ssh`. Расшифрованные ключи остаются в памяти.

Когда `docker compose` разворачивает стек на хосте SSH или TLS, Homeport открывает на этом компьютере кратковременный частный сокет — доступный для чтения только вашему пользователю, а в Windows именованный канал, отклоняющий удалённых клиентов, — и пробрасывает его через собственное подключение для этой одной команды.

Ключи и токены репозиториев тоже никогда не попадают на диск. Для каждой команды `git` Homeport предоставляет частный агент SSH, содержащий только ключ развёртывания этого репозитория, — на сокете, который может открыть только ваш пользователь, а в Windows на именованном канале, отклоняющем удалённых клиентов, — или передаёт токен в заголовке HTTPS через окружение команды. Ваша собственная конфигурация git, помощники учётных данных и ключи SSH не используются, поэтому ничего не кэшируется ни в вашей связке ключей, ни в `~/.git-credentials`.

Входы в реестры тоже никогда не попадают в `docker compose`: Homeport сам скачивает образы стека через Engine API перед запуском `docker compose up`, поэтому окружение команды и переданные ей файлы не содержат ни пароля, ни токена.

## Доверие к серверам

При первом подключении к серверу SSH Homeport просит подтвердить отпечаток ключа сервера и отказывается подключаться, если этот ключ потом изменится, пока вы не подтвердите снова. Хосты TLS проверяют сертификат сервера по вашему ЦС и имени сервера; хосты Incus по HTTPS принимают только тот сертификат, с которым были добавлены. См. [Хосты SSH](/docs/hosts/ssh/#первое-подключение).

### Сертификаты Incus

При добавлении [хоста Incus по HTTPS](/docs/hosts/incus/#по-https-с-токеном-доверия) в памяти создаются клиентский сертификат и его закрытый ключ ECDSA P-384, которые хранятся в зашифрованном виде вместе с другими секретами хоста и никогда не лежат на диске в открытом виде. Собственный сертификат Incus хранится так же и закрепляется: Homeport принимает от сервера только этот сертификат, сравнивая по отпечатку SHA-256, и отклоняет другой, показывая оба отпечатка. Токен доверия используется один раз и не хранится. Чтобы отозвать доступ, удалите сертификат Homeport на сервере командой `incus config trust remove`.

## К чему подключается Homeport

- **К добавленным вами хостам.** Когда вы скачиваете, отправляете или собираете образ, к реестру обращается движок, а не Homeport. Homeport передаёт ему вместе с запросом сохранённый вход для этого реестра через подключение хоста; движок его не сохраняет.
- **К реестрам ваших образов, через движок каждого хоста**, чтобы узнать, опубликован ли [более новый образ](/docs/guides/containers/#новые-версии-образов): при загрузке страниц «Контейнеры», «Образы» или «Стеки» (каждый ответ хранится 6 часов) и когда вы выбираете **Проверить новые версии образов**. Движок спрашивает у реестра дайджест, на который указывает тег, с сохранённым входом для приватных реестров и ничего не скачивает. Для локального хоста движок работает на вашем компьютере, поэтому запрос уходит с него.
- **К Docker Hub, когда вы просматриваете теги** в диалоге скачивания: Homeport получает список тегов репозитория с `hub.docker.com` с этого компьютера, с вашим входом в Docker Hub, если он сохранён. Поиск репозиториев вместо этого идёт через движок хоста.
- **К реестру, когда вы проверяете вход в него** в **Настройки → Реестры**: Homeport обращается к конечной точке `/v2/` реестра и его службе токенов с этого компьютера, отправляя имя пользователя и пароль или токен по HTTPS (обычный HTTP — только для реестра на этом компьютере, например `localhost:5000`).
- **К серверам ваших репозиториев** для [синхронизируемых стеков](/docs/guides/synced-stacks/): когда вы проверяете доступ, создаёте или синхронизируете синхронизируемый стек, а также с заданным интервалом, пока Homeport открыт, если опрос включён. Homeport запускает `git` с этого компьютера с ключом развёртывания или токеном этого репозитория.
- **К добавленным вами кластерам** через API-сервер Kubernetes, указанный в их kubeconfig (и его прокси, если он есть), с выданными им учётными данными, проверяя сертификат сервера по ЦС из kubeconfig. Плагины exec обращаются к своему облаку (AWS, Google Cloud, Azure) с этого компьютера, как и для `kubectl`.
- **К добавленным вами кластерам Nomad** через указанный вами адрес агента и больше ни к чему: журналы и оболочки job идут через этот агент, который пересылает их на client node, поэтому Homeport никогда не подключается к самим узлам. Сертификат агента проверяется по указанному вами ЦС или по ЦС этого компьютера.
- **К серверам образов Incus** для выбора образа на [хосте Incus](/docs/guides/instances/#создание-экземпляра): Homeport скачивает с этого компьютера список образов сервера (`streams/v1/images.json`, с `images.linuxcontainers.org`, если вы не выберете другой) и хранит его десять минут. Сами образы скачивает Incus.
- **К репозиториям чартов и реестрам OCI, через helm**, когда вы добавляете или обновляете репозиторий, ищете чарты или устанавливаете либо обновляете чарт: `helm` скачивает индексы и чарты с этого компьютера, как в терминале.
- **К этому сайту, для проверки обновлений**: при запуске и каждые 6 часов Homeport скачивает `updates/latest.json` — небольшой файл с последней версией. Запрос не несёт ничего ни о вас, ни о ваших хостах, ни о контейнерах, но, как любой веб-запрос, приходит с вашего IP-адреса на GitHub Pages, где размещён этот сайт. Отключите его в **Настройки → Обновления**. Сами обновления скачиваются с GitHub Releases, и Homeport устанавливает обновление, только если оно подписано ключом обновлений Homeport. См. [обновление](/docs/reference/updating/).

## Что Homeport запускает на ваших хостах

Homeport общается с движком хоста через его API и запускает команды на сервере хоста только для того, чего этот API не умеет:

| Когда                                                                                     | Где                                                         | Команда                                                                                                            |
| ----------------------------------------------------------------------------------------- | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Сервер хоста SSH отказывается открыть сокет движка                                        | сервер SSH                                                  | проверка в оболочке POSIX: существует ли сокет и доступен ли он для чтения, установлен ли движок                   |
| **Запустить**, **Остановить** или **Перезапустить** [юнит Quadlet](/docs/guides/quadlet/) | сервер SSH или этот компьютер для локального сокета в Linux | `systemctl [--user] start\|stop\|restart '<unit>.service'`                                                         |
| [Журналы контейнера containerd](/docs/hosts/containerd/#журналы)                          | сервер SSH или этот компьютер для локального сокета в Linux | `tail -n <lines> [-F] -- '<log file>'`, после `ls` папки журналов контейнера Kubernetes, если CRI не называет файл |
| [Терминал в контейнере containerd](/docs/hosts/containerd/#терминал-в-контейнере)         | сервер SSH или этот компьютер для локального сокета в Linux | `mktemp -d`, `mkfifo -m 600` для двух FIFO в этой папке, `cat` через них, затем `rm -rf` папки                     |

Они выполняются с правами пользователя SSH (или с вашими, на этом компьютере) и никогда через `sudo`. Значения проверяются и экранируются, прежде чем попасть в команду. Установка, изменение и удаление юнитов Quadlet идут через API Podman, который сам записывает файлы. На хосте Incus ничего не запускается: его консоль и терминалы идут через собственный API Incus. Единственные файлы, которые Homeport создаёт на хосте, — два FIFO терминала containerd во временной приватной папке, удаляемой при закрытии терминала.

## Чего Homeport никогда не делает

- **Никакой учётной записи.** Регистрироваться негде.
- **Никакой телеметрии, аналитики или отчётов о сбоях.** Когда вы сообщаете об ошибке, [пакет диагностики](/docs/reference/troubleshooting/#экспорт-диагностики-для-сообщения-об-ошибке) — это файл, который вы сами экспортируете, просматриваете и прикладываете.
- **Ничего не устанавливается в ваши кластеры.** Homeport использует только API Kubernetes с правами ваших учётных данных и ничего не меняет без вашей просьбы: всё, что удаляет или заменяет что-либо, сначала спрашивает, называя кластер.
- **Ничего не устанавливается на ваши хосты.** Единственные команды, которые Homeport выполняет на хосте, [перечислены выше](#что-homeport-запускает-на-ваших-хостах). Единственный контейнер, который Homeport когда-либо запускает сам, — кратковременный [вспомогательный контейнер](/docs/guides/volumes-networks/#вспомогательный-контейнер), когда вы открываете, сохраняете в резервную копию, восстанавливаете или клонируете том; у него нет сети, и он удаляется по завершении. Его образ скачивается только с вашего согласия.
- **Никаких скрытых установок.** Обновление устанавливается, только когда вы выбираете **Установить и перезапустить**; пакеты для Linux обновляет только ваш менеджер пакетов.

В [политике конфиденциальности](/privacy/) изложено, что это означает с юридической точки зрения: кто отвечает за ваши данные, на каком основании и как осуществлять свои права.

## Журналы

Homeport пишет небольшой файл журнала — несколько десятков килобайт, заменяемый при заполнении — для диагностики проблем. Он содержит события подключения и ошибки, но не ваши учётные данные и не вывод контейнеров.

| Система | Папка                                   |
| ------- | --------------------------------------- |
| Linux   | `~/.local/share/com.homeport.app/logs/` |
| macOS   | `~/Library/Logs/com.homeport.app/`      |
| Windows | `%LOCALAPPDATA%\com.homeport.app\logs\` |

У Homeport нет телеметрии и отчётов о сбоях: журнал никогда не покидает ваш компьютер, если вы сами его не отправите. Для сообщения об ошибке **Настройки → О программе → Экспортировать диагностику…** сохраняет zip-архив со сводкой версий и этими журналами, заменив всё, что похоже на секрет (ключи, пароли, токены, учётные данные в URL), а также, если вы не попросите иначе, имена и адреса ваших хостов и кластеров. См. [Экспорт диагностики](/docs/reference/troubleshooting/#экспорт-диагностики-для-сообщения-об-ошибке).

## Доверие к загрузке

Релизы собираются GitHub Actions из публичного исходного кода. Каждый файл сопровождается контрольной суммой SHA-256 и подписанной аттестацией происхождения сборки, которая связывает его с точным коммитом и процессом, его собравшими. См. [проверку загрузок](/docs/reference/verifying/).
