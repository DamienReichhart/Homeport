**Стек** — это проект Compose, работающий на хосте. Homeport находит все стеки на выбранном хосте по меткам, которые Compose ставит на их контейнеры, как бы они ни были развёрнуты.

## Управляемые, связанные, синхронизируемые и внешние стеки

Каждый стек относится к одному из четырёх видов:

| Вид                  | Где находится его файл compose                              | Изменение | Развёртывание | Сборка | Запуск, остановка, удаление |
| -------------------- | ----------------------------------------------------------- | --------- | ------------- | ------ | --------------------------- |
| **Управляемый**      | В Homeport, с окружением в зашифрованном виде               | ✓         | ✓             | —      | ✓                           |
| **Связанный**        | В папке проекта на **этом** компьютере                      | ✓         | ✓             | ✓      | ✓                           |
| **Синхронизируемый** | В git-репозитории, который Homeport клонирует и отслеживает | git       | ✓             | ✓      | ✓                           |
| **Внешний**          | Там, где Homeport его не видит: развёрнут иным способом     | —         | —             | —      | ✓                           |

- **Управляемый стек** — это стек, файл compose и окружение которого хранит Homeport. Его можно изменять, разворачивать и сворачивать из Homeport.
- **Связанный стек** — это стек, файлы compose которого находятся в папке на этом компьютере, где вы продолжаете их редактировать. Homeport запоминает, где находится папка, работает с файлами в ней и разворачивает из неё. См. [Связанные стеки](#связанные-стеки).
- **Синхронизируемый стек** — это стек, файл compose которого берётся из git-репозитория. Homeport получает его ветку или тег, показывает, что изменилось, и разворачивает новый коммит; он изменяется через git, а не в Homeport. См. [Синхронизируемые стеки](/docs/guides/synced-stacks/).
- **Внешний стек** был развёрнут иным способом — `docker compose up` на сервере, задание CI, другой инструмент или из папки на другом компьютере. Homeport может запускать, останавливать, перезапускать и удалять его контейнеры, но у него нет файла compose, чтобы развернуть стек заново. Вы можете [взять его под управление](#взятие-внешнего-стека-под-управление), чтобы сделать его управляемым.

Каждый стек находится в одном из этих состояний:

| Состояние             | Значение                                                                          |
| --------------------- | --------------------------------------------------------------------------------- |
| **Работает**          | Работают все его контейнеры.                                                      |
| **Работает частично** | Работают некоторые.                                                               |
| **Остановлен**        | Не работает ни один.                                                              |
| **Не развёрнут**      | Управляемый, связанный или синхронизируемый стек, у которого ещё нет контейнеров. |

Управляемые, связанные и синхронизируемые стеки принадлежат одному хосту или одному Swarm. Чтобы запустить один и тот же файл compose на двух хостах, создайте стек на каждом.

<Aside>
  Стеки, развёрнутые в [Swarm](/docs/guides/swarm/) из терминала или из Homeport, перечислены не
  здесь, а на собственной странице Swarm, на вкладке **Стеки**. Чтобы развернуть такой стек,
  выберите Swarm в поле **Куда развернуть** на странице **Новый стек**. См. [Развёртывание стеков в
  Swarm](/docs/guides/swarm/#развёртывание-стеков-в-swarm).
</Aside>

## Связанные стеки

**Связанный стек** хранит свои файлы compose в папке проекта на этом компьютере, где вы редактируете их в своём редакторе и держите под контролем версий. Homeport никогда их не копирует: он запоминает папку и используемые файлы compose по порядку и читает их там, где они лежат. Файл `.env` папки остаётся в папке.

Связанный стек можно также развернуть в Swarm, при этом его `configs: file:` и `secrets: file:` читаются из папки; см. [Связанные и синхронизируемые стеки в Swarm](/docs/guides/swarm/#связанные-и-синхронизируемые-стеки-в-swarm).

### Создание связанного стека

Папку проекта, который ещё не работает на хосте, можно связать из Homeport:

<Steps>

1. Откройте **Стеки**, выберите **Новый стек**, затем **Использовать папку на этом компьютере**.

2. Выберите **Выбрать папку…** и укажите папку с проектом compose.

3. Homeport перечисляет файлы compose, которые Compose использовал бы там, по порядку: первый из `compose.yaml`, `compose.yml`, `docker-compose.yml` и `docker-compose.yaml`, затем его файл переопределений (`compose.override.yaml` и подобные), если он есть. Папку, в которой нет ни одного из них, связать нельзя, и Homeport сообщает об этом.

4. Проверьте **Имя**. Оно берётся из `name:` верхнего уровня в файлах или из имени папки в том виде, в каком его записывает Compose (`My App` становится `myapp`).

5. Выберите **Сохранить и развернуть** — или **Сохранить**, чтобы развернуть позже.

</Steps>

Если стек с таким именем уже работает на хосте как внешний, создание связанного стека берёт его под управление, как это делает [взятие под управление](#взятие-внешнего-стека-под-управление): повторное развёртывание пересоздаёт его контейнеры в соответствии с файлами папки. Чтобы использовать файлы с другими именами или в другом порядке, см. [Несколько файлов compose](#несколько-файлов-compose).

### Как находятся связанные стеки

Когда вы запускаете `docker compose up` в папке, Compose помечает каждый контейнер этой папкой и её файлами compose — даже когда `DOCKER_HOST` указывает на удалённый хост. Когда Homeport перечисляет стеки хоста, найденный работающий стек показывается как **Связанный**, если:

1. обе метки есть, а папка и все файлы compose, которые они называют, существуют на этом компьютере, и
2. эти файлы определяют работающие сервисы: каждый работающий сервис есть в файлах, и у каждого сервиса, который файлы определяют вне профиля, есть контейнер.

Второе правило не даёт пути, который случайно существует здесь, связать не те файлы, — например, стек, запущенный на самом сервере в `/srv/app`, когда на этом компьютере тоже есть `/srv/app`. Файлы, использующие `include:` или `extends:`, не отслеживаются, поэтому такой стек пока остаётся внешним. Для поиска связанных стеков Compose CLI не нужен.

Папка показывается под именем стека в списке и на его странице.

### Изменение связанного стека

Вкладка **Определение** связанного стека показывает каждый его файл compose на отдельной вкладке, прочитанный из папки, с путём к папке над ними. Измените их и выберите **Сохранить**: Homeport записывает каждый изменённый файл обратно на место, так что ваш собственный редактор и система контроля версий видят изменение. Файл заменяется за один шаг с сохранением его прав, так что никто никогда не прочитает его записанным наполовину.

Проверки под редактором следуют правилам для связанных стеков: `build:`, `env_file:` и относительные пути допустимы, поскольку папка на месте. Редактора окружения нет: Compose читает файл `.env` папки при запуске, а Homeport его не показывает и не изменяет.

#### Изменено вне Homeport

Homeport отмечает файлы каждый раз, когда читает или записывает их. Когда они отличаются — вы изменили их в другом редакторе или получили новую версию, — вкладка показывает **Изменено вне Homeport**. Он проверяет это при открытии вкладки и каждый раз, когда вы возвращаетесь в окно Homeport. Выберите **Перезагрузить**, чтобы увидеть файлы в текущем виде; несохранённые правки будут отброшены.

Если вы сохраняете файл, который был изменён на диске после того, как вы его открыли, Homeport отказывает: **compose.yaml изменился вне Homeport после того, как вы его открыли**. Перезагрузите, чтобы увидеть чужое изменение, или выберите **Перезаписать**, чтобы заменить его своей версией.

Если папки больше нет или файл не удаётся прочитать, вместо редактора вкладка сообщает, какой именно, и что делать.

### Развёртывание и сборка связанного стека

**Развернуть**, **Развернуть заново**, **Скачать образы** и **Свернуть** работают и для связанных стеков. Homeport запускает `docker compose` в папке стека, с `--project-directory`, указывающим на неё, и по одному `--file` на каждый его файл compose, по порядку, — так же, как если бы вы запустили его там сами, — по-прежнему через собственное подключение для хостов SSH и TLS. Поэтому `build:`, `env_file:`, пути `./relative` и файл `.env` папки работают.

Сервис с `build:` собирается, когда у него ещё нет образа. Чтобы пересобрать его после изменения кода, выберите **Пересобрать и развернуть** в меню **⋮** стека (`up --build`). Сборка выполняется движком **хоста**, а контекст сборки отправляется с этого компьютера. Сервисы с `build:` никогда не скачиваются; их базовые образы скачивает сама сборка, с вашим собственным `docker login`.

**Сохранить и развернуть заново** на вкладке **Определение** записывает изменённые вами файлы, затем разворачивает.

<Aside type="caution" title="Относительные пути на удалённом хосте">
  Bind-монтирование вроде `./data:/data` указывает на папку на **этом** компьютере, например
  `/home/me/site/data`. На удалённом хосте такого пути может не быть, и движок вместо этого создаёт
  там пустую папку. Когда вы разворачиваете связанный стек на хосте, который не является этим
  компьютером, вывод начинается с предупреждения для каждого такого монтирования. Для данных,
  которые должны жить на хосте, используйте именованный том или абсолютный путь на хосте.
</Aside>

Если папки больше нет, развёртывание останавливается с сообщением **Папки … больше нет на этом компьютере**. Без Compose CLI связанные стеки всё равно можно запускать, останавливать и удалять.

### Когда папка перемещена или исчезла

Если файлов compose связанного стека больше нет на месте — папку переместили, переименовали или удалили, — стек показывается как **Внешний** с пометкой ⚠ **Его файлов compose больше нет на этом компьютере**. Из Homeport и с хоста ничего не удаляется: верните файлы на место, и при следующем обновлении стек снова станет связанным. Чтобы прекратить связь, откройте его вкладку **Определение** и выберите **Забыть**; это лишь удаляет запись Homeport о папке, но никогда не саму папку или контейнеры.

Стек, запущенный из папки на другом компьютере, на этом компьютере является внешним, поскольку его метки указывают на путь, которого здесь нет.

## Что нужно для развёртывания

Homeport разворачивает управляемые, связанные и синхронизируемые стеки командой `docker compose` на **этом** компьютере, направленной на хост. Установите Docker CLI с плагином Compose или отдельный `docker-compose` v2; **Настройки → Этот компьютер** показывает, нашёл ли его Homeport.

Для управляемого стека команда запускается с файлом compose на стандартном вводе, окружением стека в виде переменных и пустой рабочей папкой, так что на диск ничего не записывается. Для связанного стека она запускается в папке стека с его файлами compose, как если бы вы запустили её там. Для хостов SSH и TLS Homeport направляет команду через собственное подключение к хосту, так что Compose никогда не видит ваших ключей.

Без Compose CLI вы всё равно можете запускать, останавливать и удалять стеки; он нужен только для **Развернуть**, **Скачать образы** и **Свернуть**.

### Приватные образы

Перед `docker compose up` Homeport скачивает образы, которых ещё нет на хосте, через собственное подключение к хосту, с [входом в реестр](/docs/guides/settings/#реестры), сохранённым для реестра каждого образа, поэтому приватные образы разворачиваются на любом хосте без `docker login` на этом компьютере. Вывод развёртывания показывает каждое скачивание и используемый вход — **Pulling ghcr.io/org/app:1 as alice on ghcr.io** или **anonymously**, — но никогда не пароль. Сервис с `pull_policy: always` скачивается каждый раз; `never` и `build` не трогаются.

Самому Compose вход никогда не передаётся: ни один файл, который Homeport создаёт для запуска, и ни одна переменная окружения команды его не содержит. Ваш собственный `docker login` на этом компьютере к этим скачиваниям не применяется; вместо этого добавьте вход в **Настройки → Реестры**. Если реестр отказывает в образе, развёртывание останавливается до запуска Compose, а сообщение предлагает добавить или проверить вход.

## Создание управляемого стека

<Steps>

1. Откройте **Стеки** и выберите **Новый стек**. Выбрано **Написать файл compose**.

2. Выберите [шаблон](#начало-с-шаблона) — или **Пустой**, чтобы начать с нуля.

3. Введите **Имя**: строчные буквы, цифры, `-` и `_`, начинается с буквы или цифры. Шаблон предлагает имя. Оно становится именем проекта Compose, и изменить его потом нельзя.

4. Отредактируйте файл compose в редакторе.

5. Поместите переменные в **Окружение**, по одной `KEY=value` на строку, как в файле `.env`. Compose подставляет их вместо `${KEY}` в файле. Заполните пароли, которые шаблон оставляет пустыми.

6. Выберите **Сохранить и развернуть** — или **Сохранить**, чтобы развернуть позже.

</Steps>

### Начало с шаблона

Страница «Новый стек» открывается на галерее шаблонов. Каждый — это файл compose и окружение, следующие хорошим практикам: теги образов закреплены за версией, данные — в именованных томах, а секреты — в окружении, а не в файле. Используйте **Tab**, чтобы переходить между карточками, и **Enter**, чтобы выбрать; **Выбрать другой шаблон** возвращает назад.

| Шаблон                      | Что он запускает                                                              |
| --------------------------- | ----------------------------------------------------------------------------- |
| **Статический сайт**        | nginx, отдающий файлы из именованного тома, на порту `HTTP_PORT`.             |
| **PostgreSQL и Adminer**    | PostgreSQL и Adminer на `ADMINER_PORT` для его просмотра.                     |
| **MariaDB**                 | MariaDB с базой данных и пользователем для приложения.                        |
| **Redis**                   | Redis с паролем, сохраняющий данные на диск.                                  |
| **Обратный прокси (Caddy)** | Caddy, перенаправляющий `SITE_ADDRESS` на `UPSTREAM`, с автоматическим HTTPS. |
| **Uptime Kuma**             | Uptime Kuma для наблюдения за сайтами и сервисами, на `HTTP_PORT`.            |
| **WordPress**               | WordPress с собственной базой данных MariaDB.                                 |
| **Пустой**                  | Секция `services:`, которую вы заполните сами.                                |

Пароли оставлены пустыми, с комментарием о том, что туда вписать: заполните их перед развёртыванием. При взятии внешнего стека под управление галерея пропускается и открывается пустой редактор.

### Проверки по мере ввода

Homeport проверяет определение по мере ввода и перечисляет проблемы под редактором. Какие правила применяются, зависит от вида стека.

**Ошибки** не дают развернуть:

- YAML не удаётся разобрать, или в нём нет `services:` — для любого вида.
- У сервиса нет ни `image:`, ни `build:` — для любого вида.
- Сервис использует `build:` — только для **управляемых стеков**. Собирать не из чего, поэтому используйте образ, отправленный в реестр, или вместо этого [свяжите папку](#создание-связанного-стека).

**Предупреждения**, только для **управляемых стеков**, позволяют развернуть, но указывают на то, что, вероятно, сработает не так, как вы ожидаете, потому что Compose читает это с этого компьютера, а не с хоста. Папка связанного стека на месте, поэтому для него это допустимо:

- Bind-монтирование с относительным путём, например `./data:/data`. Используйте абсолютный путь на хосте или именованный том.
- `env_file:` или `configs` и `secrets`, читаемые из `file:`. Вместо этого поместите переменные в окружение стека.

### Окружение

Окружение хранится в зашифрованном виде и передаётся прямо в Compose, никогда не записываясь на диск, — подходящее место для паролей и токенов. Сам файл compose хранится открытым текстом, поэтому не держите в нём секреты:

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
```

```ini
DB_PASSWORD=correct-horse-battery-staple
```

Допускаются пустые строки, `# comments` и префиксы `export`. Значения можно заключать в кавычки; в двойных кавычках `\n` — это перевод строки.

<Aside>
  Для хранения окружения нужна [связка ключей ОС](/docs/requirements/#необязательно-связка-ключей-ос). Без
  неё поле неактивно, и стеки разворачиваются без окружения.
</Aside>

## Несколько файлов compose

Стек может состоять из нескольких файлов compose, объединяемых по порядку, так же, как их объединяет `docker compose -f compose.yaml -f compose.prod.yaml`: базовый файл, затем переопределения, которые добавляют или изменяют ключи, — `ports:` для продакшена, отладочный сервис для разработки.

**Управляемые стеки** показывают над редактором по вкладке на каждый файл. Выберите **Добавить файл**, чтобы добавить файл (Homeport предлагает `compose.override.yaml`, `compose.prod.yaml` и так далее), переименуйте его в поле **Имя файла**, передвиньте раньше или позже стрелками или удалите. Первый файл — базовый, и удалить его нельзя. Имена заканчиваются на `.yaml` или `.yml`.

С одним файлом Homeport, как и раньше, передаёт его Compose на стандартный ввод. С несколькими он записывает их на время выполнения команды в приватную папку, которую может открыть только ваш пользователь, и затем удаляет её. Окружение туда никогда не записывается: оно по-прежнему передаётся Compose в виде переменных.

**Связанные стеки** перечисляют свои файлы по порядку в боковой панели вкладки **Определение**. **Добавить файл…** выбирает ещё один файл compose из папки стека — например, `compose.prod.yaml` вместо стандартного файла переопределений, — а стрелки и **✕** меняют порядок и удаляют файлы. Сначала сохраните или перезагрузите правки: изменение набора файлов перезагружает редактор.

Проверки рассматривают объединённые файлы, так что сервис, определённый в базовом файле и получивший `ports:` в переопределении, проверяется как один сервис.

## Профили

Файлы compose часто прячут необязательные сервисы — отладочные инструменты, воркеры, локальную базу данных — за `profiles:`:

```yaml
services:
  app:
    image: ghcr.io/org/app:1.4
  adminer:
    image: adminer:4.8.1
    profiles: [debug]
```

Сервисы без профиля работают всегда. Сервисы за профилем работают, только когда стек его включает. Когда файлы управляемого, связанного или синхронизируемого стека объявляют профили, его вкладка **Определение** показывает **Профили** с флажком для каждого. Включите профиль и выберите **Сохранить и развернуть заново** — или **Сохранить профили**, чтобы применить его при следующем развёртывании.

Выключение профиля и повторное развёртывание удаляет контейнеры его сервисов: Homeport удаляет их перед `docker compose up`, поскольку сам Compose оставляет их работать. **Свернуть** удаляет сервисы всех профилей, которые объявляют файлы, включены они или нет.

Учитываются только профили стека. Переменная `COMPOSE_PROFILES` в вашей оболочке, в окружении управляемого стека или в `.env` связанного стека не меняет того, что разворачивает Homeport. Связанный стек, найденный по меткам compose, начинает без включённых профилей, даже если он был запущен с `--profile`: включите их на его вкладке **Определение**. Если включённый вами профиль исчезает из файлов, Homeport сообщает об этом и выключает его при следующем сохранении.

## Развёртывание и повторное развёртывание

**Развернуть** — или **Развернуть заново**, когда стек уже работает, — запускает `docker compose up --detach --remove-orphans`. Окно показывает вывод Compose по мере выполнения и заканчивается строкой **✓ Готово** или кодом выхода, с которым он завершился сбоем.

<Aside type="caution">
  Закрытие окна вывода во время работы Compose останавливает его, что может оставить развёртывание
  выполненным наполовину. Разверните заново, чтобы его завершить.
</Aside>

Чтобы изменить управляемый стек, откройте его, измените его **Определение** и выберите **Сохранить и развернуть заново**. Compose пересоздаёт только изменившиеся сервисы и удаляет сервисы, которые вы убрали из файла.

### Проверка изменений перед повторным развёртыванием

Прежде чем запустится повторное развёртывание — **Развернуть заново**, **Пересобрать и развернуть** или **Сохранить и развернуть заново** для работающего стека, — Homeport показывает **Проверьте изменения**: определение, развёрнутое в прошлый раз (самая новая успешная запись его [истории](#история-развёртываний-и-откат)), в сравнении с тем, которое будет развёрнуто.

- Каждый файл compose показывает изменённые строки прямо в тексте: удалённые строки над теми, что их заменяют. Неизменённый файл свёрнут; выберите его, чтобы раскрыть. Добавленные, удалённые или объединяемые в другом порядке файлы называются.
- Переменные окружения показывают только имена с пометкой **Добавлено**, **Удалено** или **Изменено** — изменённый пароль отображается как **Изменено** без показа какого-либо значения, — а также сколько остальных не изменилось.
- Включение или выключение профиля тоже показывается.

Выберите **Развернуть**, чтобы перейти к запуску, или **Назад**, чтобы вернуться в редактор, ничего не меняя. Если ничего не изменилось, проверка сообщает об этом и предлагает **Всё равно развернуть заново**. Если Homeport не знает, что развёрнуто, — стек был развёрнут до того, как Homeport начал вести историю, или вне его, — проверка сообщает об этом и показывает определение, которое будет развёрнуто. Первое развёртывание, откат и [обновление](#обновление-стека) пропускают проверку.

Сравниваются только определения, а не текущая конфигурация контейнеров на хосте.

## История развёртываний и откат

Каждое развёртывание управляемого, связанного или синхронизируемого стека из Homeport — **Развернуть**, **Развернуть заново**, **Пересобрать и развернуть**, **Сохранить и развернуть заново**, [синхронизация](/docs/guides/synced-stacks/#синхронизация) — записывается вместе с использованными файлами compose, окружением и профилями, временем запуска и результатом; для синхронизируемого стека также показываются его коммит и то, было ли развёртывание запущено автоматически. Вкладка **История** на странице стека перечисляет последние 20, сначала самые новые: **Успешно**, **Сбой** с кодом выхода или **Не завершено** для запуска, окно которого было закрыто до его окончания. **Развёрнуто сейчас** отмечает самое новое успешное.

Выберите развёртывание, чтобы увидеть его файлы compose в режиме только для чтения. Его окружение хранится в зашифрованном виде, как и окружение самого стека, и вкладка показывает только имена его переменных. Без связки ключей список всё равно работает; развёртывание с окружением просто сообщает, что его нельзя открыть.

Чтобы отменить неудачное изменение **управляемого** стека, выберите развёртывание, которое работало, и нажмите **Откатить**. Homeport возвращает его файлы compose, окружение и профили на место текущих, затем разворачивает заново, так что следующей записью в истории будет сам откат.

<Aside type="caution" title="Что восстанавливает откат">
  Только определение. Образы скачиваются заново по указанным в нём тегам в их текущем виде — если
  `app:1.4` с тех пор был отправлен заново, вы получите новый `app:1.4`. Тома и их данные остаются
  как есть.
</Aside>

История **связанного** стека доступна только для чтения: его папка — его источник, поэтому восстановите прежние файлы там — например, с помощью вашей системы контроля версий — и разверните заново. Если забыть стек, его история тоже удаляется.

- **Журналы** показывает журналы всех контейнеров вместе, каждая строка помечена своим сервисом.

## Обновление стека

**Доступно обновление** рядом с состоянием стека означает, что один из его сервисов работает на образе, тег которого указывает на более новую версию в его реестре; наведите указатель, чтобы увидеть, какие сервисы. На странице стека **Сервисы** называет их и отмечает каждый устаревший образ. **Проверить новые версии образов** вверху страницы «Стеки» снова опрашивает реестры. Проверка та же, что использует страница «Контейнеры», — см. [Новые версии образов](/docs/guides/containers/#новые-версии-образов), — поэтому открытие «Стеков» сразу после «Контейнеров» больше ничего у реестров не запрашивает. У образа, закреплённого дайджестом (`app@sha256:…`), никогда не бывает обновления, а сервис с `build:` не проверяется.

Чтобы обновить управляемый, связанный или синхронизируемый стек, выберите **Обновить**. Оно выполняет оба шага в одном окне: скачивает образ каждого сервиса с сохранёнными входами, затем запускает `docker compose up` со скачанным, так что новые контейнеры получают только сервисы, у которых изменился образ. Перед началом окно сообщает, какие образы новее, и [шага проверки](#проверка-изменений-перед-повторным-развёртыванием) нет, поскольку определение не меняется. Если скачивание не удаётся, обновление на этом останавливается: работающие контейнеры остаются как были, а ошибка объясняет причину и что делать.

Внешний стек тоже показывает **Доступно обновление**, но его кнопка **Обновить** неактивна: у Homeport нет файла compose, чтобы развернуть его заново, поэтому сначала [возьмите его под управление](#взятие-внешнего-стека-под-управление). Сервисы с `build:` в связанном стеке никогда не скачиваются; для них используйте **Пересобрать и развернуть**.

## Действия со стеком

| Действие                               | Стеки                  | Что делает                                                                                                          |
| -------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------- |
| **Развернуть** / **Развернуть заново** | Управляемые, связанные | `docker compose up` с определением стека.                                                                           |
| **Пересобрать и развернуть**           | Связанные              | `docker compose up --build`: сначала пересобирает все сервисы с `build:`.                                           |
| **Запустить** / **Остановить**         | Любые                  | Запускает остановленные контейнеры или останавливает работающие.                                                    |
| **Перезапустить**                      | Любые                  | Перезапускает все контейнеры.                                                                                       |
| **Скачать образы**                     | Управляемые, связанные | Скачивает образ каждого сервиса с сохранёнными входами, чтобы получить новые версии перед повторным развёртыванием. |
| **Свернуть**                           | Управляемые, связанные | `docker compose down`: удаляет контейнеры и сети, сохраняет тома и определение.                                     |
| **Свернуть вместе с томами**           | Управляемые, связанные | Также удаляет тома стека **вместе с их данными**.                                                                   |
| **Удалить контейнеры**                 | Внешние                | Удаляет его контейнеры и сети. Тома сохраняются.                                                                    |
| **Взять под управление**               | Внешние                | Передаёт Homeport файл compose, делая стек управляемым.                                                             |

**Забыть определение** на вкладке **Определение** управляемого стека удаляет файл compose и окружение из Homeport, но оставляет контейнеры работающими; стек становится внешним. **Забыть** на вкладке **Определение** связанного стека удаляет запись Homeport о папке; папка, её файлы и контейнеры не затрагиваются.

## Взятие внешнего стека под управление

<Steps>

1. Откройте внешний стек и выберите **Взять под управление**.

2. Вставьте файл compose, с которым он был развёрнут. Имя заполнено и заблокировано.

3. Добавьте его переменные окружения, если он их использовал.

4. Выберите **Сохранить**, чтобы взять его под управление, не трогая работающие контейнеры, или **Сохранить и развернуть**, чтобы развернуть его заново сейчас.

</Steps>

<Aside type="caution" title="Используйте то же определение">
  Повторное развёртывание с другим файлом пересоздаёт контейнеры в соответствии с ним и удаляет
  сервисы, которых в нём больше нет. Пути, которые были относительными на машине, где стек был
  развёрнут впервые, теперь могут указывать на другие места.
</Aside>

Создание нового стека с тем же именем, что и у внешнего, тоже берёт его под управление.
