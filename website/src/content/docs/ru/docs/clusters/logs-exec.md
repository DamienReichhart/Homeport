На странице Pod есть вкладки **Журналы** и **Терминал**, а на странице рабочей нагрузки — вкладка **Журналы** для всех её Pod: повседневные `kubectl logs` и `kubectl exec -it` через API Kubernetes с собственными учётными данными кластера.

## Журналы

**Журналы** передаёт журналы контейнера по мере их записи. Это тот же просмотрщик, что и для контейнера на хосте:

- **История**: начать с последних 100, 1000 или 10 000 строк либо со всех.
- **С**: только строки за последние минуты, часы или дни.
- **Метки времени**: время, которое Kubernetes записал для каждой строки.
- **Следить**: держать в поле зрения самую новую строку; выключите, чтобы читать назад, пока продолжают поступать новые строки.
- **Найти в журналах**, **Очистить** и **Скачать журналы** (в виде текстового файла, уже показанные строки).

У Pod с несколькими контейнерами есть выбор **Контейнер**, init-контейнеры отмечены. Он открывается на том контейнере, который выбрал бы `kubectl`: на указанном в аннотации `kubectl.kubernetes.io/default-container` Pod, иначе на его первом контейнере приложения.

Kubernetes хранит стандартный вывод и стандартный поток ошибок контейнера вместе, поэтому фильтра stdout/stderr, как у контейнеров хоста, здесь нет.

Поток останавливается, когда вы уходите с вкладки, и сообщает, когда контейнер останавливается.

### Почему он упал?

Если контейнер перезапускался, **Предыдущий запуск** показывает журналы запуска перед последним перезапуском — для Pod в `CrashLoopBackOff` это запуск, который упал, — как `kubectl logs --previous`. Для контейнера, который ни разу не перезапускался, он выключен, ведь показывать нечего.

Если контейнер ещё не запустился (`ContainerCreating`, `CrashLoopBackOff`, пока он ждёт повторного запуска), журналы сообщают об этом на своём месте с указанием причины. Страница его Pod объясняет, чего он ждёт.

### Журналы рабочей нагрузки

Вкладка **Журналы** у Deployment, StatefulSet, DaemonSet или Job перемежает журналы всех его Pod по мере их записи, и каждая строка помечена своим Pod своим цветом, как в `kubectl logs -l app=api --prefix`. Выберите один Pod, чтобы читать только его, и контейнер, если в шаблоне их несколько.

## Терминал

**Терминал** открывает оболочку в одном из работающих контейнеров Pod: `bash`, если он есть в образе, иначе `sh`. Вместо этого введите команду в поле (`psql -U app shop`, `top`), и **Подключиться** запустит её, разобрав кавычки, как это сделала бы оболочка.

Это настоящий TTY: `vi`, `top`, цвета и клавиши со стрелками работают, а изменение размера окна меняет размер терминала в контейнере. Когда процесс завершается, терминал сообщает код завершения; **Переподключиться** запускает новый. Уход с вкладки завершает процесс в контейнере.

### Если он не открывается

- **Нет оболочки**: в минимальных (distroless) образах оболочки нет вовсе. Введите команду, которая есть в образе, или подключите отладочный контейнер из терминала командой `kubectl debug -it <pod> --image=busybox --target=<container>`; Homeport не создаёт отладочные контейнеры.
- **Не запущен**: контейнер, который ожидает или завершился, ничего запустить не может. Pod завершённого Job остановились навсегда.
- **Не разрешено**: для открытия терминала нужен `create` на `pods/exec`, а для чтения журналов — `get` на `pods/log`, которых часто нет у ролей только для чтения. Homeport говорит, чего именно не хватает, и даёт команду `kubectl auth can-i` для проверки.

Homeport не копирует файлы в Pod и из него (`kubectl cp`).
