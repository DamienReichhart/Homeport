Ein ⬆ neben dem Namen bedeutet, dass eines der Tags des Images in seiner Registry auf ein neueres Image zeigt; fahren Sie mit dem Mauszeiger darüber, um zu sehen, welches. ## Ein Image pullen

Wählen Sie **Image pullen** und geben Sie eine Referenz ein: `nginx` (was `nginx:latest` bedeutet), `nginx:1.27`, `ghcr.io/org/app:v2`, `registry.example.com:5000/app` oder einen Digest wie `app@sha256:…`.

Homeport zeigt den Fortschritt des Pulls Layer für Layer und meldet **Fertig.**, wenn er abgeschlossen ist. **Abbrechen** hört auf, dem Pull zu folgen.

### Docker Hub durchsuchen

Die Eingabe eines bloßen Namens wie `postg` durchsucht Docker Hub schon beim Tippen und listet die passenden Repositorys mit ihrer Beschreibung, ihren Sternen und einer Markierung **Offiziell** auf. Wählen Sie eines, um seine Tags zu sehen, die neuesten zuerst, mit ihrer Größe und dem Zeitpunkt des Pushs; **Tags filtern** grenzt die Liste ein (`alpine`), und **Weitere Tags** lädt die nächste Seite. Die Wahl eines Tags füllt die Referenz aus, etwa `postgres:17-alpine`, bereit zum **Pullen**.

Die Suche läuft auf dem ausgewählten Host und erreicht Docker Hub daher über das Netzwerk des Hosts, so wie der Pull es tun wird. Tags liest dieser Computer von Docker Hub; eine gespeicherte Docker-Hub-[Anmeldung](/docs/guides/settings/#registries) erhöht dessen Ratenlimits. Die Eingabe eines Tags, eines Digests oder einer anderen Registry (`ghcr.io/…`) überspringt die Suche, und ist Docker Hub nicht erreichbar, sagt der Dialog das und pullt trotzdem, was Sie eingeben. Andere Registrys lassen sich noch nicht durchsuchen.

### Private Images

Ist in [**Einstellungen → Registrys**](/docs/guides/settings/#registries) eine Anmeldung für die Registry des Images gespeichert, übergibt Homeport sie mit dem Pull an die Engine, sodass private Images auf jedem Host gepullt werden – lokal, TCP, TLS oder SSH –, ohne dass dort etwas eingerichtet ist. Unter der Referenz sagt der Dialog, wie das Image gepullt wird: **Als alice auf ghcr.io gepullt** oder **Anonym gepullt**, wenn keine Anmeldung passt.

Ein Image ohne Registry im Namen (`nginx`, `bitnami/redis`) verwendet die Docker-Hub-Anmeldung. Eine Docker-Hub-Anmeldung erhöht außerdem das Pull-Limit von Docker Hub.

Lehnt die Registry den Pull ab, sagt die Meldung, was zu tun ist: eine Anmeldung für diese Registry hinzufügen, wenn keine gespeichert war, oder die gespeicherte prüfen.

<Aside>
  Die Anmeldung gelangt mit der Anfrage zur Engine und wird nicht auf dem Host gespeichert. Homeport
  liest keine `docker login`-Zugangsdaten aus `~/.docker/config.json`.
</Aside>

## Ein Image bauen

Wählen Sie **Bauen** und einen **Ordner** auf diesem Computer, der ein Dockerfile enthält – den Build-Kontext. Homeport packt den Ordner, lässt alles weg, was seine `.dockerignore` ausschließt (nach den Regeln von Docker: `*`, `**`, `!`-Ausnahmen, die letzte passende Zeile gewinnt), und streamt ihn an den ausgewählten Host, dessen Engine ihn baut. Derselbe Build funktioniert auf einem entfernten Host über SSH oder TLS, ohne dass dort etwas installiert ist.

| Feld                            | Was es bewirkt                                                                                                  |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **Dockerfile**                  | Sein Pfad im Ordner; standardmäßig `Dockerfile`. Es wird immer gesendet, auch wenn `.dockerignore` es aufführt. |
| **Ziel-Stage**                  | Die Stage eines mehrstufigen Dockerfiles, bei der angehalten wird (`--target`).                                 |
| **Namen**                       | Ein oder mehrere Namen für das Ergebnis, etwa `app:1.0, ghcr.io/me/app:1.0`.                                    |
| **Build-Argumente**             | `NAME=value`, eines pro Zeile, für die `ARG`s des Dockerfiles.                                                  |
| **Build-Cache nicht verwenden** | Führt jeden Schritt erneut aus (`--no-cache`).                                                                  |
| **Neuere Basis-Images pullen**  | Pullt die `FROM`-Images, auch wenn der Host sie hat (`--pull`).                                                 |

Die Ausgabe des Builds wird live gestreamt; **Abbrechen** stoppt ihn. Wenn er fertig ist, erscheinen die Namen auf der Seite Images. Schlägt ein Schritt fehl, nennt die Meldung ihn (**Der Build ist bei Schritt 3/5 (RUN make) fehlgeschlagen.**), und **Details** enthält das Ende der Ausgabe. Private `FROM`-Images werden mit den gespeicherten [Registry-Anmeldungen](/docs/guides/settings/#registries) gepullt.

<Aside>
  Homeport verwendet den klassischen Builder der Engine, den ihre API anbietet. BuildKit-Funktionen
  wie `RUN --mount` und Build-Secrets sind nicht verfügbar; bauen Sie solche in einem Terminal.
</Aside>

### Stattdessen einen Container committen

Ein Image kann auch aus einem Container entstehen: **Als Image committen…** im Menü **⋮** eines Containers speichert seine Dateien und Einstellungen so, wie sie jetzt sind – siehe [Einen Container committen](/docs/guides/containers/#committing-a-container). Das ist der schnelle Weg, zu behalten, was jemand in einem laufenden Container installiert oder geändert hat. Ein Build ist der dauerhafte Weg: Sein Dockerfile sagt, wie das Image entsteht, sodass es neu gebaut, geprüft und aktualisiert werden kann, wenn sich das Basis-Image weiterentwickelt. Ein committetes Image kann das nicht.

## Ein Image pushen

Wählen Sie **Pushen** im Menü **⋮** eines Images. **Zu pushender Name** beginnt mit dem ersten Namen des Images; wählen Sie einen anderen seiner Namen oder geben Sie einen neuen ein, etwa `ghcr.io/org/app:v2` – das Image erhält diesen Namen zuerst, wie bei **Taggen**. Der erste Teil des Namens sagt, in welche Registry es geht: `ghcr.io/org/app` geht zu GHCR, `org/app` zu Docker Hub.

Homeport pusht über die Engine des Hosts mit der für diese Registry gespeicherten [Registry-Anmeldung](/docs/guides/settings/#registries) und sagt unter dem Namen, welche (**Als alice auf ghcr.io gepusht**). Ist keine Anmeldung gespeichert, warnt der Dialog vor dem Start, da die meisten Registrys anonyme Pushes ablehnen. Während er läuft, zählt der Dialog die gepushten Layer und die, die die Registry bereits hatte, und zeigt den laufenden Upload; **Abbrechen** stoppt den Push.

Lehnt die Registry ab, sagt die Meldung, ob eine Anmeldung hinzugefügt oder geprüft werden muss, ob die gespeicherte in dieses Repository pushen darf.

## Images speichern und laden

Um Images auf einen Host zu bringen, der keine Registry erreicht – einen Air-Gap-Server, einen Raspberry Pi im Heimnetz –, speichern Sie sie in einer Datei auf diesem Computer und laden die Datei in den anderen Host.

- **Speichern…** im Menü **⋮** eines Images schreibt es mit allen seinen Namen in eine `.tar`-Datei Ihrer Wahl. Um mehrere auf einmal zu speichern, kreuzen Sie sie in der Liste an und wählen oben auf der Seite **N Images speichern…**.
- **Laden…** oben auf der Seite liest eine mit **Speichern…** oder `docker save` erstellte `.tar` – auch komprimierte `.tar.gz` – in den ausgewählten Host ein. Wenn es fertig ist, nennt der Dialog die geladenen Images mit ihren Tags.

Die Datei wird über die eigene Verbindung des Hosts zwischen diesem Computer und dem Host übertragen, daher funktioniert das auch bei entfernten Hosts. Der Fortschritt zeigt die geschriebenen oder gesendeten Bytes; **Abbrechen** stoppt den Vorgang, und ein abgebrochenes oder fehlgeschlagenes Speichern hinterlässt keine unvollständige Datei. Homeport hält nie das ganze Archiv im Arbeitsspeicher, daher sind Images von mehreren Gigabyte kein Problem.

### Ein Dateisystem importieren

**Aus tar importieren…** oben auf der Seite macht aus einem tar eines Root-Dateisystems ein Image, wie `docker import`: eines, das mit [**Dateisystem exportieren…**](/docs/guides/containers/#exporting-a-containers-filesystem) eines Containers oder `docker export` erstellt wurde, eine Ausgabe von `debootstrap` oder Buildroot oder eine Appliance eines Herstellers. Wählen Sie die Datei (unkomprimiert oder mit gzip, xz oder bzip2 komprimiert), geben Sie dem Image einen **Namen** – er beginnt mit dem Dateinamen – und optional **Änderungen**: Dockerfile-Anweisungen wie `CMD ["/bin/sh"]` oder `ENV LANG=C.UTF-8`, da ein importiertes Image keinen eigenen Befehl hat. Der Fortschritt zeigt die gesendeten Bytes; das Image erscheint dann in der Liste.

### Speichern und Laden oder Exportieren und Importieren?

|              | **Speichern** / **Laden**                                  | **Dateisystem exportieren** / **Aus tar importieren**                                 |
| ------------ | ---------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Geht aus von | Einem oder mehreren Images                                 | Den Dateien eines Containers, so wie sie jetzt sind                                   |
| Behält       | Jeden Layer, die Historie, die Namen und die Einstellungen | Nur die Dateien, zu einem Layer zusammengefasst                                       |
| Verliert     | Nichts                                                     | Historie, Namen und Einstellungen wie Befehl und Umgebung                             |
| Wofür        | Images auf einen Host ohne Registry bringen                | Die Dateien eines Containers sichern oder untersuchen, oder von einem rootfs ausgehen |

## Mit einem Image arbeiten

- **▶ Ausführen** öffnet den [Dialog zum Ausführen](/docs/guides/containers/#running-a-container) mit eingetragenem Image.
- **Untersuchen** – oder die Auswahl der Zeile – zeigt **Layer**, die Anweisungen, die jeden Layer gebaut haben, und ihre Größen, sowie **Rohes JSON**.
- **Taggen** fügt einen weiteren Namen hinzu, etwa `registry.example.com/app:v2`. Es pusht nichts; das tut **Pushen**.
- **Entfernen** löscht das Image und die Layer, die kein anderes Image verwendet. Ein Image mit mehreren Tags verliert alle. Die Engine weigert sich, ein Image zu entfernen, das ein Container noch verwendet; entfernen Sie zuerst den Container.

## Aufräumen

**Aufräumen** bietet zwei Stufen:

- **Verwaiste Images** – ungetaggte Images, die Builds und Pulls hinterlassen haben. Sie können gefahrlos entfernt werden.
- **Alle unbenutzten Images** – jedes Image, das kein Container verwendet, getaggte eingeschlossen. Sie lassen sich erneut pullen, aber das kostet Zeit und Bandbreite.

Homeport sagt Ihnen, wie viele entfernt wurden und wie viel Platz frei wurde. Das [Aufräumen in der Übersicht](/docs/guides/overview/#cleaning-up) kann außerdem gestoppte Container, Netzwerke, Build-Cache und Volumes in einem Durchgang entfernen.
