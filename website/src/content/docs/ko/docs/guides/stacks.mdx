## 관리형, 링크된, 동기화, 외부 스택

모든 스택은 다음 네 종류 중 하나입니다.

| 종류       | compose 파일의 위치                            | 편집 | 배포 | 빌드 | 시작, 중지, 삭제 |
| ---------- | ---------------------------------------------- | ---- | ---- | ---- | ---------------- |
| **관리형** | Homeport 안. 환경은 암호화됨                   | ✓    | ✓    | —    | ✓                |
| **링크됨** | **이** 컴퓨터의 프로젝트 폴더                  | ✓    | ✓    | ✓    | ✓                |
| **동기화** | Homeport가 클론하고 따라가는 git 저장소        | git  | ✓    | ✓    | ✓                |
| **외부**   | Homeport가 볼 수 없는 곳. 다른 방법으로 배포됨 | —    | —    | —    | ✓                |

- **관리형 스택** 유형은 Homeport가 compose 파일과 환경을 보관하는 스택입니다. Homeport에서 편집, 배포하고 내릴 수 있습니다.
- **링크된 스택** 유형은 compose 파일이 이 컴퓨터의 폴더에 있고 그곳에서 계속 편집하는 스택입니다. Homeport는 폴더의 위치를 기억하고, 그곳의 파일을 다루며, 그 폴더에서 배포합니다. [링크된 스택](#링크된-스택)을 참고하세요.
- **동기화 스택** 유형은 compose 파일을 git 저장소에서 가져오는 스택입니다. Homeport가 브랜치나 태그를 가져와 무엇이 바뀌었는지 보여 주고 새 커밋을 배포합니다. 편집은 git으로 하며, Homeport에서는 절대 하지 않습니다. [동기화 스택](/docs/guides/synced-stacks/)을 참고하세요.
- **외부 스택** 유형은 서버에서 실행한 `docker compose up`, CI 작업, 다른 도구, 또는 다른 컴퓨터의 폴더 등 다른 방법으로 배포된 스택입니다. Homeport는 그 컨테이너를 시작, 중지, 다시 시작, 삭제할 수 있지만, 다시 배포할 compose 파일이 없습니다. 스택을 [관리형으로 전환](#외부-스택을-관리형으로-전환)하면 관리형 스택이 됩니다.

각 스택은 다음 상태 중 하나로 표시됩니다.

| 상태              | 의미                                                    |
| ----------------- | ------------------------------------------------------- |
| **실행 중**       | 모든 컨테이너가 실행 중입니다.                          |
| **일부 실행 중**  | 일부 컨테이너만 실행 중입니다.                          |
| **중지됨**        | 실행 중인 컨테이너가 없습니다.                          |
| **배포되지 않음** | 아직 컨테이너가 없는 관리형, 링크된, 동기화 스택입니다. |

관리형, 링크된, 동기화 스택은 호스트 하나 또는 Swarm 하나에 속합니다. 같은 compose 파일을 두 호스트에서 실행하려면 각 호스트에 스택을 만드세요.

<Aside>
  터미널에서든 Homeport에서든 [Swarm](/docs/guides/swarm/)에 배포한 스택은 여기가 아니라 Swarm 자체
  페이지의 **스택** 탭에 나열됩니다. Swarm에 배포하려면 **새 스택** 페이지의 **배포 대상** 항목에서
  Swarm을 고르세요. [Swarm에 스택 배포](/docs/guides/swarm/#swarm에-스택-배포)를 참고하세요.
</Aside>

## 링크된 스택

**링크된 스택** 유형은 compose 파일을 이 컴퓨터의 프로젝트 폴더에 보관하며, 사용자는 그곳에서 직접 쓰는 편집기로 파일을 편집하고 버전 관리합니다. Homeport는 파일을 복사하지 않습니다. 폴더와 사용하는 compose 파일을 순서대로 기억하고, 파일을 있는 자리에서 읽습니다. 폴더의 `.env`는 폴더에 그대로 남습니다.

링크된 스택은 Swarm에도 배포할 수 있으며, 이때 `configs: file:`과 `secrets: file:`은 폴더에서 읽습니다. [Swarm의 링크된 스택과 동기화 스택](/docs/guides/swarm/#swarm의-링크된-스택과-동기화-스택)을 참고하세요.

### 링크된 스택 만들기

아직 호스트에서 실행되지 않는 프로젝트 폴더는 Homeport에서 링크할 수 있습니다.

<Steps>

1. **스택** 페이지를 열고 **새 스택** 버튼을 누른 다음 **이 컴퓨터의 폴더 사용** 항목을 고릅니다.

2. **폴더 선택…** 버튼을 누르고 compose 프로젝트가 있는 폴더를 고릅니다.

3. Homeport는 Compose가 그 폴더에서 사용할 compose 파일을 순서대로 나열합니다. `compose.yaml`, `compose.yml`, `docker-compose.yml`, `docker-compose.yaml` 중 첫 번째 파일, 그다음 재정의 파일(`compose.override.yaml` 등)이 있으면 그 파일입니다. 이 중 어떤 파일도 없는 폴더는 링크할 수 없으며, Homeport가 그 사실을 알려 줍니다.

4. **이름** 항목을 확인합니다. 파일의 최상위 `name:`에서 가져오거나, Compose가 쓰는 방식대로 폴더 이름에서 가져옵니다(`My App`은 `myapp`이 됩니다).

5. **저장 후 배포** 버튼을 누릅니다. 나중에 배포하려면 **저장** 버튼을 누르세요.

</Steps>

같은 이름의 스택이 이미 호스트에서 외부 스택으로 실행 중이면, 링크된 스택을 만들 때 [관리형으로 전환](#외부-스택을-관리형으로-전환)할 때처럼 그 스택을 넘겨받습니다. 다시 배포하면 폴더의 파일에 맞게 컨테이너가 다시 생성됩니다. 다른 이름의 파일이나 다른 순서를 쓰려면 [여러 compose 파일](#여러-compose-파일)을 참고하세요.

### 링크된 스택을 찾는 방법

폴더에서 `docker compose up`을 실행하면, `DOCKER_HOST`가 원격 호스트를 가리키더라도 Compose는 모든 컨테이너에 그 폴더와 compose 파일의 레이블을 붙입니다. Homeport가 호스트의 스택을 나열할 때, 실행 중으로 발견된 스택은 다음 조건을 만족하면 **링크됨** 상태로 표시됩니다.

1. 두 레이블이 모두 있고, 레이블이 가리키는 폴더와 모든 compose 파일이 이 컴퓨터에 있으며,
2. 그 파일들이 실행 중인 서비스를 정의합니다. 즉, 실행 중인 모든 서비스가 파일에 있고, 파일이 프로필 밖에서 정의하는 모든 서비스에 컨테이너가 있습니다.

두 번째 규칙은 우연히 여기에도 있는 경로가 엉뚱한 파일을 링크하지 않게 합니다. 예를 들어 서버 자체의 `/srv/app`에서 시작한 스택이 있고, 이 컴퓨터에도 `/srv/app`이 있는 경우입니다. `include:`나 `extends:`를 사용하는 파일은 따라가지 않으므로, 그런 스택은 지금으로서는 외부 스택으로 남습니다. 링크된 스택을 찾는 데는 Compose CLI가 필요하지 않습니다.

폴더는 목록과 스택 페이지에서 스택 이름 아래에 표시됩니다.

### 링크된 스택 편집

링크된 스택의 **정의** 탭은 폴더에서 읽은 각 compose 파일을 각자의 탭에 보여 주며, 위쪽에 폴더 경로를 표시합니다. 파일을 편집하고 **저장** 버튼을 누르세요. Homeport가 변경된 각 파일을 원래 자리에 다시 쓰므로, 직접 쓰는 편집기와 버전 관리에서도 변경 사항이 보입니다. 파일은 권한을 유지한 채 한 번에 교체되므로, 반쯤 쓰인 파일을 읽는 일은 없습니다.

편집기 아래의 검사는 링크된 스택의 규칙을 따릅니다. 폴더가 있으므로 `build:`, `env_file:`, 상대 경로는 문제없습니다. 환경 편집기는 없습니다. Compose가 실행될 때 폴더의 `.env`를 읽으며, Homeport는 이 파일을 보여 주거나 변경하지 않습니다.

#### Homeport 밖에서 변경됨

Homeport는 파일을 읽거나 쓸 때마다 파일 상태를 기록합니다. 다른 편집기에서 편집했거나 새 버전을 풀해서 파일이 달라지면, 탭에 **Homeport 밖에서 변경됨** 표시가 나타납니다. 탭이 열릴 때와 Homeport 창으로 돌아올 때마다 확인합니다. 현재 상태의 파일을 보려면 **다시 불러오기** 버튼을 누르세요. 저장하지 않은 편집 내용은 사라집니다.

파일을 연 뒤 디스크에서 변경된 파일을 저장하면 Homeport가 거부합니다. **파일을 연 이후 Homeport 밖에서 compose.yaml 파일이 변경되었습니다.** 다시 불러와 다른 변경 사항을 확인하거나, **덮어쓰기** 버튼을 눌러 내 버전으로 바꾸세요.

폴더가 없어졌거나 파일을 읽을 수 없으면, 탭에 편집기 대신 어느 것이 문제인지와 해결 방법이 표시됩니다.

### 링크된 스택 배포와 빌드

**배포**, **다시 배포**, **이미지 풀**, **내리기** 기능은 링크된 스택에서도 작동합니다. Homeport는 스택의 폴더에서 `docker compose`를 실행하며, `--project-directory`를 그 폴더로 설정하고 compose 파일마다 `--file`을 하나씩 순서대로 지정합니다. 직접 그곳에서 실행하는 것과 같지만, SSH와 TLS 호스트에서는 여전히 Homeport 자체 연결을 거칩니다. 따라서 `build:`, `env_file:`, `./relative` 경로, 폴더의 `.env`가 모두 작동합니다.

`build:`가 있는 서비스는 아직 이미지가 없을 때 빌드됩니다. 코드를 변경한 뒤 다시 빌드하려면 스택의 **⋮** 메뉴에서 **다시 빌드 후 배포** 항목을 고르세요(`up --build`). 빌드는 **호스트의** 엔진에서 실행되며, 빌드 컨텍스트는 이 컴퓨터에서 전송됩니다. `build:`가 있는 서비스는 풀하지 않습니다. 기본 이미지는 빌드 과정에서 사용자 자신의 `docker login`으로 풀됩니다.

**정의** 탭의 **저장 후 다시 배포** 버튼은 편집한 파일을 쓴 다음 배포합니다.

<Aside type="caution" title="원격 호스트의 상대 경로">
  `./data:/data` 같은 바인드 마운트는 **이** 컴퓨터의 폴더(예: `/home/me/site/data`)로 해석됩니다.
  원격 호스트에는 그 경로가 없을 수 있으며, 그러면 엔진이 대신 그곳에 빈 폴더를 만듭니다. 이
  컴퓨터가 아닌 호스트에 링크된 스택을 배포하면, 출력의 시작 부분에 이런 마운트마다 경고가
  표시됩니다. 호스트에 있어야 하는 데이터에는 이름 있는 볼륨이나 호스트의 절대 경로를 사용하세요.
</Aside>

폴더가 없어졌으면 배포가 **… 폴더가 더 이상 이 컴퓨터에 없습니다.** 오류와 함께 멈춥니다. Compose CLI가 없어도 링크된 스택을 시작, 중지, 삭제할 수는 있습니다.

### 폴더가 이동하거나 사라졌을 때

폴더를 옮기거나 이름을 바꾸거나 삭제해서 링크된 스택의 compose 파일이 더 이상 그 자리에 없으면, 스택은 ⚠ **compose 파일이 더 이상 이 컴퓨터에 없습니다.** 표시와 함께 **외부** 상태로 표시됩니다. Homeport나 호스트에서 아무것도 삭제되지 않습니다. 파일을 되돌려 놓으면 다음 새로 고침 때 다시 링크된 스택이 됩니다. 링크를 그만두려면 **정의** 탭을 열고 **잊기** 버튼을 누르세요. 이는 Homeport가 기록한 폴더 정보만 지우며, 폴더나 컨테이너는 절대 지우지 않습니다.

다른 컴퓨터의 폴더에서 시작한 스택은 레이블이 이 컴퓨터에 없는 경로를 가리키므로, 이 컴퓨터에서는 외부 스택입니다.

## 배포에 필요한 것

Homeport는 **이** 컴퓨터의 `docker compose` 명령을 호스트에 연결해 관리형, 링크된, 동기화 스택을 배포합니다. Compose 플러그인이 포함된 Docker CLI 또는 독립 실행형 `docker-compose` v2를 설치하세요. **설정 → 이 컴퓨터** 항목에서 Homeport가 찾았는지 확인할 수 있습니다.

관리형 스택에서는 compose 파일을 표준 입력으로, 스택의 환경을 변수로 전달하고 빈 작업 폴더에서 명령을 실행하므로 디스크에 아무것도 기록되지 않습니다. 링크된 스택에서는 직접 실행하는 것처럼 스택의 폴더에서 compose 파일과 함께 명령을 실행합니다. SSH와 TLS 호스트에서는 Homeport가 호스트에 대한 자체 연결로 명령을 전달하므로, Compose는 사용자의 키를 볼 수 없습니다.

Compose CLI가 없어도 스택을 시작, 중지, 삭제할 수 있습니다. Compose CLI가 필요한 것은 **배포**, **이미지 풀**, **내리기** 기능뿐입니다.

### 비공개 이미지

`docker compose up` 전에 Homeport는 호스트에 아직 없는 이미지를, 각 이미지의 레지스트리용으로 저장된 [레지스트리 로그인](/docs/guides/settings/#레지스트리)을 사용해 호스트에 대한 자체 연결로 풀합니다. 따라서 이 컴퓨터에서 `docker login`을 하지 않아도 어떤 호스트에서든 비공개 이미지를 배포할 수 있습니다. 배포 출력에는 각 풀과 그 풀에 사용한 로그인이 표시되며(**ghcr.io에서 alice 사용자로 ghcr.io/org/app:1 풀하는 중**, 또는 **익명으로**), 비밀번호는 절대 표시되지 않습니다. `pull_policy: always`인 서비스는 매번 풀하며, `never`와 `build`는 그대로 둡니다.

Compose 자체에는 로그인이 전달되지 않습니다. Homeport가 실행을 위해 만드는 어떤 파일에도, 명령의 어떤 환경 변수에도 로그인이 들어 있지 않습니다. 이 컴퓨터에서 직접 한 `docker login`은 이 풀에 적용되지 않으므로, 대신 **설정 → 레지스트리** 항목에서 로그인을 추가하세요. 레지스트리가 이미지를 거부하면 Compose가 실행되기 전에 배포가 멈추며, 메시지에 로그인을 추가하거나 확인하라는 안내가 표시됩니다.

## 관리형 스택 만들기

<Steps>

1. **스택** 페이지를 열고 **새 스택** 버튼을 누릅니다. **compose 파일 작성** 항목이 선택되어 있습니다.

2. [템플릿](#템플릿으로-시작)을 고르거나, 처음부터 시작하려면 **비어 있음** 항목을 고릅니다.

3. **이름** 값을 입력합니다. 소문자, 숫자, `-`, `_`를 사용하며 문자나 숫자로 시작합니다. 템플릿이 이름을 제안합니다. 이 이름은 Compose 프로젝트 이름이 되며 나중에 바꿀 수 없습니다.

4. 편집기에서 compose 파일을 조정합니다.

5. **환경** 항목에 `.env` 파일처럼 한 줄에 `KEY=value` 하나씩 변수를 입력합니다. Compose가 파일의 `${KEY}`를 이 값으로 치환합니다. 템플릿이 비워 둔 비밀번호를 채우세요.

6. **저장 후 배포** 버튼을 누릅니다. 나중에 배포하려면 **저장** 버튼을 누르세요.

</Steps>

### 템플릿으로 시작

새 스택 페이지는 템플릿 갤러리로 열립니다. 각 템플릿은 모범 사례를 따르는 compose 파일과 환경입니다. 이미지 태그는 버전으로 고정되어 있고, 데이터는 이름 있는 볼륨에 있으며, 비밀 정보는 파일이 아닌 환경에 있습니다. **Tab** 키로 카드 사이를 이동하고 **Enter** 키로 하나를 고르세요. **다른 템플릿 선택** 버튼을 누르면 돌아갑니다.

| 템플릿                    | 실행하는 것                                                           |
| ------------------------- | --------------------------------------------------------------------- |
| **정적 사이트**           | `HTTP_PORT` 포트에서 이름 있는 볼륨의 파일을 제공하는 nginx.          |
| **PostgreSQL 및 Adminer** | PostgreSQL과, 이를 탐색하기 위해 `ADMINER_PORT`에서 실행되는 Adminer. |
| **MariaDB**               | 데이터베이스 하나와 앱 사용자가 있는 MariaDB.                         |
| **Redis**                 | 비밀번호가 설정되고 데이터를 디스크에 저장하는 Redis.                 |
| **리버스 프록시(Caddy)**  | 자동 HTTPS와 함께 `SITE_ADDRESS`를 `UPSTREAM`으로 전달하는 Caddy.     |
| **Uptime Kuma**           | `HTTP_PORT`에서 사이트와 서비스를 지켜보는 Uptime Kuma.               |
| **WordPress**             | 자체 MariaDB 데이터베이스가 있는 WordPress.                           |
| **비어 있음**             | 직접 채울 `services:` 섹션.                                           |

비밀번호는 비워져 있으며, 무엇을 넣어야 하는지 설명하는 주석이 붙어 있습니다. 배포하기 전에 채우세요. 외부 스택을 관리형으로 전환할 때는 갤러리를 건너뛰고 빈 편집기가 열립니다.

### 입력하는 동안 검사

Homeport는 입력하는 동안 정의를 검사하고 편집기 아래에 문제를 나열합니다. 적용되는 규칙은 스택의 종류에 따라 다릅니다.

**오류** 항목은 배포를 막습니다.

- YAML을 구문 분석할 수 없거나 `services:`가 없습니다. 모든 종류에 적용됩니다.
- 서비스에 `image:`도 `build:`도 없습니다. 모든 종류에 적용됩니다.
- 서비스가 `build:`를 사용합니다. **관리형 스택** 유형에만 적용됩니다. 빌드할 폴더가 없으므로, 레지스트리에 푸시한 이미지를 사용하거나 대신 [폴더를 링크](#링크된-스택-만들기)하세요.

**경고** 항목은 **관리형 스택** 유형에만 적용되며, 배포는 할 수 있지만 Compose가 호스트가 아닌 이 컴퓨터에서 읽기 때문에 예상대로 동작하지 않을 가능성이 높은 부분을 가리킵니다. 링크된 스택은 폴더가 있으므로 문제없습니다.

- `./data:/data`처럼 상대 경로를 사용하는 바인드 마운트. 호스트의 절대 경로나 이름 있는 볼륨을 사용하세요.
- `env_file:`, 또는 `file:`에서 읽는 `configs`와 `secrets`. 대신 스택의 환경에 변수를 넣으세요.

### 환경

환경은 암호화되어 저장되고 디스크에 기록되지 않은 채 Compose에 바로 전달되므로, 비밀번호와 토큰을 두기에 알맞은 곳입니다. compose 파일 자체는 일반 텍스트로 저장되므로 비밀 정보를 넣지 마세요.

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
```

```ini
DB_PASSWORD=correct-horse-battery-staple
```

빈 줄, `# comments`, `export` 접두사를 쓸 수 있습니다. 값은 따옴표로 감쌀 수 있으며, 큰따옴표 안에서 `\n`은 줄 바꿈입니다.

<Aside>
  환경을 저장하려면 [OS 키체인](/docs/requirements/#선택-사항-os-키체인)이 필요합니다. 키체인이
  없으면 이 필드가 비활성화되며 스택은 환경 없이 배포됩니다.
</Aside>

## 여러 compose 파일

스택은 `docker compose -f compose.yaml -f compose.prod.yaml`이 병합하는 방식처럼, 순서대로 병합되는 여러 compose 파일로 구성할 수 있습니다. 기본 파일이 있고, 그다음 키를 추가하거나 변경하는 재정의 파일이 옵니다. 예를 들어 프로덕션용 `ports:`나 개발용 디버그 서비스입니다.

**관리형 스택** 유형에서는 편집기 위에 파일마다 탭이 하나씩 표시됩니다. **파일 추가** 버튼으로 파일을 추가하고(Homeport가 `compose.override.yaml`, `compose.prod.yaml` 등을 제안합니다), **파일 이름** 필드에서 이름을 바꾸고, 화살표로 순서를 앞뒤로 옮기거나 삭제합니다. 첫 번째 파일은 기본 파일이며 삭제할 수 없습니다. 이름은 `.yaml` 또는 `.yml`로 끝나야 합니다.

파일이 하나이면 Homeport는 이전처럼 표준 입력으로 Compose에 보냅니다. 여러 개이면 명령이 실행되는 동안 사용자만 열 수 있는 비공개 폴더에 파일을 쓰고, 끝나면 삭제합니다. 환경은 그곳에 절대 기록되지 않으며, 여전히 변수로 Compose에 전달됩니다.

**링크된 스택** 유형은 **정의** 탭의 사이드 패널에 파일을 순서대로 나열합니다. **파일 추가…** 버튼은 스택의 폴더에서 다른 compose 파일(예: 기본 재정의 파일 대신 `compose.prod.yaml`)을 고르며, 화살표와 **✕** 버튼으로 순서를 바꾸고 삭제합니다. 파일을 바꾸면 편집기가 다시 불러와지므로, 먼저 편집 내용을 저장하거나 다시 불러오세요.

검사는 병합된 파일을 기준으로 하므로, 기본 파일에서 정의되고 재정의 파일에서 `ports:`가 지정된 서비스는 하나의 서비스로 검사됩니다.

## 프로필

compose 파일은 디버그 도구, 워커, 로컬 데이터베이스 같은 선택적 서비스를 `profiles:` 뒤에 두는 경우가 많습니다.

```yaml
services:
  app:
    image: ghcr.io/org/app:1.4
  adminer:
    image: adminer:4.8.1
    profiles: [debug]
```

프로필이 없는 서비스는 항상 실행됩니다. 프로필이 있는 서비스는 스택이 그 프로필을 켤 때만 실행됩니다. 관리형, 링크된, 동기화 스택의 파일에 프로필이 선언되어 있으면, **정의** 탭에 프로필마다 체크박스가 있는 **프로필** 섹션이 표시됩니다. 프로필을 켜고 **저장 후 다시 배포** 버튼을 누르세요. 다음 배포 때 적용하려면 **프로필 저장** 버튼을 누르세요.

프로필을 끄고 다시 배포하면 그 서비스의 컨테이너가 삭제됩니다. Compose 자체는 컨테이너를 실행 중인 채로 두므로, Homeport가 `docker compose up` 전에 삭제합니다. **내리기** 기능은 켜져 있든 아니든 파일이 선언하는 모든 프로필의 서비스를 삭제합니다.

스택의 프로필만 적용됩니다. 셸의 `COMPOSE_PROFILES` 변수, 관리형 스택의 환경이나 링크된 스택의 `.env`에 있는 이 변수는 Homeport가 배포하는 내용을 바꾸지 않습니다. compose 레이블로 발견된 링크된 스택은 `--profile`로 시작했더라도 켜진 프로필 없이 시작합니다. **정의** 탭에서 프로필을 켜세요. 켜 둔 프로필이 파일에서 사라지면 Homeport가 그 사실을 알리고 다음 저장 때 프로필을 끕니다.

## 배포와 다시 배포

**배포** 버튼(스택이 실행 중이면 **다시 배포** 버튼)은 `docker compose up --detach --remove-orphans`를 실행합니다. 창에 Compose의 출력이 실시간으로 표시되며, 마지막에 **✓ 완료** 또는 실패한 종료 코드가 표시됩니다.

<Aside type="caution">
  Compose가 실행되는 동안 출력 창을 닫으면 Compose가 중지되므로, 배포가 중간에 멈출 수 있습니다.
  마무리하려면 다시 배포하세요.
</Aside>

관리형 스택을 변경하려면 스택을 열고 **정의** 탭을 편집한 다음 **저장 후 다시 배포** 버튼을 누르세요. Compose는 변경된 서비스만 다시 만들고, 파일에서 지운 서비스는 삭제합니다.

### 다시 배포 전에 변경 사항 검토

다시 배포가 실행되기 전에(**다시 배포**, **다시 빌드 후 배포**, 또는 실행 중인 스택의 **저장 후 다시 배포**), Homeport는 **변경 사항 검토** 화면을 보여 줍니다. 지난번에 배포된 정의([기록](#배포-기록과-롤백)에서 가장 최근에 성공한 항목)와 이제 배포할 정의를 비교합니다.

- 각 compose 파일은 변경된 줄을 인라인으로 보여 줍니다. 삭제된 줄이 그 줄을 대체한 줄 위에 표시됩니다. 변경되지 않은 파일은 접혀 있으며, 선택하면 펼쳐집니다. 추가되거나, 삭제되거나, 다른 순서로 병합된 파일은 이름이 표시됩니다.
- 환경 변수는 이름만 **추가됨**, **삭제됨**, **변경됨** 표시와 함께 보여 주며(변경된 비밀번호는 어느 값도 보여 주지 않고 **변경됨** 표시만 붙습니다), 변경되지 않은 나머지 변수의 수도 표시합니다.
- 프로필을 켜거나 끈 것도 표시됩니다.

실행을 계속하려면 **배포** 버튼을, 아무것도 바꾸지 않고 편집기로 돌아가려면 **뒤로** 버튼을 누르세요. 변경된 것이 없으면 검토 화면에 그 사실이 표시되고 **그래도 다시 배포** 버튼이 제공됩니다. Homeport가 현재 배포된 내용을 모르면(Homeport가 기록을 보관하기 전에 배포되었거나 Homeport 밖에서 배포된 경우) 검토 화면에 그 사실이 표시되고 배포될 정의가 표시됩니다. 첫 배포, 롤백, [업데이트](#스택-업데이트)는 검토를 건너뜁니다.

비교 대상은 정의뿐이며, 호스트에 있는 컨테이너의 실시간 구성은 비교하지 않습니다.

## 배포 기록과 롤백

Homeport에서 관리형, 링크된, 동기화 스택을 배포할 때마다(**배포**, **다시 배포**, **다시 빌드 후 배포**, **저장 후 다시 배포**, [동기화](/docs/guides/synced-stacks/#동기화)) 사용한 compose 파일, 환경, 프로필, 실행 시각, 결과가 기록됩니다. 동기화 스택의 기록에는 커밋과, 자동 배포로 시작되었는지도 표시됩니다. 스택 페이지의 **기록** 탭은 최근 20개를 최신순으로 나열합니다. 결과는 **성공**, 종료 코드와 함께 **실패**, 또는 끝나기 전에 창을 닫은 실행이면 **완료되지 않음** 상태로 표시됩니다. **현재 배포됨** 표시는 가장 최근에 성공한 배포에 붙습니다.

배포를 선택하면 그 compose 파일을 읽기 전용으로 볼 수 있습니다. 배포의 환경은 스택 자체의 환경처럼 암호화되어 저장되며, 탭에는 변수 이름만 표시됩니다. 키체인이 없어도 목록은 작동하며, 환경이 있는 배포에는 열 수 없다는 안내만 표시됩니다.

**관리형** 스택의 잘못된 변경을 되돌리려면, 제대로 작동했던 배포를 선택하고 **롤백** 버튼을 누르세요. Homeport가 현재 compose 파일, 환경, 프로필을 그 배포의 것으로 되돌린 다음 다시 배포하므로, 다음 기록 항목은 롤백 자체가 됩니다.

<Aside type="caution" title="롤백이 복원하는 것">
  정의만 복원합니다. 이미지는 정의에 적힌 태그로, 그 태그의 현재 상태대로 다시 풀됩니다. 그사이
  `app:1.4`가 다시 푸시되었다면 새 `app:1.4`를 받게 됩니다. 볼륨과 그 데이터는 그대로 남습니다.
</Aside>

**링크된** 스택의 기록은 읽기 전용입니다. 폴더가 원본이므로, 버전 관리 등을 사용해 그곳에서 이전 파일을 복원한 다음 다시 배포하세요. 스택을 잊으면 기록도 삭제됩니다.

## 스택의 페이지

- **서비스** 탭은 각 서비스를 컨테이너, 이미지, 상태와 함께 나열합니다. 컨테이너를 선택하면 해당 컨테이너가 열립니다.
- **로그** 탭은 모든 컨테이너의 로그를 함께 보여 주며, 각 줄에는 서비스 이름이 붙습니다.

<DocScreenshot
  name="stack-logs"
  alt="모든 서비스의 출력이 섞여 레이블과 함께 표시된 스택의 로그 탭."
/>

- **정의** 탭에는 관리형 또는 링크된 스택이라면 편집기가, 동기화 스택이라면 원본과 읽기 전용 파일이 있으며, 외부 스택이라면 스택이 어디에서 왔는지 설명합니다.
- **기록** 탭은 관리형, 링크된, 동기화 스택의 배포를 나열합니다. [배포 기록](#배포-기록과-롤백)을 참고하세요.

## 스택 업데이트

스택 상태 옆의 **업데이트 있음** 표시는 스택의 서비스 중 하나가, 태그가 레지스트리에서 더 새로운 버전을 가리키는 이미지를 실행하고 있다는 뜻입니다. 포인터를 올리면 어떤 서비스인지 볼 수 있습니다. 스택 페이지의 **서비스** 탭은 해당 서비스의 이름을 표시하고 오래된 이미지마다 표시를 붙입니다. 스택 페이지 위쪽의 **새 이미지 확인** 버튼은 레지스트리에 다시 묻습니다. 이 확인은 컨테이너 페이지가 사용하는 것과 같으므로([새 이미지](/docs/guides/containers/#새-이미지) 참고), 컨테이너 페이지 바로 뒤에 스택 페이지를 열면 레지스트리에 더 묻지 않습니다. 다이제스트로 고정된 이미지(`app@sha256:…`)에는 업데이트가 없으며, `build:`가 있는 서비스는 확인하지 않습니다.

관리형, 링크된, 동기화 스택을 업데이트하려면 **업데이트** 버튼을 누르세요. 두 단계를 한 창에서 실행합니다. 저장된 로그인으로 모든 서비스의 이미지를 풀한 다음, 풀한 이미지로 `docker compose up`을 실행하므로 이미지가 바뀐 서비스만 새 컨테이너를 받습니다. 시작하기 전에 창에 어떤 이미지가 더 새로운지 표시되며, 정의가 바뀌지 않으므로 [검토 단계](#다시-배포-전에-변경-사항-검토)는 없습니다. 풀이 실패하면 업데이트가 거기서 멈춥니다. 실행 중인 컨테이너는 그대로 남으며, 오류에 이유와 해결 방법이 표시됩니다.

외부 스택에도 **업데이트 있음** 표시가 나타나지만 **업데이트** 버튼은 비활성화됩니다. Homeport에 다시 배포할 compose 파일이 없으므로 먼저 [관리형으로 전환](#외부-스택을-관리형으로-전환)하세요. 링크된 스택에서 `build:`가 있는 서비스는 풀하지 않으므로, 그런 서비스에는 **다시 빌드 후 배포** 기능을 사용하세요.

## 스택 작업

| 작업                     | 스택                   | 하는 일                                                                                                                              |
| ------------------------ | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **배포** / **다시 배포** | 관리형, 링크됨, 동기화 | 스택의 정의로 `docker compose up`을 실행합니다.                                                                                      |
| **동기화**               | 동기화                 | 브랜치나 태그를 가져와 무엇이 바뀌었는지 보여 주고, 새 커밋을 배포합니다. [동기화](/docs/guides/synced-stacks/#동기화)를 참고하세요. |
| **다시 빌드 후 배포**    | 링크됨, 동기화         | `docker compose up --build`: 먼저 `build:`가 있는 모든 서비스를 다시 빌드합니다.                                                     |
| **시작** / **중지**      | 모두                   | 중지된 컨테이너를 시작하거나, 실행 중인 컨테이너를 중지합니다.                                                                       |
| **다시 시작**            | 모두                   | 모든 컨테이너를 다시 시작합니다.                                                                                                     |
| **이미지 풀**            | 관리형, 링크됨, 동기화 | 다시 배포하기 전에 새 이미지를 가져오도록, 저장된 로그인으로 모든 서비스의 이미지를 풀합니다.                                        |
| **내리기**               | 관리형, 링크됨, 동기화 | `docker compose down`: 컨테이너와 네트워크를 삭제하고, 볼륨과 정의는 유지합니다.                                                     |
| **볼륨과 함께 내리기**   | 관리형, 링크됨, 동기화 | 스택의 볼륨과 **그 데이터까지** 삭제합니다.                                                                                          |
| **컨테이너 삭제**        | 외부                   | 컨테이너와 네트워크를 삭제합니다. 볼륨은 유지됩니다.                                                                                 |
| **관리형으로 전환**      | 외부                   | Homeport에 compose 파일을 제공해 관리형 스택으로 만듭니다.                                                                           |

관리형 스택의 **정의** 탭에 있는 **정의 잊기** 버튼은 Homeport에서 compose 파일과 환경을 삭제하지만 컨테이너는 실행 중인 채로 두며, 스택은 외부 스택이 됩니다. 링크된 스택의 **정의** 탭에 있는 **잊기** 버튼은 Homeport가 기록한 폴더 정보를 지우며, 폴더, 그 파일, 컨테이너는 그대로 둡니다.

## 외부 스택을 관리형으로 전환

<Steps>

1. 외부 스택을 열고 **관리형으로 전환** 버튼을 누릅니다.

2. 스택을 배포할 때 사용한 compose 파일을 붙여 넣습니다. 이름은 채워진 채 잠겨 있습니다.

3. 사용한 환경 변수가 있으면 추가합니다.

4. 실행 중인 컨테이너를 건드리지 않고 넘겨받으려면 **저장** 버튼을, 지금 다시 배포하려면 **저장 후 배포** 버튼을 누릅니다.

</Steps>

<Aside type="caution" title="같은 정의 사용">
  다른 파일로 다시 배포하면 그 파일에 맞게 컨테이너가 다시 생성되고, 더 이상 나열되지 않은 서비스는
  삭제됩니다. 처음 배포한 머신에서 상대 경로였던 경로가 이제는 다르게 해석될 수 있습니다.
</Aside>

외부 스택과 같은 이름으로 새 스택을 만들어도 관리형으로 전환됩니다.
