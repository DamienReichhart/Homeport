## The list

Containers that belong to a [Stack](/docs/guides/stacks/) are grouped under it; standalone containers follow. A Stack's row shows how many of its containers are running and their combined CPU and memory. Select it to fold the group, or **Open stack** to go to the Stack.

| Column      | Shows                                                                                                 |
| ----------- | ----------------------------------------------------------------------------------------------------- |
| **Name**    | A status dot, the name (the service name inside a Stack) and the short ID.                            |
| **Image**   | The image it was created from, with a ⬆ mark when a [newer image](#newer-images) is published.        |
| **Status**  | As the Engine reports it, e.g. _Up 3 hours (healthy)_, with a health badge if there's a health check. |
| **Ports**   | Up to three ports, published ones first. A published port is a link that opens it in your browser.    |
| **CPU**     | Live, as a percentage of one CPU: `200%` means two CPUs fully used.                                   |
| **Memory**  | Live, not counting page cache the kernel can reclaim.                                                 |
| **Created** | How long ago.                                                                                         |

CPU and memory update every two seconds. **Search containers** matches names, images, Stacks, services and ID prefixes; **Only running** hides the rest.

Select a container to open it.

### Newer images

A ⬆ next to the image means its registry now has a different image under the tag the container was created from: `nginx:1.27` moved on since it was pulled, or a newer one was pulled but the container wasn't recreated. Hover it to see which. To update, pull the image and recreate the container — for a Stack, **Pull images** then **Redeploy**.

Homeport asks the registry through the Host's Engine, which compares digests without pulling anything, using your stored [registry logins](/docs/guides/settings/#registries) for private images. Answers are kept for 6 hours, so opening the list again asks nothing; **Check for newer images**, at the top of the page, asks every registry again now. Images built locally, pulled by digest (`app@sha256:…`) or whose registry can't be reached show nothing rather than a false alarm. The container's page shows the same mark next to its image.

### Actions

The button at the end of each row starts or stops the container. The **⋮** menu has the rest: **Logs**, **Open terminal**, **Restart**, **Pause** or **Resume**, **Kill**, **Rename**, [**Edit**](#editing-a-container), [**Duplicate**](#duplicating-a-container), [**Commit to image…**](#committing-a-container) and **Remove**.

Tick containers to act on several at once with **Start**, **Stop**, **Restart** or **Remove**. The tick box on a Stack's row selects all of its containers.

<Aside type="caution" title="What Remove deletes">
  Removing a container deletes it, its writable layer and its anonymous volumes. Named volumes are
  kept. A running container is stopped immediately, without waiting for it to shut down cleanly.
</Aside>

**Kill** sends `SIGKILL` straight away, so the process gets no chance to clean up. **Stop** gives it the container's stop timeout first.

## A container's page

The header shows the image and status, with **Start** or **Stop**, **Restart**, **Pause** or **Resume**, and **Remove**; its **⋮** menu has **Rename**, **Edit**, **Duplicate** and **Commit to image…**. The tabs below hold everything else.

<Aside>
  Leaving a tab closes what it was doing: terminals close when you leave **Exec**, charts start
  again when you return to **Stats**, and **Logs** reload.
</Aside>

### Logs

<DocScreenshot
  name="container-logs"
  alt="A container's Logs tab, with history, timestamps, stream filters and search."
/>

Logs stream as the container writes them. The toolbar controls what you see:

- **History** — how many past lines to load: the last 100, 1 000 (the default) or 10 000, or everything.
- **Since** — any time, or the last 5 minutes, hour or 24 hours.
- **Timestamps** — show the Engine's timestamp before each line.
- **stdout** and **stderr** — show or hide either stream.
- **Follow** — keep scrolling to the newest line. New lines keep arriving even when it's off.
- **Find in logs** — highlights matches. Press <kbd>Enter</kbd> for the next match and <kbd>Shift</kbd>+<kbd>Enter</kbd> for the previous one.
- **Clear** empties the view; **Download logs** saves what you've loaded as a text file, up to the last 100 000 lines.

When the container stops, the log ends with _— end of logs —_.

### Inspect

**Details** summarises the container in cards: state and exit code, command, restart policy, health checks, environment, mounts, ports, networks and labels. **Raw JSON** shows the Engine's full inspect document.

<Aside type="caution">
  Environment variables are shown in clear text, as the Engine stores them. Keep this in mind before
  sharing your screen.
</Aside>

### Exec

<DocScreenshot name="container-terminal" alt="An interactive terminal in a container's Exec tab." />

An interactive terminal in the running container. The first one, **Shell**, opens on its own and runs `bash`, or `sh` when the image has no bash.

**New terminal** opens another with your own **Command**, **User** and **Directory**, for example `psql -U postgres` as user `postgres`. Several can be open at once; close one with its **×**. Terminals resize with the window.

Images without a shell — `scratch` or distroless images — can't open the default terminal.

### Files

Browse the container's file system from `/`. Select a folder to open it, or use the path at the top to go back up.

- **Download** a file, or a whole folder as a `.tar` archive, with the button at the end of its row.
- **Upload here** copies files from your computer into the folder you're in, replacing files with the same name.

Listing files runs `find` and `stat` inside the container, so minimal images without them can't be browsed. Transfers are held in memory, so very large files are better copied with `docker cp`.

### Stats

Live charts of the last five minutes, updated every second: **CPU**, **Memory** (against the container's limit), **Network** received and sent, and **Disk I/O** read and written, with the number of processes.

### Processes

The processes running in the container, as `ps aux` shows them, refreshed every five seconds.

## Running a container

**Run container** on the Containers page — or the ▶ button next to an image — opens **Run a container**:

| Field                                  | Notes                                                                                                                                                       |
| -------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Image**                              | Required. Suggests the Host's images. Pulled first if the Host doesn't have it, with the stored [registry login](/docs/guides/settings/#registries).        |
| **Name**                               | Optional; the Engine generates one if empty.                                                                                                                |
| **Command**                            | Replaces the image's default command (not its entrypoint). Quote arguments as in a shell.                                                                   |
| **Ports**                              | **Host port** → **Container port**, `tcp` or `udp`. Leave the host port empty to let the Engine pick a free one. Ports are published on every interface.    |
| **Volumes**                            | A volume name or an absolute `/host/path`, mounted at an absolute container path, optionally **read-only**. A name that doesn't exist yet creates a volume. |
| **Environment**                        | One `KEY=value` per line. Blank lines and lines starting with `#` are ignored.                                                                              |
| **Network**                            | **Default (bridge)**, or any network on the Host.                                                                                                           |
| **Restart**                            | **Never**, **On failure**, **Unless stopped** or **Always**.                                                                                                |
| **Remove the container when it exits** | Like `docker run --rm`. A container removed on exit can't also restart.                                                                                     |

Choose **Run**: Homeport creates and starts the container, then opens its logs.

If the container can't start — a port already in use, say — Homeport removes it again and the dialog stays open with the reason, so you can fix the field and run it under the same name.

### Advanced options

**Advanced options**, below the restart policy, opens the settings people reach for less often, one tab each. A value Homeport can't read is explained under its field, and **Run** waits until it's fixed. Everything set here shows in the container's **Inspect** tab.

**Resources**

| Field                     | Notes                                                                                           |
| ------------------------- | ----------------------------------------------------------------------------------------------- |
| **CPU limit**             | How many CPUs it may use, like `0.5` or `2` (`--cpus`). Empty uses every CPU.                   |
| **CPU shares**            | Its weight against other containers when CPUs are busy; `1024` is the default (`--cpu-shares`). |
| **Memory limit**          | Like `512m` or `2g` (`--memory`). Sizes count in powers of 1024, as Docker does. At least `6m`. |
| **Memory reservation**    | A soft limit the Engine enforces only when the Host runs short of memory; at most the limit.    |
| **Memory and swap limit** | Memory plus swap, so at least the memory limit; `-1` for unlimited swap. Needs a memory limit.  |

**Labels** — one `key=value` per line, as reverse proxies such as Traefik and Caddy and backup tools read them. Keys starting with `com.docker.compose.` are refused: they belong to Docker Compose, and Homeport would show the container as part of a Stack.

**Security** — capabilities to add and to drop, typed one at a time with suggestions (`NET_ADMIN` and `CAP_NET_ADMIN` are the same; `ALL` means every one), and **Privileged**.

<Aside type="danger" title="Privileged mode">
  A privileged container can use every device and capability of the Host, and anything running in it
  can take the Host over. Add only the capabilities and devices it needs instead, when you can.
</Aside>

**Devices** — Host devices to pass in, like `/dev/dri` for hardware transcoding or `/dev/ttyUSB0` for a Zigbee stick, with the path inside the container (the same when empty) and permissions: some of `r`ead, `w`rite and `m`ake device files. **GPUs** asks for all of them, a number of them, or chosen ones by index or UUID, like `docker run --gpus`.

<Aside type="note" title="GPUs need the vendor's toolkit">
  The Host must have its GPU vendor's container toolkit installed — for NVIDIA, the [NVIDIA
  Container
  Toolkit](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/install-guide.html)
  — and the Docker Engine restarted after. Homeport doesn't install it. Without it, the run fails
  with _This host can't give containers a GPU._
</Aside>

**Healthcheck** — keep **the image's own**, define **a command** run with `/bin/sh -c` (exit code 0 means healthy), or turn the image's off with **None**. **Interval**, **Timeout** and **Start period** take durations like `30s` or `1m30s`; **Retries** is how many failures in a row make it unhealthy. The status then shows in the list as _healthy_ or _unhealthy_.

**Network identity** — the container's **Hostname** and **Domain name**, its **DNS servers** (addresses) and **search domains**, and **Extra hosts**: `name:address` lines added to its `/etc/hosts`, for names your network's DNS doesn't know. `host-gateway` stands for the Host's own address, so `host.docker.internal:host-gateway` reaches services on the Host.

**Logging** — the **Log driver**: `json-file`, `local`, `journald`, `syslog`, `none`, or any other the Engine has; empty uses the Engine's default. **Driver options** are `key=value` lines; for `json-file`, `max-size=10m` and `max-file=3` keep logs from filling a small Host's disk. With `journald`, `syslog` or `none`, the **Logs** tab may stay empty.

## Duplicating a container

**Duplicate** opens the Run dialog filled in from the container — image, command, environment, ports, volumes, network, restart policy and every advanced option — under the name `<name>-copy`. Change what you need and choose **Run**.

Settings the dialog doesn't show, such as ulimits, sysctls, security options, tmpfs mounts and the other networks the container is on (with their aliases), are copied as they are. Only what you only got from the image is left out of the form, so a newer tag of the image brings its own defaults.

The copy doesn't take what identifies the original: it gets its own hostname (unless you set one), MAC address and fresh anonymous volumes, and a container from a [Stack](/docs/guides/stacks/) loses its Stack labels and service aliases, so the copy doesn't join the Stack or answer to its service name. If the original publishes a fixed host port, the dialog says so: two containers can't both use it while they run, so change it or leave it empty to let the Engine pick one.

## Editing a container

The Docker Engine can't change most settings of an existing container, so **Edit** recreates it: it opens the Run dialog filled in from the container, and **Apply** replaces it with one created from your changes. The name stays (use **Rename** to change it).

Before anything happens, Homeport lists what the new container won't have:

- **Anonymous volumes** — the new container starts with empty ones. The old ones aren't deleted: they're kept as unused volumes you can still open or [clean up](/docs/guides/volumes-networks/).
- **Files changed inside the container** since it was created, such as installed packages or edited configuration. To keep them, [commit the container to an image](#committing-a-container) first — the confirmation has a button for it — and edit the container to use that image.
- **Downtime** — a running container stops while the two are swapped, usually for a few seconds.
- **A Stack's next deploy** — for a container in a Stack, the Stack's next deploy recreates it from its compose file, without your edit. Change the compose file to make it last.

What's kept: the name, the networks with their aliases, named volumes and bind mounts, and every setting the dialog doesn't show. The container runs afterwards if it was running.

<Aside type="note" title="If something goes wrong">
  Homeport creates the new container before touching the original, and removes the original only
  once the new one is running. If any step fails — the new port is taken, say — the new container is
  removed and the original put back as it was, running if it was running, and the dialog shows why.
  In the rare case putting it back fails too, the message names where the original is, such as
  `web-old-1a2b3c4d`, so you can rename it back and start it.
</Aside>

## Committing a container

**Commit to image…** saves the container's files as they are now — including everything changed inside it since it was created — and its settings as a new image on the Host, like `docker commit`.

| Field                                    | Notes                                                                                                                                                                             |
| ---------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Image name**                           | `repo:tag`, starting as the container's name and today's date, such as `web:2026-11-04`. If an image already has that name, the dialog says so: the name moves to the new image.  |
| **Message**                              | Shown in the image's history (**Inspect** → **Layers**).                                                                                                                          |
| **Author**                               | Optional.                                                                                                                                                                         |
| **Changes**                              | Dockerfile instructions applied to the new image, one per line: `CMD`, `ENTRYPOINT`, `ENV`, `EXPOSE`, `LABEL`, `ONBUILD`, `USER`, `VOLUME` or `WORKDIR`, such as `ENV MODE=prod`. |
| **Pause the container while committing** | On by default: its processes are frozen for the few seconds it takes, so files being written are consistent. The container carries on afterwards.                                 |

The new image shows up on the [Images page](/docs/guides/images/) straight away. Volumes, named or anonymous, aren't part of it: back them up separately. To make an image you can rebuild, prefer [building one from a Dockerfile](/docs/guides/images/#building-an-image).
