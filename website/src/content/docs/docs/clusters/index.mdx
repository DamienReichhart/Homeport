A **Cluster** is a Kubernetes cluster, or a [Nomad cluster](/docs/clusters/nomad/), Homeport connects to through its API. This section is about Kubernetes ones; Nomad ones have [their own page](/docs/clusters/nomad/). A Kubernetes Cluster is one Homeport reaches through its API server. You add one from a context of a kubeconfig — the file `kubectl` already uses — so there are no new credentials to create, and Homeport installs nothing on the cluster: it only talks to the Kubernetes API your kubeconfig already reaches, with the rights its credentials have.

Clusters are listed in the sidebar under your Hosts, each with its status. Selecting one opens its pages beneath it, after its [Overview](/docs/guides/overview/#a-clusters-overview), in three groups: its resources (**Workloads**, **Pods**, **Network**, **Configuration**), the cluster itself (**Nodes**, **Events**) and tools (**API resources**, **RBAC**, **Apply YAML**, **Helm**, **Port forwards**). Selecting a Host shows the Host pages again. On the [Board](/docs/guides/overview/#board), each Cluster has a tile next to your Hosts'.

## What you can do

You can see what runs on a Cluster and whether it's healthy, live, and do the everyday `kubectl` tasks from Homeport:

1. [Add a cluster](#adding-a-cluster) from your kubeconfig, or a [local one](/docs/clusters/local/) in one click; cloud ones sign in through their [exec plugin](/docs/clusters/exec-plugins/).
2. Browse its [workloads and Pods](/docs/clusters/workloads/), its [Services, Ingresses, ConfigMaps and Secrets](/docs/clusters/networking-config/), its [Nodes and Events](/docs/clusters/nodes-events/), and [any other API resource](/docs/clusters/api-resources/), custom resources included.
3. Read a Pod's or a workload's [logs and open a terminal](/docs/clusters/logs-exec/) in a container, and [forward a port](/docs/clusters/port-forward/) to this computer.
4. [Scale, restart and delete](/docs/clusters/actions/), and [apply or edit YAML](/docs/clusters/yaml/) with a preview of what changes.
5. List, install, upgrade, roll back and uninstall [Helm releases](/docs/clusters/helm/), and manage helm's chart repositories, with the `helm` CLI on this computer.

Every change goes to the Kubernetes API with your credentials' rights, and anything that removes or replaces something asks first, naming the cluster.

## Adding a Cluster

<DocScreenshot
  name="add-cluster"
  alt="The Add a cluster page: local clusters found on this machine at the top, then the contexts of ~/.kube/config with their API server, how they sign in, and which are already added."
/>

Choose **Add host or cluster**, under the list of Hosts in the sidebar, then **Add cluster…**, or **Add a cluster** on the Clusters page. [Local clusters](/docs/clusters/local/) — Docker Desktop, OrbStack, Rancher Desktop, kind, k3d, minikube — are offered at the top, one click each. Each context you pick becomes a Cluster, named after the context; you can rename it before or after importing.

- **From this machine's kubeconfig** reads the files listed in `KUBECONFIG`, merged as `kubectl` merges them, or `~/.kube/config` when `KUBECONFIG` isn't set. The current context is picked for you.
- **Paste a kubeconfig** reads text you paste, in memory only: it's never saved as a file. Files it refers to (`certificate-authority: /…`) must be full paths; the simplest is to paste one with everything inlined:

  ```bash
  kubectl config view --raw --flatten --minify
  ```

Each context shows its API server, its namespace, and how its user signs in — **Client certificate**, **Token**, **OpenID Connect**, or **Exec plugin (aws)** for a cloud one — so you can tell a local cluster from a production one before importing it. Tick the ones you want; each gets a name field, filled with the context's name. Long ARNs such as `arn:aws:eks:…:cluster/prod` are worth renaming to something short like `eks-prod`: the name is what the sidebar, the Board and the Overview show.

A context that is already a Cluster can't be imported twice: Homeport offers **Refresh it** instead. A context that can't be used says why, for example a user whose `auth-provider` is `gcp` or `azure`, which Kubernetes removed (switch it to `gke-gcloud-auth-plugin` or `kubelogin`, as `kubectl` now requires).

Users can sign in with a client certificate, a token (or `tokenFile`), a user name and password, an OpenID Connect `auth-provider` (its ID token is refreshed in memory), or an exec plugin.

## What is stored where

| Kept in clear in Homeport's database                                     | Kept only encrypted (like SSH keys)                                         |
| ------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| the name, the API server's URL, the context's namespace                  | the CA certificate, client certificate and key                              |
| how its user signs in (certificate, token…), the context it was imported | the token or password, the OIDC tokens, the exec plugin's arguments and env |

Files the kubeconfig refers to are read once, when you import, and stored encrypted with the rest. Your kubeconfig is never changed. Without an OS keychain, Homeport can't store credentials and won't add a Cluster; see [Security and your data](/docs/reference/security/).

## Refreshing from the kubeconfig

kind, k3d and minikube give a cluster new certificates each time they recreate it, and cloud credentials get renewed. **Refresh from kubeconfig** on a Cluster's page reads its context again — from this machine's kubeconfig, or from a kubeconfig you paste again for one that was pasted — keeps its name, and reconnects.

## Managing Clusters

- **Manage clusters**, the settings icon beside **Clusters** in the sidebar, lists every Cluster with its status, API server and how it signs in.
- On a Cluster's page, the **Enabled** switch disconnects it without forgetting it, **Reconnect** tries again at once, and **Rename…** (in its **More actions** menu) changes its name in Homeport only.
- **Remove cluster** (at the foot of a Cluster's page) forgets the Cluster and its stored credentials. Nothing changes on the cluster or in your kubeconfig.

Cluster names must be unique, ignoring case.

## Statuses

| Status               | Meaning                                                                                            |
| -------------------- | -------------------------------------------------------------------------------------------------- |
| **Connected**        | The API server answers; its Kubernetes version shows next to it.                                   |
| **Connecting**       | Homeport is reaching it.                                                                           |
| **Unreachable**      | The API server didn't answer. Homeport tries again on its own, waiting 1 s and up to a minute.     |
| **Access refused**   | The API server refused the credentials. Check that `kubectl` works with the context, then refresh. |
| **Misconfigured**    | Something only you can fix, such as a certificate that doesn't match. Homeport waits until you do. |
| **Credentials lost** | The OS keychain's key that protects them is gone; refresh the Cluster from its kubeconfig.         |
| **Disabled**         | Turned off with the **Enabled** switch.                                                            |

A connected Cluster is checked every 15 seconds, so one that goes away shows it and reconnects on its own when it's back, like a Host.
