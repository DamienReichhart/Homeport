**क्लस्टर** एक Kubernetes क्लस्टर, या एक [Nomad क्लस्टर](/docs/clusters/nomad/), है जिससे Homeport उसके API के ज़रिए कनेक्ट होता है। यह सेक्शन Kubernetes क्लस्टर के बारे में है; Nomad क्लस्टर का [अपना पेज](/docs/clusters/nomad/) है। Kubernetes क्लस्टर वह है जिस तक Homeport उसके API सर्वर के ज़रिए पहुँचता है। आप इसे किसी kubeconfig के context से जोड़ते हैं — वही फ़ाइल जिसे `kubectl` पहले से इस्तेमाल करता है — इसलिए कोई नया क्रेडेंशियल बनाने की ज़रूरत नहीं होती, और Homeport क्लस्टर पर कुछ भी इंस्टॉल नहीं करता: यह सिर्फ़ उसी Kubernetes API से बात करता है जिस तक आपका kubeconfig पहले से पहुँचता है, उतने ही अधिकारों के साथ जितने उसके क्रेडेंशियल के पास हैं।

क्लस्टर साइडबार के ऊपर स्विचर में आपके होस्ट के बगल में होते हैं। किसी एक को चुनने पर उससे जुड़े पेज दिखते हैं — **वर्कलोड**, **Pods**, **नेटवर्क**, **कॉन्फ़िगरेशन**, **Nodes**, **इवेंट**, **API रिसोर्स**, **YAML लागू करें**, **Helm** और **पोर्ट फ़ॉरवर्ड** — और [अवलोकन](/docs/guides/overview/#चुना-गया-क्लस्टर) पर उसका सारांश; कोई होस्ट चुनने पर होस्ट के पेज फिर से दिखते हैं।

## आप क्या कर सकते हैं

आप देख सकते हैं कि किसी क्लस्टर पर क्या चल रहा है और वह स्वस्थ है या नहीं, लाइव, और रोज़ के `kubectl` काम Homeport से कर सकते हैं:

1. अपने kubeconfig से [क्लस्टर जोड़ें](#क्लस्टर-जोड़ना), या एक क्लिक में कोई [लोकल क्लस्टर](/docs/clusters/local/); क्लाउड क्लस्टर अपने [exec प्लगइन](/docs/clusters/exec-plugins/) से साइन इन करते हैं।
2. इसके [वर्कलोड और Pods](/docs/clusters/workloads/), इसके [Services, Ingresses, ConfigMaps और Secrets](/docs/clusters/networking-config/), इसके [Nodes और Events](/docs/clusters/nodes-events/), और [कोई भी दूसरा API रिसोर्स](/docs/clusters/api-resources/) देखें, कस्टम रिसोर्स भी।
3. किसी Pod या वर्कलोड के [लॉग पढ़ें और किसी कंटेनर में टर्मिनल खोलें](/docs/clusters/logs-exec/), और इस कंप्यूटर पर [कोई पोर्ट फ़ॉरवर्ड करें](/docs/clusters/port-forward/)।
4. [स्केल करें, फिर से शुरू करें और हटाएँ](/docs/clusters/actions/), और जो बदलेगा उसके पूर्वावलोकन के साथ [YAML लागू या संपादित करें](/docs/clusters/yaml/)।
5. इस कंप्यूटर के `helm` CLI से [Helm रिलीज़](/docs/clusters/helm/) की सूची देखें, उन्हें इंस्टॉल, अपग्रेड, वापस और अनइंस्टॉल करें, और helm की चार्ट रिपॉज़िटरी प्रबंधित करें।

हर बदलाव आपके क्रेडेंशियल के अधिकारों के साथ Kubernetes API को जाता है, और जो कुछ भी किसी चीज़ को हटाता या बदलता है, वह क्लस्टर का नाम लेकर पहले पूछता है।

## क्लस्टर जोड़ना

<DocScreenshot

/>

स्विचर में **क्लस्टर जोड़ें…** चुनें, या क्लस्टर पेज पर **क्लस्टर जोड़ें**। [लोकल क्लस्टर](/docs/clusters/local/) — Docker Desktop, OrbStack, Rancher Desktop, kind, k3d, minikube — ऊपर दिए जाते हैं, हर एक बस एक क्लिक में। आपका चुना हर context एक क्लस्टर बन जाता है, जिसका नाम context के नाम पर होता है; इम्पोर्ट करने से पहले या बाद में आप उसका नाम बदल सकते हैं।

- **इस मशीन के kubeconfig से** `KUBECONFIG` में दी गई फ़ाइलें पढ़ता है, उन्हें वैसे ही मिलाकर जैसे `kubectl` मिलाता है, या `KUBECONFIG` सेट न होने पर `~/.kube/config`। मौजूदा context आपके लिए चुन लिया जाता है।
- **kubeconfig पेस्ट करें** आपका पेस्ट किया गया टेक्स्ट सिर्फ़ मेमोरी में पढ़ता है: इसे कभी फ़ाइल के रूप में सहेजा नहीं जाता। जिन फ़ाइलों का यह संदर्भ देता है (`certificate-authority: /…`), उनके पूरे पाथ होने चाहिए; सबसे आसान है ऐसा kubeconfig पेस्ट करना जिसमें सब कुछ inline हो:

  ```bash
  kubectl config view --raw --flatten --minify
  ```

हर context अपना API सर्वर, अपना namespace, और उसका यूज़र कैसे साइन इन करता है, यह दिखाता है — **क्लाइंट प्रमाणपत्र**, **टोकन**, **OpenID Connect**, या किसी क्लाउड क्लस्टर के लिए **Exec प्लगइन (aws)** — ताकि इम्पोर्ट करने से पहले आप लोकल क्लस्टर और प्रोडक्शन क्लस्टर में फ़र्क़ कर सकें। जो चाहिए उन पर टिक करें; हर एक को context के नाम से भरा एक नाम फ़ील्ड मिलता है। `arn:aws:eks:…:cluster/prod` जैसे लंबे ARN का नाम बदलकर `eks-prod` जैसा कुछ छोटा रखना अच्छा है: स्विचर और अवलोकन यही नाम दिखाते हैं।

जो context पहले से क्लस्टर है, उसे दो बार इम्पोर्ट नहीं किया जा सकता: Homeport इसकी बजाय **इसे रीफ़्रेश करें** देता है। जिस context का इस्तेमाल नहीं हो सकता, वह कारण बताता है, जैसे ऐसा यूज़र जिसका `auth-provider` `gcp` या `azure` है, जिसे Kubernetes ने हटा दिया है (इसे `gke-gcloud-auth-plugin` या `kubelogin` पर बदलें, जैसा `kubectl` अब माँगता है)।

यूज़र क्लाइंट प्रमाणपत्र, टोकन (या `tokenFile`), यूज़र नाम और पासवर्ड, OpenID Connect `auth-provider` (इसका ID टोकन मेमोरी में रीफ़्रेश होता है), या exec प्लगइन से साइन इन कर सकते हैं।

## क्या कहाँ सहेजा जाता है

| Homeport के डेटाबेस में सादे रूप में रखा जाता है                               | सिर्फ़ एन्क्रिप्ट करके रखा जाता है (SSH कुंजियों की तरह)      |
| ------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| नाम, API सर्वर का URL, context का namespace                                    | CA प्रमाणपत्र, क्लाइंट प्रमाणपत्र और कुंजी                    |
| इसका यूज़र कैसे साइन इन करता है (प्रमाणपत्र, टोकन…), इम्पोर्ट किया गया context | टोकन या पासवर्ड, OIDC टोकन, exec प्लगइन के आर्ग्युमेंट और env |

kubeconfig जिन फ़ाइलों का संदर्भ देता है, वे इम्पोर्ट करते समय एक बार पढ़ी जाती हैं और बाकी के साथ एन्क्रिप्ट करके सहेजी जाती हैं। आपका kubeconfig कभी नहीं बदला जाता। OS keychain के बिना, Homeport क्रेडेंशियल सहेज नहीं सकता और क्लस्टर नहीं जोड़ेगा; [सुरक्षा और आपका डेटा](/docs/reference/security/) देखें।

## kubeconfig से रीफ़्रेश करना

kind, k3d और minikube हर बार क्लस्टर दोबारा बनाने पर उसे नए प्रमाणपत्र देते हैं, और क्लाउड क्रेडेंशियल नवीनीकृत होते रहते हैं। क्लस्टर के पेज पर **kubeconfig से रीफ़्रेश करें** उसका context फिर से पढ़ता है — इस मशीन के kubeconfig से, या पेस्ट किए गए क्लस्टर के लिए आपके दोबारा पेस्ट किए गए kubeconfig से — उसका नाम बनाए रखता है, और फिर से कनेक्ट होता है।

## क्लस्टर प्रबंधित करना

- स्विचर में **क्लस्टर प्रबंधित करें** हर क्लस्टर को उसकी स्थिति, API सर्वर और साइन इन के तरीके के साथ सूचीबद्ध करता है।
- क्लस्टर के पेज पर, **सक्षम** स्विच उसे भूले बिना डिस्कनेक्ट करता है, **फिर से कनेक्ट करें** तुरंत फिर से कोशिश करता है, और **नाम बदलें** उसका नाम सिर्फ़ Homeport में बदलता है।
- **क्लस्टर हटाएँ** क्लस्टर और उसके सहेजे गए क्रेडेंशियल भूल जाता है। क्लस्टर पर या आपके kubeconfig में कुछ नहीं बदलता।

क्लस्टर के नाम अनोखे होने चाहिए, बड़े-छोटे अक्षरों को अनदेखा करके।

## स्थितियाँ

| स्थिति                     | मतलब                                                                                                                           |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| **कनेक्ट है**              | API सर्वर जवाब देता है; इसका Kubernetes संस्करण इसके बगल में दिखता है।                                                         |
| **कनेक्ट हो रहा है**       | Homeport इस तक पहुँच रहा है।                                                                                                   |
| **पहुँच से बाहर**          | API सर्वर ने जवाब नहीं दिया। Homeport अपने आप फिर से कोशिश करता है, 1 s से लेकर एक मिनट तक रुककर।                              |
| **पहुँच अस्वीकृत**         | API सर्वर ने क्रेडेंशियल अस्वीकार कर दिए। जाँचें कि `kubectl` इस context के साथ काम करता है, फिर रीफ़्रेश करें।                |
| **गलत कॉन्फ़िगर किया गया** | कुछ ऐसा जिसे सिर्फ़ आप ठीक कर सकते हैं, जैसे मेल न खाने वाला प्रमाणपत्र। Homeport तब तक प्रतीक्षा करता है जब तक आप ऐसा न करें। |
| **क्रेडेंशियल खो गए**      | उन्हें सुरक्षित रखने वाली OS keychain की कुंजी नहीं रही; क्लस्टर को उसके kubeconfig से रीफ़्रेश करें।                          |
| **अक्षम**                  | **सक्षम** स्विच से बंद किया गया।                                                                                               |

कनेक्ट हुए क्लस्टर की हर 15 सेकंड में जाँच होती है, इसलिए जो क्लस्टर चला जाता है वह यह दिखाता है और वापस आने पर अपने आप फिर से कनेक्ट हो जाता है, होस्ट की तरह।
