**堆栈**是在主机上运行的 Compose 项目。无论堆栈是如何部署的，Homeport 都会通过 Compose 添加在其容器上的标签，找到所选主机上的每个堆栈。

## 托管、关联、同步和外部堆栈

每个堆栈都属于以下四种类型之一：

| 类型     | compose 文件所在位置                  | 编辑 | 部署 | 构建 | 启动、停止、删除 |
| -------- | ------------------------------------- | ---- | ---- | ---- | ---------------- |
| **托管** | 在 Homeport 中，其环境变量加密保存    | ✓    | ✓    | —    | ✓                |
| **关联** | 在**本机**上的项目文件夹中            | ✓    | ✓    | ✓    | ✓                |
| **同步** | 在 Homeport 克隆并跟踪的 git 仓库中   | git  | ✓    | ✓    | ✓                |
| **外部** | Homeport 看不到的地方：以其他方式部署 | —    | —    | —    | ✓                |

- **托管堆栈**是由 Homeport 保存其 compose 文件和环境变量的堆栈。你可以从 Homeport 编辑、部署和下线它。
- **关联堆栈**是 compose 文件位于本机上某个文件夹中的堆栈，你在那里继续编辑这些文件。Homeport 会记住该文件夹的位置，直接处理其中的文件，并从那里进行部署。请参阅[关联堆栈](#关联堆栈)。
- **同步堆栈**是 compose 文件来自 git 仓库的堆栈。Homeport 会获取其分支或标签，显示更改内容，并部署新提交；它通过 git 编辑，从不在 Homeport 中编辑。请参阅[同步堆栈](/docs/guides/synced-stacks/)。
- **外部堆栈**是以其他方式部署的堆栈：在服务器上运行 `docker compose up`、CI 作业、其他工具，或从另一台计算机上的文件夹部署。Homeport 可以启动、停止、重启和删除它的容器，但没有可用于重新部署它的 compose 文件。你可以[接管](#接管外部堆栈)它，使其成为托管堆栈。

每个堆栈会显示以下状态之一：

| 状态         | 含义                             |
| ------------ | -------------------------------- |
| **运行中**   | 它的所有容器都在运行。           |
| **部分运行** | 部分容器在运行。                 |
| **已停止**   | 没有容器在运行。                 |
| **未部署**   | 尚无容器的托管、关联或同步堆栈。 |

托管、关联和同步堆栈属于一个主机或一个 Swarm。要在两个主机上运行同一个 compose 文件，请在每个主机上分别创建一个堆栈。

<Aside>
  部署到 [Swarm](/docs/guides/swarm/) 的堆栈，无论是从终端还是从 Homeport 部署的，都列在 Swarm
  自己页面的**堆栈**下，而不是这里。要部署一个，请在**新建堆栈**的**部署到**下选择该
  Swarm。请参阅[将堆栈部署到 Swarm](/docs/guides/swarm/#将堆栈部署到-swarm)。
</Aside>

## 关联堆栈

**关联堆栈**将其 compose 文件保存在本机上的项目文件夹中，你在自己的编辑器中编辑它们，并用版本控制管理它们。Homeport 从不复制这些文件：它会记住该文件夹以及它按顺序使用的 compose 文件，并在原处读取它们。文件夹中的 `.env` 留在文件夹中。

关联堆栈也可以部署到 Swarm，其 `configs: file:` 和 `secrets: file:` 从该文件夹读取；请参阅 [Swarm 上的关联堆栈和同步堆栈](/docs/guides/swarm/#swarm-上的关联堆栈和同步堆栈)。

### 创建关联堆栈

尚未在主机上运行的项目文件夹可以从 Homeport 关联：

<Steps>

1. 打开**堆栈**，选择**新建堆栈**，然后选择**使用本机上的文件夹**。

2. 选择**选择文件夹…**，然后选择包含该 compose 项目的文件夹。

3. Homeport 会按顺序列出 Compose 在该文件夹中会使用的 compose 文件：`compose.yaml`、`compose.yml`、`docker-compose.yml` 和 `docker-compose.yaml` 中第一个存在的文件，然后是其覆盖文件（`compose.override.yaml` 之类，如果有）。不包含任何这些文件的文件夹无法关联，Homeport 会说明这一点。

4. 检查**名称**。它来自文件顶层的 `name:`，或者按照 Compose 的写法由文件夹名称生成（`My App` 变为 `myapp`）。

5. 选择**保存并部署**，或选择**保存**以稍后部署。

</Steps>

如果已有同名堆栈作为外部堆栈在主机上运行，创建关联堆栈会接管它，与[接管](#接管外部堆栈)相同：重新部署会重新创建其容器，使之与文件夹中的文件一致。要使用其他名称或其他顺序的文件，请参阅[多个 compose 文件](#多个-compose-文件)。

### 如何找到关联堆栈

当你在某个文件夹中运行 `docker compose up` 时，Compose 会为每个容器标记该文件夹及其 compose 文件，即使 `DOCKER_HOST` 指向远程主机也是如此。当 Homeport 列出主机的堆栈时，满足以下条件的正在运行的堆栈会显示为**关联**：

1. 这两个标签都存在，并且它们指定的文件夹和每个 compose 文件都存在于本机上，并且
2. 这些文件定义了正在运行的服务：每个正在运行的服务都在这些文件中，并且文件中在 profile 之外定义的每个服务都有一个容器。

第二条规则可以防止某个碰巧在本机上也存在的路径关联到错误的文件，例如在服务器本身的 `/srv/app` 中启动的堆栈，而本机上恰好也有 `/srv/app`。使用 `include:` 或 `extends:` 的文件不会被追踪，因此这样的堆栈目前仍为外部堆栈。查找关联堆栈不需要 Compose CLI。

文件夹会显示在列表中堆栈名称的下方以及堆栈页面上。

### 编辑关联堆栈

关联堆栈的**定义**标签页会把每个 compose 文件显示在单独的标签中，内容从文件夹读取，文件夹路径显示在上方。编辑它们并选择**保存**：Homeport 会将每个更改过的文件写回原处，因此你自己的编辑器和版本控制都能看到更改。文件会一步替换并保留其权限，因此任何时候都不会读到写了一半的文件。

编辑器下方的检查遵循关联堆栈的规则：`build:`、`env_file:` 和相对路径都没有问题，因为文件夹就在那里。没有环境变量编辑器：Compose 运行时会读取文件夹中的 `.env`，Homeport 既不显示也不更改它。

#### 在 Homeport 之外被更改

Homeport 每次读取或写入文件时都会记录它们。当文件不一致时（你在另一个编辑器中编辑了它们，或拉取了新版本），标签页会显示**在 Homeport 之外被更改**。它会在标签页打开时以及每次你回到 Homeport 窗口时进行检查。选择**重新加载**可查看文件的当前内容；未保存的编辑会被丢弃。

如果你保存的文件在打开后已在磁盘上被更改，Homeport 会拒绝保存：**自你打开以来，compose.yaml 已在 Homeport 之外被更改。**重新加载以查看另一处更改，或选择**覆盖**用你的版本替换它。

如果文件夹已不存在，或某个文件无法读取，标签页会说明是哪个文件以及该怎么做，而不显示编辑器。

### 部署和构建关联堆栈

**部署**、**重新部署**、**拉取镜像**和**下线**同样适用于关联堆栈。Homeport 会在堆栈的文件夹中运行 `docker compose`，将 `--project-directory` 设为该文件夹，并按顺序为每个 compose 文件传入一个 `--file`，与你自己在那里运行它相同；对于 SSH 和 TLS 主机，仍然通过 Homeport 自己的连接进行。因此 `build:`、`env_file:`、`./relative` 路径以及文件夹中的 `.env` 都能正常工作。

带有 `build:` 的服务在还没有镜像时会被构建。要在更改其代码后重新构建，请在堆栈的 **⋮** 菜单中选择**重新构建并部署**（`up --build`）。构建在**主机**的引擎上运行，构建上下文从本机发送。带有 `build:` 的服务从不会被拉取；它们的基础镜像由构建本身使用你自己的 `docker login` 拉取。

**定义**标签页中的**保存并重新部署**会写入你编辑的文件，然后进行部署。

<Aside type="caution" title="远程主机上的相对路径">
  `./data:/data` 这样的绑定挂载会解析为**本机**上的文件夹，例如
  `/home/me/site/data`。在远程主机上，该路径可能不存在，此时引擎会在那里创建一个空文件夹。当你将关联堆栈部署到不是本机的主机时，输出会以针对每个此类挂载的警告开头。对于必须保存在主机上的数据，请使用命名卷或主机上的绝对路径。
</Aside>

如果文件夹已不存在，部署会停止并显示**文件夹 … 已不在本机上。**没有 Compose CLI 时，关联堆栈仍然可以启动、停止和删除。

### 当文件夹被移动或消失时

如果关联堆栈的 compose 文件已不在原处（文件夹被移动、重命名或删除），该堆栈会显示为**外部**，并带有 ⚠ **它的 compose 文件已不在本机上。**Homeport 和主机上都不会删除任何内容：把文件放回原处，下次刷新时它就会重新成为关联堆栈。要停止关联它，请打开其**定义**标签页并选择**忘记**；这只会删除 Homeport 对该文件夹的记录，绝不会删除文件夹或容器。

从另一台计算机上的文件夹启动的堆栈在本机上是外部堆栈，因为它的标签指向本机上不存在的路径。

## 部署需要什么

Homeport 使用**本机**上的 `docker compose` 命令部署托管、关联和同步堆栈，并将其指向主机。请安装带有 Compose 插件的 Docker CLI，或独立的 `docker-compose` v2；**设置 → 本机**会显示 Homeport 是否找到了它。

对于托管堆栈，该命令运行时 compose 文件通过标准输入传入，堆栈的环境变量作为变量传入，工作文件夹为空，因此不会向磁盘写入任何内容。对于关联堆栈，它在堆栈的文件夹中运行并使用其 compose 文件，就像你在那里运行一样。对于 SSH 和 TLS 主机，Homeport 会通过自己与主机的连接转发该命令，因此 Compose 永远看不到你的密钥。

没有 Compose CLI 时，你仍然可以启动、停止和删除堆栈；只有**部署**、**拉取镜像**和**下线**需要它。

### 私有镜像

在运行 `docker compose up` 之前，Homeport 会通过自己与主机的连接，使用为每个镜像所在镜像仓库保存的[镜像仓库登录](/docs/guides/settings/#镜像仓库)，拉取主机上尚未有的镜像，因此私有镜像可以部署到任何主机，而无需在本机上运行 `docker login`。部署输出会显示每次拉取及其使用的登录（**正在拉取 ghcr.io/org/app:1，在 ghcr.io 上以 alice 身份**，或**匿名**），但从不显示密码。带有 `pull_policy: always` 的服务每次都会被拉取；`never` 和 `build` 则不受影响。

Compose 本身从不会获得登录信息：Homeport 为运行创建的任何文件、命令的任何环境变量中都不包含登录信息。你自己在本机上的 `docker login` 不适用于这些拉取；请改为在**设置 → 镜像仓库**中添加登录。如果镜像仓库拒绝某个镜像，部署会在 Compose 运行前停止，消息会提示添加或检查登录。

## 创建托管堆栈

<Steps>

1. 打开**堆栈**并选择**新建堆栈**。**编写 compose 文件**已被选中。

2. 选择一个[模板](#从模板开始)，或选择**空白**从头开始。

3. 输入**名称**：小写字母、数字、`-` 和 `_`，以字母或数字开头。模板会建议一个名称。它会成为 Compose 项目名称，之后无法更改。

4. 在编辑器中调整 compose 文件。

5. 在**环境变量**中填写变量，每行一个 `KEY=value`，与 `.env` 文件相同。Compose 会用它们替换文件中的 `${KEY}`。请填写模板留空的密码。

6. 选择**保存并部署**，或选择**保存**以稍后部署。

</Steps>

### 从模板开始

新建堆栈页面会打开一个模板库。每个模板都是一个遵循良好实践的 compose 文件和环境变量：镜像标签固定到某个版本，数据保存在命名卷中，机密放在环境变量中而不是文件中。使用 **Tab** 在卡片之间移动，使用 **Enter** 选择一个；**选择其他模板**可返回。

| 模板                      | 运行的内容                                                       |
| ------------------------- | ---------------------------------------------------------------- |
| **静态网站**              | 由 nginx 提供命名卷中的文件，端口为 `HTTP_PORT`。                |
| **PostgreSQL 和 Adminer** | PostgreSQL，以及在 `ADMINER_PORT` 上用于浏览它的 Adminer。       |
| **MariaDB**               | 带有一个数据库和一个应用用户的 MariaDB。                         |
| **Redis**                 | 带密码的 Redis，会将数据保存到磁盘。                             |
| **反向代理 (Caddy)**      | 将 `SITE_ADDRESS` 转发到 `UPSTREAM` 的 Caddy，并自动启用 HTTPS。 |
| **Uptime Kuma**           | 用于监视网站和服务的 Uptime Kuma，端口为 `HTTP_PORT`。           |
| **WordPress**             | 带有独立 MariaDB 数据库的 WordPress。                            |
| **空白**                  | 一个由你自己填写的 `services:` 部分。                            |

密码留空，并附有注释说明应填写什么：请在部署前填写它们。接管外部堆栈时会跳过模板库，直接打开一个空的编辑器。

### 输入时检查

Homeport 会在你输入时检查定义，并在编辑器下方列出问题。适用哪些规则取决于堆栈的类型。

**错误**会阻止部署：

- YAML 无法解析，或没有 `services:`：所有类型。
- 某个服务既没有 `image:` 也没有 `build:`：所有类型。
- 某个服务使用了 `build:`：仅限**托管堆栈**。没有可用于构建的文件夹，因此请使用你已推送到镜像仓库的镜像，或改为[关联该文件夹](#创建关联堆栈)。

**警告**仅针对**托管堆栈**，允许你部署，但会指出那些可能不会按你预期工作的内容，因为 Compose 是从本机而不是从主机读取它们的。关联堆栈的文件夹就在本机上，因此对它来说这些都没有问题：

- 使用相对路径的绑定挂载，例如 `./data:/data`。请使用主机上的绝对路径或命名卷。
- `env_file:`，或从 `file:` 读取的 `configs` 和 `secrets`。请改为将变量放入堆栈的环境变量中。

### 环境变量

环境变量加密保存并直接传给 Compose，从不写入磁盘，是存放密码和令牌的合适位置。compose 文件本身以明文保存，因此不要在其中放入机密：

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
```

```ini
DB_PASSWORD=correct-horse-battery-staple
```

允许空行、`# comments` 和 `export` 前缀。值可以加引号；在双引号中，`\n` 表示换行。

<Aside>
  保存环境变量需要[系统钥匙串](/docs/requirements/#可选系统钥匙串)。没有钥匙串时，该字段会被禁用，堆栈部署时不带环境变量。
</Aside>

## 多个 compose 文件

一个堆栈可以由多个按顺序合并的 compose 文件组成，与 `docker compose -f compose.yaml -f compose.prod.yaml` 的合并方式相同：一个基础文件，然后是添加或更改键的覆盖文件，例如用于生产环境的 `ports:`，或用于开发环境的调试服务。

**托管堆栈**会在编辑器上方为每个文件显示一个标签。选择**添加文件**可添加一个文件（Homeport 会建议 `compose.override.yaml`、`compose.prod.yaml` 等），在**文件名**中重命名它，用箭头将其前移或后移，或移除它。第一个文件是基础文件，无法移除。名称以 `.yaml` 或 `.yml` 结尾。

只有一个文件时，Homeport 会像以前一样通过标准输入将其发送给 Compose。有多个文件时，它会在命令运行期间将它们写入一个只有你的用户才能打开的私有文件夹，之后再删除。环境变量从不写入那里：它仍然作为变量传给 Compose。

**关联堆栈**会在**定义**标签页的侧边面板中按顺序列出它们的文件。**添加文件…**会从堆栈的文件夹中选择另一个 compose 文件（例如用 `compose.prod.yaml` 代替默认的覆盖文件），箭头和 **✕** 用于重新排序和移除它们。请先保存或重新加载你的编辑：更改文件会重新加载编辑器。

检查针对的是合并后的文件，因此在基础文件中定义、在覆盖文件中添加了 `ports:` 的服务会作为一个服务进行检查。

## Profile

compose 文件经常把可选的服务（调试工具、工作进程、本地数据库）放在 `profiles:` 之后：

```yaml
services:
  app:
    image: ghcr.io/org/app:1.4
  adminer:
    image: adminer:4.8.1
    profiles: [debug]
```

没有 profile 的服务总会运行。属于某个 profile 的服务只有在堆栈开启该 profile 时才会运行。当托管、关联或同步堆栈的文件声明了 profile 时，其**定义**标签页会显示 **Profile**，每个 profile 都有一个复选框。开启一个并选择**保存并重新部署**，或选择**保存 profile** 以在下次部署时应用。

关闭某个 profile 并重新部署会删除其服务的容器：Homeport 会在 `docker compose up` 之前删除它们，因为 Compose 本身会让它们继续运行。**下线**会删除文件中声明的所有 profile 的服务，无论是否开启。

只有堆栈自己的 profile 才算数。你的 shell 中、托管堆栈的环境变量中或关联堆栈的 `.env` 中的 `COMPOSE_PROFILES` 变量不会改变 Homeport 部署的内容。通过 compose 标签找到的关联堆栈一开始不会开启任何 profile，即使它是用 `--profile` 启动的：请在其**定义**标签页中开启它们。如果你开启的某个 profile 从文件中消失了，Homeport 会说明这一点，并在下次保存时将其关闭。

## 部署和重新部署

**部署**（堆栈运行后则为**重新部署**）会运行 `docker compose up --detach --remove-orphans`。一个窗口会实时显示 Compose 的输出，并以 **✓ 完成**或失败时的退出码结束。

<Aside type="caution">
  在 Compose 运行时关闭输出窗口会停止它，这可能使部署只完成一半。请重新部署以完成它。
</Aside>

要更改托管堆栈，请打开它，编辑其**定义**，然后选择**保存并重新部署**。Compose 只会重新创建发生更改的服务，并删除你从文件中删掉的服务。

### 重新部署前审阅更改

在重新部署运行之前（**重新部署**、**重新构建并部署**，或对正在运行的堆栈选择**保存并重新部署**），Homeport 会显示**审阅更改**：上次部署的定义（其[历史](#部署历史和回滚)中最新的成功条目）与即将部署的定义的对比。

- 每个 compose 文件会内联显示其更改的行：被删除的行显示在替换它们的行上方。未更改的文件会折叠起来；选择它即可展开。会列出添加、删除或以不同顺序合并的文件的名称。
- 环境变量只显示其名称，并标记为**已添加**、**已删除**或**已更改**（更改过的密码显示为**已更改**，不会显示任何一个值），以及还有多少个未更改。
- 开启或关闭 profile 也会显示出来。

选择**部署**继续运行，或选择**返回**回到编辑器而不做任何更改。没有任何更改时，审阅界面会说明这一点，并提供**仍然重新部署**。当 Homeport 不知道当前部署的是什么时（堆栈是在 Homeport 保存历史之前部署的，或是在 Homeport 之外部署的），审阅界面会说明这一点，并显示将要部署的定义。首次部署、回滚和[更新](#更新堆栈)会跳过审阅。

对比只针对定义，而不是容器在主机上的实时配置。

## 部署历史和回滚

从 Homeport 对托管、关联或同步堆栈的每次部署（**部署**、**重新部署**、**重新构建并部署**、**保存并重新部署**、[同步](/docs/guides/synced-stacks/#同步)）都会被记录下来，包括所用的 compose 文件、环境变量和 profile、运行时间以及结束方式；同步堆栈的记录还会显示其提交，以及是否由自动部署启动。堆栈页面的**历史**标签页列出最近 20 次部署，最新的排在前面：**成功**、带退出码的**失败**，或者对于在结束前关闭了窗口的运行显示**未完成**。**当前部署**标记最新一次成功的部署。

选择一次部署即可以只读方式查看其 compose 文件。它的环境变量与堆栈自己的环境变量一样加密保存，标签页只显示其变量的名称。没有钥匙串时，列表仍然可用；带有环境变量的部署只会说明无法打开。

要撤销对**托管**堆栈的错误更改，请选择那次正常工作的部署，然后选择**回滚**。Homeport 会用它的 compose 文件、环境变量和 profile 替换当前的内容，然后重新部署，因此下一条历史记录就是这次回滚本身。

<Aside type="caution" title="回滚会恢复什么">
  只恢复定义。镜像会按其指定的标签重新拉取，以这些标签现在的状态为准：如果 `app:1.4`
  之后被重新推送过，你得到的是新的 `app:1.4`。卷及其数据保持原样。
</Aside>

**关联**堆栈的历史是只读的：它的文件夹就是它的来源，因此请在那里恢复较早的文件（例如使用你的版本控制），然后重新部署。忘记堆栈也会删除其历史。

## 堆栈的页面

- **服务**列出每个服务及其容器、镜像和状态。选择一个容器即可打开它。
- **日志**会同时显示所有容器的日志，每一行都标有其服务。

- **定义**包含托管堆栈或关联堆栈的编辑器、同步堆栈的来源和只读文件，或说明外部堆栈的来历。
- **历史**针对托管、关联和同步堆栈，列出它们的部署。请参阅[部署历史](#部署历史和回滚)。

## 更新堆栈

堆栈状态旁的**有可用更新**表示它的某个服务运行的镜像，其标签在镜像仓库中指向一个更新的版本；将鼠标悬停在上面可查看是哪些服务。在堆栈的页面上，**服务**会列出它们，并标记每个过时的镜像。“堆栈”页面顶部的**检查新版镜像**会重新询问镜像仓库。该检查与“容器”页面使用的检查相同（请参阅[新版镜像](/docs/guides/containers/#新版镜像)），因此在打开“容器”之后紧接着打开“堆栈”不会再次询问镜像仓库。按摘要固定的镜像（`app@sha256:…`）永远不会有更新，带有 `build:` 的服务也不会被检查。

要更新托管、关联或同步堆栈，请选择**更新**。它会在一个窗口中运行两个步骤：先使用已保存的登录拉取每个服务的镜像，然后使用拉取的镜像运行 `docker compose up`，因此只有镜像发生变化的服务才会获得新容器。窗口会在开始前说明哪些镜像有新版本，并且没有[审阅步骤](#重新部署前审阅更改)，因为定义没有变化。如果拉取失败，更新会在那里停止：正在运行的容器保持原样，错误信息会说明原因以及该怎么做。

外部堆栈也会显示**有可用更新**，但它的**更新**被禁用：Homeport 没有可用于重新部署它的 compose 文件，因此请先[接管](#接管外部堆栈)它。关联堆栈中带有 `build:` 的服务从不会被拉取；对它们请使用**重新构建并部署**。

## 堆栈操作

| 操作                    | 堆栈             | 作用                                                                                                |
| ----------------------- | ---------------- | --------------------------------------------------------------------------------------------------- |
| **部署** / **重新部署** | 托管、关联、同步 | 使用堆栈的定义运行 `docker compose up`。                                                            |
| **同步**                | 同步             | 获取其分支或标签，显示有哪些变化，并部署新的提交。参见[同步](/docs/guides/synced-stacks/#syncing)。 |
| **重新构建并部署**      | 关联、同步       | `docker compose up --build`：先重新构建每个带有 `build:` 的服务。                                   |
| **启动** / **停止**     | 任意             | 启动已停止的容器，或停止正在运行的容器。                                                            |
| **重启**                | 任意             | 重启每个容器。                                                                                      |
| **拉取镜像**            | 托管、关联、同步 | 使用已保存的登录拉取每个服务的镜像，以便在重新部署前获取新版本。                                    |
| **下线**                | 托管、关联、同步 | `docker compose down`：删除容器和网络，保留卷和定义。                                               |
| **下线并删除卷**        | 托管、关联、同步 | 同时删除堆栈的卷**及其数据**。                                                                      |
| **删除容器**            | 外部             | 删除其容器和网络。卷会保留。                                                                        |
| **接管**                | 外部             | 向 Homeport 提供 compose 文件，使其成为托管堆栈。                                                   |

托管堆栈**定义**标签页中的**忘记定义**会从 Homeport 中删除 compose 文件和环境变量，但让容器继续运行；该堆栈将成为外部堆栈。关联堆栈**定义**标签页中的**忘记**会删除 Homeport 对该文件夹的记录；文件夹、其中的文件以及容器都不受影响。

## 接管外部堆栈

<Steps>

1. 打开该外部堆栈并选择**接管**。

2. 粘贴部署它时所用的 compose 文件。名称已填好并锁定。

3. 如果它使用了环境变量，请添加这些变量。

4. 选择**保存**以接管它而不影响正在运行的容器，或选择**保存并部署**立即重新部署它。

</Steps>

<Aside type="caution" title="使用相同的定义">
  使用不同的文件重新部署会重新创建容器以与之匹配，并删除不再列出的服务。在最初部署它的机器上为相对路径的路径，现在可能会解析到不同的位置。
</Aside>

使用与某个外部堆栈相同的名称创建新堆栈，也会接管它。
