**Swarm** 是一个 Docker Swarm 集群。Homeport 不会单独添加 Swarm：它通过属于该 Swarm 的[主机](/docs/hosts/)找到它，并通过任意一个已连接的管理节点来管理它。任何节点上都不会安装任何东西，本机上也不会保存关于 Swarm 的任何信息。

本页从找到或创建 Swarm 开始，依次介绍它的节点、服务和任务、机密和配置，以及它的[堆栈](/docs/guides/stacks/)：从终端部署的堆栈，以及由 Homeport 部署的堆栈。

## 找到 Swarm

将 Swarm 的一个管理节点添加为主机，方式与添加其他主机相同（请参阅[主机和连接](/docs/hosts/)）。一旦连接，Swarm 就会出现在：

- 侧边栏中的 **Swarm** 下，
- **概览**中，作为单独的一张卡片，
- 它的每个主机上，显示为该 Swarm 的**管理节点**或**工作节点**。

Docker 给每个 Swarm 起的名称都相同，因此 Homeport 以其首个管理节点主机来称呼它，即“_主机名_ **的 Swarm**”，并附上其 swarm ID 的开头部分。添加同一 Swarm 的第二个管理节点不会让它显示两次：Swarm 是按 swarm ID 区分的。只有当某个 Swarm 的一个管理节点也是主机时，工作节点主机才会显示它所属的 Swarm。

Swarm 的页面以**摘要**开始：它的管理节点主机和工作节点主机、有多少个节点和管理节点、上面运行着多少个服务，以及它的 swarm ID。它的标签页（**节点**、**服务**、**任务**、**堆栈**、**机密**和**配置**）将在下文介绍。

### 没有已连接的管理节点时

Homeport 对 Swarm 执行的所有操作都通过其已连接的管理节点之一进行，哪个先响应就用哪个。没有已连接的管理节点时，Swarm 的页面会显示**此 Swarm 没有已连接的管理节点**，并列出它最后看到的管理节点主机：重新连接其中一个，或将另一个管理节点添加为主机。

## 创建 Swarm

Homeport 可以用已连接的主机建立 Swarm，无需在终端之间复制任何内容。每个已连接主机的页面上都有一张 **Swarm** 卡片：

1. 在将要管理 Swarm 的主机上，选择**初始化 Swarm**。当 Homeport 通过 IP 访问主机时，会填入**通告地址**（其他节点访问它的地址）；留空则由引擎选择，这在机器只有一个地址时可行。该主机成为 Swarm 的第一个管理节点，Swarm 会出现在侧边栏中。
2. 在其他每个主机上，选择**加入 Swarm**，选择该 Swarm，然后以**工作节点**或**管理节点**身份加入。Homeport 会从已连接的管理节点获取加入令牌。要加入 Homeport 不知道的 Swarm，请选择**其他 Swarm（使用令牌）**，然后粘贴 `docker swarm join-token worker` 给出的令牌和管理节点地址。
3. 对于不是 Homeport 主机的机器，Swarm 的**摘要**中有**加入命令**：显示它们，然后复制工作节点或管理节点的 `docker swarm join` 命令。令牌在你显示它们时获取，从不保存或记录到日志。

主机卡片上的**退出 Swarm**会让它退出：工作节点的任务会转移到其他节点。管理节点需要选择**强制**；为保持 Swarm 健康，请先将其降级。最后一个管理节点退出时会带走整个 Swarm，包括所有服务、机密和配置，因此 Homeport 会要求你先输入主机名称。

### 节点之间的端口

节点之间直接通信，而不是通过 Homeport，并且 Homeport 不会在节点上安装任何东西，因此它无法为你开放端口。请在 Swarm 的每个节点之间，在它们的防火墙以及你的网络防火墙中允许：

| 端口 | 协议     | 用途                        |
| ---- | -------- | --------------------------- |
| 2377 | TCP      | 管理 Swarm（到管理节点）    |
| 7946 | TCP、UDP | 节点相互发现                |
| 4789 | UDP      | 节点之间的 overlay 网络流量 |

当主机无法访问管理节点时，加入会失败并显示**此主机无法访问 Swarm 的管理节点**，提示中会列出这些端口。

## 节点

<DocScreenshot
  name="swarm-nodes"
  alt="Swarm 的节点标签页：三个管理节点（其中一个是领导者）和两个工作节点（其中一个已腾空），以及它们的引擎版本、地址和标签。"
/>

**节点**标签页列出 Swarm 的每个节点：其主机名、它是管理节点（以及是否为领导者、可访问或无法访问）还是工作节点、其可用性、它是在线（`ready`）还是 `down`、其引擎版本、地址和标签。同时也是你的主机之一的节点会链接到该主机的页面，主机的页面也会链接回其节点。列表会随节点的变化自动刷新。

每个节点的菜单用于更改它：

| 操作               | 作用                                                                                        |
| ------------------ | ------------------------------------------------------------------------------------------- |
| **激活**           | 调度器可以再次在它上面放置新任务。                                                          |
| **暂停**           | 它保留现有任务，但不再接收新任务。                                                          |
| **腾空**           | 它的任务会转移到其他节点：在维护前执行此操作。                                              |
| **升级为管理节点** | 它加入管理节点。请保持奇数个管理节点（1、3 或 5 个），以便 Swarm 在其中一个故障时仍能运行。 |
| **降级为工作节点** | 它离开管理节点，但继续运行任务。                                                            |
| **编辑标签**       | 设置放置约束据以选择节点的标签，例如 `node.labels.zone==a`。                                |
| **删除**           | 将它从 Swarm 中移出。                                                                       |

Homeport 会在询问引擎之前拒绝降级 Swarm 最后一个可访问的管理节点（没有管理节点的 Swarm 根本无法管理），也会拒绝腾空其最后一个活动节点（它的任务将无处可去）。删除仍在线的节点需要选择**强制**；管理节点必须先降级。如果在读取列表之后有其他人更改了某个节点，更改会被拒绝并显示**自 Homeport 读取以来，它已在其他地方被更改**：请刷新后重试，这样就不会覆盖任何内容。

## 服务

<DocScreenshot
  name="swarm-services"
  alt="Swarm 的服务标签页，列出每个服务及其镜像、模式、正在运行和期望的任务数、端口和堆栈。"
/>

**服务**标签页列出 Swarm 运行的内容：每个服务的名称、镜像、模式（副本模式及其副本数，或全局模式：每个节点一个任务）、有多少个任务正在运行以及应该运行多少个（运行数量不足时以警告颜色显示）、其发布的端口、它所属的 Swarm 堆栈，以及其最后一次更新的状态。列表会随服务的变化自动刷新。

每个服务的菜单：

- **日志**会打开其日志，合并自每个任务，每一行都标有其任务和节点，例如 `web.2@node-b`。跟踪日志时，Swarm 之后启动的任务也会加入进来。
- **扩缩**设置副本模式服务运行多少个副本；设为 0 会停止它但不删除它。全局服务不能扩缩：它们在每个节点上运行一个任务。
- **回滚**会恢复服务在最后一次更新之前的设置（镜像、环境变量、副本数…），与 `docker service rollback` 相同。从未更新过的服务没有可回滚的版本，并会说明这一点。
- **删除**会停止并删除其任务。它的卷会保留。

选择一个服务即可打开它。它的页面从**任务**开始，因此正在进行的滚动更新或无法启动的副本会立即显示出来，页面顶部有**编辑**、**扩缩**、**回滚**和**删除**。

**日志**标签页会跟踪其日志，**检查**会显示引擎中保存的完整定义，包括 Homeport 不编辑的内容（放置约束、资源限制、健康检查、更新和回滚策略）。

### 创建和更新服务

“服务”标签页上的**创建服务**会从镜像启动一个服务：它的名称、是副本模式（以及副本数）还是全局模式、任务何时重启、替换镜像自身命令的命令、环境变量（每行一个 `KEY=value`）、发布的端口、卷和绑定挂载、它加入的 overlay 网络，以及提供给它的机密和配置，每个都挂载到你指定的位置（机密默认为 `/run/secrets/<name>`）。端口通过 Swarm 的路由网格发布，可在每个节点上访问，除非你选择只在运行每个任务的节点上发布。绑定挂载是每个节点上的路径，而不是本机上的路径。Homeport 会在发送前检查表单：有效的名称、`KEY=value` 条目、被发布两次的端口。新服务会在其**任务**标签页上打开，你可以在那里观察其副本启动。

服务页面上的**编辑**会更改其镜像、环境变量和副本数，且仅限这些：它的端口、挂载、网络和其他所有内容都会原样发回。随后 Swarm 会每次几个地将任务切换到新设置，页面会显示更新的进度。**重新部署所有任务**会在没有任何更改时也重启它们，并重新拉取镜像，这就是推出同一标签的新推送的方式。如果在你打开服务之后有其他人更新了它，Homeport 会说明这一点，而不是覆盖他们的更改：请刷新后重新编辑。

私有镜像：节点会自己拉取镜像，因此私有镜像需要在每个节点上登录（在那里运行 `docker login`），或者使用你的镜像仓库凭据部署堆栈（请参阅[部署堆栈](#将堆栈部署到-swarm)）。

## 任务

服务以**任务**的形式运行：每个副本一个（它的槽位，例如 `web.2`），全局服务则每个节点一个（`agent@node-b`）。每个任务在其节点上作为一个容器运行。当服务显示正在运行的任务少于应有数量时，答案就在它的任务中。

**任务**标签页列出 Swarm 的任务，按服务再按槽位分组，最新的排在前面：每个任务运行所在的节点、它正在做什么以及 Swarm 希望它做什么（两者不同时显示**应为运行中**）、从何时开始、它的消息（如果是错误则以红色显示）以及它的镜像。

常见错误：

| 错误                                                      | 含义                                                                                 |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| `No such image`、`pull access denied`                     | 节点无法拉取镜像：请检查镜像名称，或该镜像仓库是否需要在该节点上登录。               |
| `no suitable node`                                        | 没有节点满足服务的约束、拥有它预留的资源或处于活动状态：请检查放置约束和节点可用性。 |
| `port is already allocated`、`address already in use`     | 以 `host` 模式发布的端口在该节点上已被占用。                                         |
| `invalid mount config`、`bind source path does not exist` | 绑定挂载指定了节点上不存在的路径。绑定挂载是每个节点上的路径。                       |
| `task: non-zero exit (1)`                                 | 容器已启动但以错误退出：从服务的**日志**标签页打开其日志。                           |

## 机密和配置

服务从**机密**中读取凭据，从**配置**中读取配置文件，两者都作为文件挂载在容器中（机密位于 `/run/secrets/` 下）。**机密**和**配置**标签页列出它们以及使用它们的服务、它们的标签，以及创建和更新的时间。

<DocScreenshot
  name="swarm-secrets"
  alt="Swarm 的机密标签页，列出三个机密以及使用每个机密的服务。"
/>

**创建机密**会要求填写名称和值（除非你选择**显示**，否则值会被遮盖），也可以选择**从文件加载…**改为发送本机上的文件（密钥、证书）。值只会发送给 Swarm 一次：Homeport 不会保存它，引擎也从不将其发回，因此任何人（包括 Homeport）都无法从 Swarm 中读取它。**创建配置**的工作方式相同，只是输入时会显示内容；配置的内容可以从其所在行再次查看。两者的大小上限均为 500 KB。

机密和配置一经创建就无法更改。要更改它们，请以新名称（例如 `db_password_v2`）创建一个新的，让服务指向它，然后删除旧的。服务正在使用的机密或配置无法删除：Swarm 会拒绝，Homeport 会列出使用它的服务。

## Swarm 堆栈

**Swarm 堆栈**是部署到 Swarm 的堆栈：由 compose 文件转换而来、共享一个命名空间的服务、网络、机密和配置。无论以何种方式部署，Homeport 都会通过 `docker stack deploy` 添加在它们上的 `com.docker.stack.namespace` 标签找到每一个 Swarm 堆栈。Swarm 的**堆栈**标签页会列出它们，就像**堆栈**页面列出主机的堆栈一样：它们的类型、状态（每个服务的每个任务都在运行时为运行中，每个服务都扩缩到 0 时为已停止）和服务。

从终端用 `docker stack deploy` 部署的堆栈是**外部堆栈**：Homeport 没有它的 compose 文件。选择它即可查看其服务（每个都链接到其页面）以及它的网络、机密和配置。**删除**与 `docker stack rm` 的作用相同：它删除服务，等待其任务停止，然后删除该命名空间的网络、机密和配置。Swarm 拒绝删除的任何内容都会被列出。卷会保留在每个节点上。

<DocScreenshot
  name="swarm-stacks"
  alt="Swarm 的堆栈标签页：部分运行的托管堆栈 shop（10 个任务中有 9 个），以及正在运行的外部堆栈 monitoring。"

Swarm 堆栈没有启动或停止操作：Docker 没有针对它的这种操作。要停止堆栈而不删除它，请从服务页面将其服务扩缩到 0。

在主机的**容器**页面上，Swarm 堆栈的任务在该主机上运行的容器会归入该堆栈下，并标记为 **Swarm**，而不是逐个列出。

## 将堆栈部署到 Swarm

托管、关联和同步堆栈可以部署到 Swarm，而不是主机。在**新建堆栈**中（从“堆栈”页面，或 Swarm 的**堆栈**标签页上的**新建堆栈**），在**部署到**下选择该 Swarm，然后像对主机一样编写 compose 文件、选择文件夹或仓库。Swarm 的**堆栈**标签页会将它们与外部堆栈一起列出；那里的堆栈页面有**部署**或**重新部署**、可编辑的**定义**，以及可用于回滚的**历史**，与主机上的相同。

Homeport 使用 `docker stack deploy` 进行部署，在本机上针对 Swarm 中已连接的任意一个管理节点运行，并通过与 compose 相同的私有、按命令建立的连接进行：不会在任何节点上安装或写入任何东西。它需要本机上有 `docker` 命令（请参阅[要求](/docs/requirements/)）。没有已连接的管理节点时，部署会说明这一点。Swarm 的堆栈属于该 Swarm，而不属于创建它时所通过的管理节点：删除该主机后堆栈仍会保留。

在 Swarm 上有哪些不同：

- **镜像来自镜像仓库。** 每个节点会拉取它所运行任务的镜像，因此从本地文件构建的服务（有 `build:` 而没有 `image:`）会在运行任何内容之前被拒绝：请先推送镜像，并在 `image:` 中指定它。堆栈**定义**中的**发送我的镜像仓库凭据**会让 docker CLI 将它在本机上拥有的登录信息（`docker login`）发送给 Swarm，以便其节点可以拉取私有镜像。它默认关闭；Homeport 自己的镜像仓库登录信息从不会交给 CLI。
- **某些 compose 键会被 `docker stack deploy` 忽略**：`container_name`、`restart`（请使用 `deploy.restart_policy`）、`depends_on` 条件以及 `profiles`。编辑器会对它们发出警告。绑定挂载是运行任务的那个节点上的路径。
- **删除**会像 `docker stack rm` 一样下线堆栈，并且没有启动或停止操作。

### Swarm 上的关联堆栈和同步堆栈

大多数 Swarm 堆栈与其配置文件一起放在文件夹或仓库中，这正是关联堆栈和同步堆栈在 Swarm 上最能发挥作用的地方。Homeport 从本机上该堆栈的文件夹（关联堆栈的文件夹，或同步堆栈的检出副本）运行 `docker stack deploy`，因此相对路径的 `env_file:`、`configs: file:` 和 `secrets: file:` 会在本机读取并发送给 Swarm。文件夹中的 `.env` 也会被读取，与 compose 的做法相同（`docker stack deploy` 本身不会读取）。不会在任何节点上写入任何东西，从文件读取的机密会发送给 Swarm，而 Homeport 不会保存它们。

- 带有 `build:` 的服务也需要 `image:`：Homeport 无法将在这里构建的镜像交给节点。请构建并推送镜像，然后再部署。
- Swarm 上的同步堆栈会像在主机上一样同步、部署和自动部署：每次部署都使用刚刚获取的提交。
- 从文件夹部署的外部 Swarm 堆栈可以关联到该文件夹：在其页面上选择**关联到文件夹…**。在关联之前，Homeport 会检查该文件夹的 compose 文件是否声明了该堆栈运行的服务，以免堆栈被绑定到其他项目的文件。

Swarm 的配置和机密一经创建就无法更改。当 `file:` 来源发生变化时，重新部署会失败并显示**此堆栈的某个配置或机密已更改，而 Swarm 无法就地更改它们**：请为该对象指定带版本的名称，例如

```yaml
configs:
  app_conf:
    name: app_conf_${CONF_VERSION}
    file: ./app.conf
```

并在每次文件更改时修改文件夹 `.env`（或堆栈的环境变量）中的 `CONF_VERSION`。Homeport 从不会在你不知情的情况下删除并重新创建它们。
