サーバー上の Docker Engine に到達するには、SSH をおすすめします。SSH ポート以外に何も公開する必要がなく、エンジンのソケットはサーバー内に閉じたままです。

## 仕組み

Homeport は独自の SSH クライアントを備えています。サーバーにログインし、エンジンの Unix ソケットへのチャネルをフォワードします。`docker -H ssh://…` と同じことを、手元のマシンに `ssh` プログラムや `docker` がなくても行えます。

- キーはメモリ上でのみ復号され、ディスクに書き込まれることはないため、Windows、macOS、Linux のどれでも同じように動作します。
- Homeport は `~/.ssh/known_hosts` を読みません。サーバーのキーは Homeport の中で、ホストごとに信頼します。踏み台サーバー経由でしか到達できないサーバーは、Homeport の `ProxyJump` である[踏み台](#踏み台を経由する)を使って追加します。
- サーバーは Unix ソケットへのフォワーディングを許可している必要があります。OpenSSH は既定で許可しています（`AllowStreamLocalForwarding yes`）。

## SSH のホストを追加する

<Steps>

1. ホストの切り替えメニューで **ホストを追加…** を選び、**SSH** を選択したままにします。

2. 接続情報を入力します:

   | フィールド                 | 入力する内容                                                                                                                                                                 |
   | -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
   | **名前**                   | `production` など、見てわかる名前。                                                                                                                                          |
   | **サーバー**               | サーバーのホスト名または IP アドレス。                                                                                                                                       |
   | **ポート**                 | SSH のポート。既定は `22`。                                                                                                                                                  |
   | **ユーザー**               | ログインに使うアカウント。Docker ソケットへのアクセス権が必要で、通常は `docker` グループを通じて付与します。                                                                |
   | **リモートソケットのパス** | サーバー上でエンジンが待ち受けている場所。既定は `/var/run/docker.sock`、rootless の Docker では `/run/user/<uid>/docker.sock`、Podman では `/run/podman/podman.sock` です。 |

3. **認証** でサインイン方法を選びます（下記参照）。

4. **ホストを追加** を選びます。Homeport がホストのページを開いて接続します。

</Steps>

<DocScreenshot name="add-host-ssh" alt="SSH が選択された「ホストを追加」フォーム。" />

## ~/.ssh/config からのインポート

サーバーがすでに `~/.ssh/config` に書かれている場合は、1 台ずつ入力する代わりに **ホストを追加** の **~/.ssh/config からインポート** を選びます。Homeport はファイルに書かれたすべてのサーバーを（`Include` をたどり、`Host *` の既定値を適用して）一覧表示し、追加するものを選べます。

| `~/.ssh/config` での記述 | Homeport での扱い                                                                                               |
| ------------------------ | --------------------------------------------------------------------------------------------------------------- |
| `Host prod`              | `prod` という名前のホスト。ワイルドカードを含むエントリ（`Host *.example.com`）は既定値の提供だけに使われます。 |
| `HostName`               | **サーバー**。ない場合はエイリアスそのもの。                                                                    |
| `User`、`Port`           | **ユーザー**（既定はローカルのユーザー名）と **ポート**（`22`）。                                               |
| `IdentityFile`           | **既存のキー**: 読み込める最初のファイル。`~` と `%h`、`%r`、`%u`、`%p` は展開されます。                        |
| `IdentityFile` なし      | **ssh-agent**。                                                                                                 |
| `ProxyJump a,b`          | 2 つの[踏み台](#踏み台を経由する)を順番どおりに。それぞれ同じファイル内で検索されます。ループは報告されます。  |

**リモートソケットのパス** の初期値は `/var/run/docker.sock` です。rootless の Docker や Podman の場合はプレビューで変更してください。暗号化されたキーは、プレビューでパスフレーズを求めます。

プレビューでは、確認が必要なものにフラグが付きます。読み込めないキー（ホストは代わりに ssh-agent を使います）、`ProxyCommand`（非対応。その踏み台サーバーを踏み台として追加してください）、すでにホスト名として使われているエイリアスです。最後のものは選択されません。インポートするには名前を変更してください。これにより、2 回インポートしても重複は作成されません。キーは一度だけ読み込まれて暗号化して保存され、ファイル自体は変更されません。`Match` ブロックと証明書（`CertificateFile`）は無視されます。

## 認証

### このホスト用の新しいキー（推奨）

Homeport はこのホスト専用の Ed25519 キーを作成して暗号化して保存し、サーバーでそれを許可するコマンドを表示します。ホストごとに 1 つのキーを使うので、ほかに一切影響を与えずに、1 台のサーバーに対する Homeport のアクセスを取り消せます。キーのコメントには、このコンピューターとホストの名前（例: `homeport@laptop-production`）が入るため、`authorized_keys` の中で見分けられます。

### 既存のキー

秘密鍵を貼り付けるか **ファイルから読み込む…** を選び、パスフレーズがある場合は **パスフレーズ** を入力します。Homeport は OpenSSH のキー（`BEGIN OPENSSH PRIVATE KEY`）、PKCS#8 と PEM のキー、PuTTY の `.ppk` ファイルを読み込めます。キーの種類は Ed25519、ECDSA、RSA に対応しています。キーとパスフレーズは暗号化して保存されるため、再度尋ねられることはありません。

### ssh-agent

Homeport は動作中の SSH エージェントにキーを要求し、何も保存しません。macOS と Linux では `$SSH_AUTH_SOCK` のエージェントを使います。

Windows では、まず OpenSSH Authentication Agent サービスに、次に PuTTY の **Pageant**（または KeeAgent や PuTTY 対応の gpg-agent など、その代わりになるツール）に要求します。どちらが持っているキーでも使えます。OpenSSH のエージェントが動作していないか、サーバーが受け付けるキーを持っていない場合、Homeport は Pageant のキーも試します。

<Aside>
  ssh-agent は、[OS のキーチェーン](/docs/requirements/#任意-os-のキーチェーン)なしで使える唯一の
  SSH の選択肢です。Homeport をデスクトップのメニューから起動した場合は、セッションのエージェントを
  Homeport が使えることを確認してください。
</Aside>

## 初回接続

Homeport が初めて接続するとき、ホストのページで 2 つのステップを案内します。

### サーバーのキーを信頼する

ステータスに **サーバーキーが信頼されていません** と表示され、ページには **これは正しいサーバーですか？** という質問とともに、`SHA256:Kx8f…` のようなサーバーのキーのフィンガープリントが表示されます。

サーバー上のフィンガープリントと照合します:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

一致すれば **このキーを信頼** を選びます。Homeport はキーを記憶して接続します。これは `ssh` が行うのと同じ初回接続時の信頼（TOFU）の確認で、キーが `~/.ssh/known_hosts` ではなく Homeport に保存される点だけが異なります。

### Homeport のキーを許可する

Homeport が作成したキーやインポートしたキーの場合、**サーバーで Homeport を許可** カードに 2 つのコマンドが表示され、それぞれに **コピー** ボタンがあります。SSH のユーザーとしてサーバーで実行してください:

<DocScreenshot
  name="host-ssh"
  alt="SSH のホストのページ。サーバーで Homeport のキーを許可するコマンドが表示されている。"
/>

<Steps>

1. ユーザーの `authorized_keys` に **公開鍵を追加** します:

   ```sh
   mkdir -p ~/.ssh && chmod 700 ~/.ssh && echo 'ssh-ed25519 AAAAC3Nza… homeport@laptop-production' >> ~/.ssh/authorized_keys && chmod 600 ~/.ssh/authorized_keys
   ```

2. まだできない場合は、**ユーザーがエンジンのソケットにアクセスできるようにします**:

   ```sh
   sudo usermod -aG docker deploy
   ```

3. Homeport に戻り、**再接続** を選びます。

</Steps>

キーが許可されるまで、ホストには **アクセスが拒否されました** と表示されます: _SSH サーバーは deploy@server のログインを拒否しました。server の authorized_keys に、このホストの公開鍵を追加してください。_ ホストは再試行せずに、ユーザーの対応を待ちます。

## サーバーのキーが変わったとき

その後サーバーが別のキーを提示した場合、Homeport は接続を止め、期待したフィンガープリントと提示されたフィンガープリントとともに **サーバーキーが変更されました** と表示します。

<Aside type="caution">
  サーバーを再インストールしたり、ホストキーを再生成したりした後は、キーが変わるのは想定どおりです。しかし、誰かが接続を傍受していることを意味する場合もあります。キーが変わった理由がわかっている場合にのみ、新しいキーを信頼してください。
</Aside>

確信が持てたら、**新しいキーを信頼** を選んで確認します。

ホストを編集して別のサーバーやポートを指すようにすると、信頼したキーは忘れられ、新しいキーを信頼するよう求められます。ホストの名前変更や、ユーザー、ソケットのパスの変更では、キーは維持されます。

## 踏み台を経由する

踏み台サーバーからの SSH しか受け付けないサーバーもあります。そのサーバーをホストのフォームの **踏み台** に追加すると、Homeport はまずそこにログインし、それを経由してホストに到達します。`ssh -J` や `ProxyJump` と同じことを Homeport 独自の SSH クライアントで行います。踏み台には何もインストールされず、キーがディスクに書き込まれることもありません。

<Steps>

1. SSH のホストのフォームで **踏み台を追加** を選びます。

2. 踏み台の **サーバー**、**ポート**、**ユーザー** を入力します。

3. Homeport が踏み台にログインする方法を選びます:

   | 認証             | 使う場面                                                                                                                                    |
   | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
   | **ホストと同じ** | 踏み台が、ホストの使うキー（Homeport が作成したキー、既存のキー、エージェントのキー）を受け付ける場合。                                     |
   | **専用のキー**   | 踏み台に別のキーが必要な場合。貼り付けるか **ファイルから読み込む…** を選びます。ホストのほかのシークレットとともに暗号化して保存されます。 |
   | **ssh-agent**    | エージェントが踏み台のキーを持っていて、ホストは別のキー（例: Homeport がそのホスト専用に作成したキー）を使う場合。                         |

4. 踏み台サーバーをつなぐ場合（`ProxyJump a,b`）は、Homeport が経由する順に、サーバーごとに踏み台を 1 つずつ追加します。矢印で踏み台を上下に移動できます。

</Steps>

初回接続では、最初の踏み台から順に、各サーバーのキーを信頼するよう求められます。**これは正しい踏み台ですか？** に踏み台の名前とフィンガープリントが表示されます。各踏み台のキーはホストとともに保存され、キーが変わると、ホスト自体の場合と同様に **踏み台 … のキーが変更されました** と表示されて接続が止まります。

ホストが Homeport の作成したキーを使う場合、**サーバーで Homeport を許可** カードには、キーを追加すべきすべてのサーバー（**ホストと同じ** に設定した各踏み台、続いてホスト）が一覧表示されます。

踏み台は、ホストへの TCP フォワーディングを許可している必要があります（`AllowTcpForwarding yes`。OpenSSH の既定です）。許可していない場合やホストに到達できない場合、ホストには _踏み台 … は … への接続を開けませんでした_ と表示されます。

一覧の中で踏み台を移動しても、信頼したキーは維持されます。サーバーやポートを変更すると、その踏み台のキーだけが忘れられます。

## キーの再生成

Homeport が作成したキーの場合、ホストのページの **キーを再生成** でキーを置き換えられます。古いキーは使えなくなるため、新しい **公開鍵を追加** のコマンドをサーバーで実行し、古い行を `~/.ssh/authorized_keys` から削除してください。

## SSH のホストを削除する

ホストを削除すると、そのキーは Homeport から削除されますが、サーバーからは削除されません。ユーザーの `~/.ssh/authorized_keys` からその行を削除してください。`homeport@` で始まるコメントが目印です。

## よくある問題

| メッセージ                                                                   | 対処                                                                                                                                                                                                           |
| ---------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| _SSH サーバーは … のログインを拒否しました_                                  | サーバーで **公開鍵を追加** のコマンドを実行してから、**再接続** します。                                                                                                                                      |
| _… は … の /var/run/docker.sock にある Docker Engine のソケットを開けません_ | **リモートソケットのパス** を確認し、ユーザーを `docker` グループに追加します。                                                                                                                                |
| _… が時間内に応答しませんでした_                                             | サーバー名、ポート、途中のファイアウォールを確認します。                                                                                                                                                       |
| _ssh-agent が動作していません_                                               | エージェントを起動し、`ssh-add` でキーを追加して、Homeport が `SSH_AUTH_SOCK` を参照できることを確認します。Windows では Pageant を開いてキーを読み込むか、OpenSSH Authentication Agent サービスを起動します。 |
| _踏み台 … は … への接続を開けませんでした_                                   | 踏み台がホストに到達できること、その `sshd` が `AllowTcpForwarding` を許可していることを確認します。                                                                                                           |

詳しくは[トラブルシューティング](/docs/reference/troubleshooting/)を参照してください。
