## インストールと起動

### Windows に「Windows によって PC が保護されました」と表示される

インストーラーはまだ商用の証明書で署名されていません。**詳細情報** を選び、**実行** を選んでください。先に[ダウンロードを検証](/docs/reference/verifying/)することもできます。

### macOS に Homeport を「開けません」と表示される

Homeport はまだ Apple の公証を受けていません。**システム設定 → プライバシーとセキュリティ** を開いて Homeport の横にある **このまま開く** を選ぶか、次を実行してください:

```sh
xattr -dr com.apple.quarantine /Applications/Homeport.app
```

### AppImage が起動しない

FUSE について表示される場合は、`libfuse2`（Ubuntu 24.04 以降では `libfuse2t64`）をインストールしてください。ファイルに実行権限があることも確認してください: `chmod +x Homeport_*.AppImage`。

### Homeport が意図しない場所に開く

Homeport は、閉じたときのウィンドウのサイズ、位置、最大化の状態で再び開きます。ウィンドウがあったディスプレイがなくなっている場合は、残っているディスプレイの中央に開きます。保存された位置を忘れさせるには、Homeport を終了し、設定フォルダーから `.window-state.json` を削除してください:

| システム | ファイル                                                            |
| -------- | ------------------------------------------------------------------- |
| Linux    | `~/.config/com.homeport.app/.window-state.json`                     |
| macOS    | `~/Library/Application Support/com.homeport.app/.window-state.json` |
| Windows  | `%APPDATA%\com.homeport.app\.window-state.json`                     |

### Homeport をもう一度開いても 2 つ目のウィンドウが開かない

Homeport は一度に 1 つしか動作しません。すでに動作中に開くと、[システムトレイ](/docs/guides/overview/#システムトレイ)に隠れている場合でも、そのウィンドウが前面に表示されます。2 つのコピーが動くと、すべてのホストに 2 回ずつ接続し、同じデータに書き込んでしまうためです。

### トレイアイコンがない

Linux では、トレイに appindicator ライブラリが必要で、トレイアイコンを隠すデスクトップもあります。GNOME では AppIndicator Support 拡張機能をインストールしてください。Homeport が appindicator ライブラリを見つけられない場合は、**設定 → デスクトップ** にそのことが表示され、ウィンドウを閉じると終了します。[要件](/docs/requirements/#任意-システムトレイ)を参照してください。

### OS のキーチェーンを利用できないという赤いバナーが表示される

Homeport がキーチェーンにアクセスできませんでした。Linux では通常、Secret Service が動作していないことを意味します。最小構成のデスクトップやウィンドウマネージャーでよくあることです。GNOME Keyring（`gnome-keyring`）をインストールして起動するか、KWallet の Secret Service を有効にしてから、Homeport を再起動してください。それまでは、ローカルソケット、TCP、ssh-agent のホストを使ってください。

## アップデートとパッケージリポジトリ

### 「アップデートを確認できませんでした」

Homeport がこの Web サイトからアップデートの情報をダウンロードできませんでした。オフラインになっているか、`damienreichhart.github.io` をブロックするプロキシやファイアウォールの内側にいる可能性があります。Homeport は引き続き動作し、後で再び確認します。**設定 → アップデート → 今すぐ確認** を選ぶこともできます。最新バージョンはいつでも[ダウンロードページ](/download/)からダウンロードできます。

### アップデートのインストールに失敗する

Homeport は、署名がアップデートキーと一致するアップデートだけをインストールし、ダウンロードが不完全か改変されている場合は中止します。後でもう一度試してください。失敗が続く場合は、[ダウンロードページ](/download/)から新しいバージョンをダウンロードし、古いものに上書きしてインストールしてください。

### apt に「NO_PUBKEY」や「The repository is not signed」と表示される

`/etc/apt/keyrings/homeport.asc` に Homeport の鍵がありません。[クイックインストール](/docs/installation/#クイックインストール)をもう一度実行するか、[手動セットアップ](/docs/installation/#手動セットアップ)の最初の 2 つのコマンドを実行してください。

### dnf や zypper が鍵をインポートするか尋ねてくる

それは Homeport のパッケージ鍵で、パッケージマネージャーが初めてリポジトリを使うときに尋ねられます。表示されたフィンガープリントが[ダウンロードの検証](/docs/reference/verifying/#パッケージの署名)に記載されたものと一致することを確認してから、受け入れてください。

### リリース直後に apt に「Hash Sum mismatch」と表示される

apt が読み込んでいる間に、リポジトリが更新されていました。数分後に `sudo apt update` をもう一度実行してください。

### パッケージマネージャーに新しいバージョンが表示されない

リポジトリがまだ設定されているか確認してください: `/etc/apt/sources.list.d/homeport.sources`、`/etc/yum.repos.d/homeport.repo`、`/etc/zypp/repos.d/homeport.repo` のいずれかです。削除してしまった場合は、[クイックインストール](/docs/installation/#クイックインストール)を実行して再び追加してください。0.2.0 以前をダウンロードしたファイルからインストールした場合、リポジトリは追加されていません。[0.2.0 以前からのアップデート](/docs/reference/updating/#020-以前からのアップデート)を参照してください。

## 接続

### 到達不能: Permission denied

ユーザーが Docker ソケットを開けません。Linux では、ユーザーを `docker` グループに追加して、ログインし直してください:

```sh
sudo usermod -aG docker $USER
```

### 到達不能: No such file or directory

ソケットのパスで何も待ち受けていません。エンジン（Docker Desktop、Colima、OrbStack、Rancher Desktop）を起動するか、パスを確認してください。[ローカルのエンジン](/docs/hosts/local/#ソケットを手動で追加する)を参照してください。

### 「Docker Engine が時間内に応答しませんでした。」または「… が時間内に応答しませんでした。」

Homeport は接続を 10 秒間待ちます。アドレスとポート、サーバーが起動していること、ファイアウォールが妨げていないことを確認してください。Homeport は自動で再試行し続けます。

### アクセスが拒否されました: 「SSH サーバーは … のログインを拒否しました。」

サーバーがまだ Homeport のキーを受け付けていません。ホストのページにある **公開鍵を追加** のコマンドをサーバーで実行してから、**再接続** を選んでください。[SSH のホスト](/docs/hosts/ssh/#homeport-のキーを許可する)を参照してください。

### 「… は … の /var/run/docker.sock にある Docker Engine のソケットを開けません。」

Homeport はログインできましたが、Docker に到達できませんでした。次を確認してください:

- **リモートソケットのパス** — rootless の Docker は `/run/user/<uid>/docker.sock` を使います。
- ユーザーが Docker を使えること — サーバーで `sudo usermod -aG docker <user>` を実行します。
- サーバーがソケットのフォワーディングを許可していること — `sshd_config` の `AllowStreamLocalForwarding`。既定で有効です。

### 「ssh-agent が動作していません。」

SSH エージェントを起動し、`ssh-add` でキーを追加してください。デスクトップのメニューから Homeport を開いた場合、ターミナルが使っているエージェントが Homeport から見えないことがあります。ログアウトしてログインし直すか、`ssh-add -l` でキーが表示されるターミナルから Homeport を起動してください。

Windows では、Homeport は OpenSSH Authentication Agent サービスか PuTTY の Pageant を使います。Pageant を開いてキーを読み込むか、管理者権限の PowerShell でサービスを起動してください:

```powershell
Get-Service ssh-agent | Set-Service -StartupType Automatic
Start-Service ssh-agent
ssh-add
```

### アクセスが拒否されました: 「… へのセキュアな接続が失敗しました。」

- CA 証明書は、サーバーの証明書に署名したものである必要があります。
- 入力したアドレスは、サーバーの証明書にある名前か IP アドレスと一致する必要があります。
- サーバーは `--tlsverify` で動作し、クライアント証明書の CA を信頼している必要があります。

### サーバーキーが変更されました

SSH サーバーが、信頼したものとは異なるキーを提示しました。サーバーを再インストールしたかキーを変更した場合は、**新しいキーを信頼** を選んでください。キーが変わった理由がわからない場合は接続せず、サーバーの管理者に問い合わせてください。[SSH のホスト](/docs/hosts/ssh/#サーバーのキーが変わったとき)を参照してください。

### 認証情報が失われました

シークレットを暗号化する鍵がキーチェーンにないか、変わっています。キーチェーンのリセット、新しいユーザープロファイル、Homeport のデータの別のコンピューターへのコピー（その場合は[エクスポートとインポート](/docs/reference/security/#別のコンピューターへの移行)を使ってください）の後に起こります。Homeport はホストを保持しているので、ホストのページで認証情報を入力し直してください:

- **TLS** — 3 つの証明書ファイルを再び読み込み、**保存** を選びます。
- **インポートしたキーを使う SSH** — 秘密鍵とパスフレーズを再び貼り付け、**保存** を選びます。
- **Homeport のキーを使う SSH** — **キーを再生成** を選び、新しいキーをサーバーで許可します。

古い鍵で封印された管理スタックの環境変数も、入力し直す必要があります。

## クラスター

### アクセスが拒否されました: 「… は kubeconfig の認証情報を拒否しました。」

API サーバーが 401 を返しました。証明書かトークンの有効期限が切れたか、取り消されています。`kubectl --context <context> get namespaces` がまだ動作するか確認してから、クラスターのページで **kubeconfig から更新** を使ってください。exec プラグインの場合、Homeport はすでに一度新しいトークンを要求しています。

### 「… はこのコンピューターにインストールされていません。」

クラスターの [exec プラグイン](/docs/clusters/exec-plugins/)（`aws`、`gke-gcloud-auth-plugin`、`kubelogin`…）が `PATH` 上にも、通常のインストール場所にも見つかりませんでした。インストールし、ターミナルで動作することを確認してから、**再接続** してください。

### 「… ではサインインが必要ですが、Homeport の中ではサインインできません。」

exec プラグインがブラウザーかデバイスコードを必要としています。ターミナルで一度 `kubectl --context <context> get namespaces` を実行してそこでサインインしてから、**再接続** してください。

### 「… は … の認証情報を取得できませんでした。」

exec プラグインは実行されましたが、失敗しました。**詳細** には、プラグインが出力した内容の末尾が表示されます。多くの場合、プロファイルの期限切れかリージョンの誤りです。Homeport は自動で再試行します。

### 「このユーザーは gcp 認証プロバイダーでサインインしますが、Kubernetes はこれをもうサポートしていません。」

`gcp` と `azure` の認証プロバイダーは Kubernetes から削除されました。`gke-gcloud-auth-plugin` をインストールした状態で認証情報を取得し直す（GKE）か、`kubelogin convert-kubeconfig` を実行して（AKS）から、コンテキストを追加し直してください。

### 「この認証情報では、… の … に対する「…」は許可されていません。」

クラスターの RBAC で、kubeconfig のユーザーにその操作が許可されていません。右上の選択欄で閲覧を許可されている Namespace を選ぶか、クラスターの管理者に問い合わせてください。メッセージには、それを確認する `kubectl auth can-i` のコマンドが示されます。ほかのページは引き続き動作します。

### 到達不能: 「… は接続を拒否しました。」または「… が時間内に応答しませんでした。」

このコンピューターから API サーバーに到達できません。クラスターが停止している（ローカルのクラスターの場合）、VPN の内側にある、または kubeconfig のサーバーのアドレスが変わった可能性があります。Homeport は自動で再試行し続けます。同じコンテキストで `kubectl cluster-info` を確認してください。

### 「… の証明書は、kubeconfig にある CA で署名されていません。」

kind、k3d、minikube は、クラスターを作り直すたびに新しい証明書を作成します。クラスターのページで **kubeconfig から更新** を使ってください。

### Nomad: 「… は Homeport が送った ACL トークンを認識していません。」

トークンの入力を誤ったか、有効期限が切れたか、削除されています。[ACL ポリシー](/docs/clusters/nomad/#acl-ポリシー)のポリシーで新しいトークンを作り（`nomad acl token create -name=homeport -policy=homeport`）、そのシークレット ID をクラスターの **設定** に貼り付けてください。それまでクラスターは **アクセスが拒否されました** のまま待機します。

### Nomad: 「… は拒否しました。ACL トークンには、これに必要な権限がありません。」

トークンのポリシーが、このページや操作に必要な権限を与えていません。メッセージにはどの権限か（ジョブやログの読み取り、ジョブの実行や停止、スケール、シェルの起動、ノードの変更）が示されます。トークンのポリシーにその権限を追加してください。それぞれに必要なものは [ACL ポリシー](/docs/clusters/nomad/#acl-ポリシー)に一覧があります。ほかのページは引き続き動作します。

### Nomad: 「… にはリーダーがいません。サーバー間でリーダーについて合意できていません。」

クラスターのサーバーのうち、動作していて互いに到達できるものが過半数に達していないため、Nomad が応答できません。サーバー上で `nomad server members` を使って確認し、十分な数のサーバーを復帰させてください。Homeport は再試行し続けます。

### Nomad: 「… にジョブ … はありません。」

ジョブが停止されて完全削除されたか、ガベージコレクションされたか、選択中のものとは別の名前空間にあります。必要に応じて **すべての名前空間** を選び、「ジョブ」ページをもう一度開いてください。

### Nomad: 「… のタスクグループ … は … を超えて実行できません。」または「… 未満では実行できません。」

タスクグループの `scaling` ブロックが `min` と `max` を設定しており、要求した数がその範囲外です。さらに増減させるには、ジョブの仕様で範囲を変更して、もう一度実行してください。

### Nomad: 「… のデプロイメントが進行中のため、Nomad はスケールしません。」

service ジョブの新しいバージョンを実行するとデプロイメントが始まり、新しいバージョンのすべてのアロケーションが正常になるまで、Nomad はその数の変更を拒否します。ジョブのアロケーションが落ち着くのを待ってから、もう一度スケールしてください。

### Nomad: 「ジョブ仕様を解析できません（… 行目、… 列目）。」

Nomad のパーサーがその場所で問題を見つけました。**詳細** にそのメッセージがあります。Homeport は変数ファイルを渡さないため、`variable` ブロックには既定値が必要です。JSON の仕様は、`nomad job inspect` が出力するような、Nomad の API 形式のジョブである必要があります。

### Nomad: 「Nomad は … のすべてのアロケーションを配置できません: …。」

計画で、タスクグループが要求するリソースを持つ、または制約に合う適格なノードが見つかりませんでした。計画にはどれかが示されます。**それでも実行** を選ぶと、配置できないものはノードが受け入れられるようになるまでキューに入ります。または、リソースを下げる、制約を変更する、ノードを追加するといった対応をしてください。

### Nomad: 「計画の後に … が変更されたため、実行されませんでした。」

計画から **実行** までの間に、ほかの誰かがジョブを実行または停止しました。Homeport はその変更を上書きしません。戻ってもう一度計画し、新しい差分を確認してから実行してください。

### Nomad: 「アロケーション … のタスク … は実行されていません。」

シェルには実行中のタスクが必要です。このタスクはまだ起動していないか、終了したか、失敗しています。そのログは、アロケーションがガベージコレクションされるまで読めます。

### Nomad: 「… は、アロケーション … が実行されているノードに到達できません。」

ログとシェルはサーバーを経由してクライアントノードに届きますが、サーバーがノードに到達できません。ノードがダウンしているか、切断されているか、エージェントが停止しています。「ノード」ページか `nomad node status` で確認してください。

### Helm: 「helm CLI はこのコンピューターにインストールされていません。」

[Helm リリース](/docs/clusters/helm/)には、このコンピューターに `helm` 3 以降が必要です。インストールして（`brew install helm`、`winget install Helm.Helm`、`snap install helm --classic`）から、Helm のページを開き直してください。Homeport が見つけたものは **設定 → このマシン** に表示されます。`helm` 2 は非対応として報告されます。

### Helm: 「このリリースの別のインストール、アップグレード、またはロールバックがまだ進行中です。」

リリースが `pending-…` の状態です。インストール、アップグレード、ロールバックが完了しておらず、多くの場合は中断されたことが原因です。それが終わるまで、helm はリリースの変更を拒否します。終わるのを待つか、リリースの **履歴** から、最後にデプロイされたリビジョンにロールバックしてください。

## Homeport の使用

### デプロイがグレーアウトされている: 「docker compose CLI はこのコンピューターにインストールされていません。」

スタックをデプロイするには、このコンピューターに `docker compose` が必要です。Docker Desktop か、Compose プラグイン付きの Docker CLI をインストールしてから、Homeport を再起動してください。見つかったかどうかは **設定 → このマシン** に表示されます。

インストールされているのに見つからない場合、Homeport の `PATH` がターミナルのものと異なる可能性があります。macOS でデスクトップのメニューから起動した場合によくあることです。`docker` が `/usr/local/bin` などの標準的な場所にあることを確認してください。

### デプロイに失敗する: 「build: を使っており」

管理スタックには、ビルド元のフォルダーがありません。代わりに[プロジェクトフォルダーをリンク](/docs/guides/stacks/#リンクスタックを作成する)する（リンクスタックならビルドできます）か、イメージをビルドしてレジストリにプッシュしてから `image:` を使ってください。

### スタックが外部スタックになった

[リンクスタック](/docs/guides/stacks/#フォルダーが移動したまたはなくなった場合)は、フォルダーが移動、名前変更、削除された場合や、その中の compose ファイルがそうなった場合に、⚠ **compose ファイルがこのコンピューター上にもうありません。** という印とともに外部スタックとして表示されます。失われたものはありません。フォルダーを元の場所に戻せば、次の更新でスタックは再びリンクスタックになります。フォルダーを恒久的に移動した場合は、スタックの **定義** タブで **破棄** を選んでから、**新しいスタック → このコンピューター上のフォルダーを使う** で新しい場所からリンクし直してください。

別のコンピューター上のフォルダーから起動したスタックは、このコンピューターにはそのパスがないため、ここでは常に外部スタックになります。

### 「Homeport の外部で変更されました」

Homeport が最後に読み込んだ後に、リンクスタックの compose ファイルが Homeport の外部（エディターや `git pull` など）で編集されました。**再読み込み** を選ぶと、現在の内容を表示します。同時に Homeport で編集していた場合、どちらの変更も黙って失われないよう、保存は **開いた後に、… が Homeport の外部で変更されました。** として拒否されます。再読み込みして編集をやり直すか、**上書き** を選んで自分の変更を残してください。[リンクスタックの編集](/docs/guides/stacks/#リンクスタックを編集する)を参照してください。

### プライベートイメージのプルに失敗する

**設定 → レジストリ** でイメージのレジストリのログイン情報を追加し、**ログインを確認** でレジストリがそれを受け付けることを確かめてください。GHCR と、2 要素認証を使う Docker Hub のアカウントには、パスワードではなくアクセストークンが必要です。プルのダイアログには、どのログイン情報を使うかが表示されます。**匿名で** と表示される場合は、イメージのレジストリが保存済みのログイン情報と一致していません。`ghcr.io/org/app` には `ghcr.io` の、`org/app` には Docker Hub のログイン情報が必要です。

### ビルドに失敗する

メッセージには **ビルドがステップ 3/5（RUN make）で失敗しました。** のように失敗したステップが示され、**詳細** にはビルドの出力の末尾があります。Homeport はエンジンの従来のビルダーを使うため、BuildKit が必要な Dockerfile（`RUN --mount`、`--secret`、ヒアドキュメント）は失敗します。それらはターミナルからビルドしてください。プライベートな `FROM` イメージには、**設定 → レジストリ** にそのレジストリのログイン情報が必要です。

### 新しいイメージの印が表示されない

印が表示されるのは、レジストリに問い合わせて回答があった場合だけです。ローカルでビルドしたイメージや、ダイジェストでプルしたイメージには表示されません。レジストリに到達できない場合やリクエストが制限されている場合（Docker Hub はこの確認をプルの制限にカウントします）、Homeport は[ログ](/docs/reference/security/#ログ)に 1 行書き込み、何も表示しません。回答は 6 時間保持されるため、今すぐ問い合わせ直すには **新しいイメージを確認** を選んでください。**設定 → レジストリ** に Docker Hub のログイン情報があれば、制限が緩和されます。

### Docker Hub の検索でエラーが表示される

検索は選択中のホストで実行されるため、そのホストのインターネットアクセスが必要です。また、タグはこのコンピューターから `hub.docker.com` を読み込んで取得します。どちらもレート制限を受けたり、プロキシにブロックされたりすることがあります。ダイアログでは、`postgres:17-alpine` のように入力した完全な参照であれば引き続きプルできます。

### 「ファイル」タブに、コンテナに find と stat のツールがないと表示される

最小構成のイメージや distroless のイメージには、Homeport がファイルの一覧表示に使う `find` と `stat` が含まれていません。そうしたコンテナには `docker cp` を使ってください。

### ターミナルが開かない

コンテナが実行中で、`/bin/sh` か `/bin/bash` がある必要があります。別のプログラムを実行するには **新しいターミナル** を使ってください。

### ボリュームやネットワークを削除できない

停止中のものも含め、コンテナがまだ使っている間はエンジンが削除を拒否します。先にそのコンテナを削除してください。確認画面にそれらが一覧表示されます。

### 「Podman 5.8 以降が必要です」

Podman の API は、[Quadlet ユニット](/docs/guides/quadlet/)の閲覧、インストール、編集、削除に Podman 5.8 から、一覧表示に 5.7 から対応しています。ホストの Podman をアップデートするか、ホストのターミナルで `podman quadlet` を使ってください。ユニットの起動と停止は、どの Podman でも動作します。

### Quadlet: 起動と停止がグレーアウトされている

Homeport はユニットのサービスを `systemctl` で起動・停止しますが、これを実行できるのは SSH 経由か、このコンピューター上の Podman（Linux）の場合だけです。TCP や TLS ではなく、SSH でホストに到達するようにしてください。サービスが **未生成** と表示されるユニットには、起動するものがありません。systemd のジェネレーターがそのファイルをスキップしました。

### Quadlet: 「ホストでユーザーの systemd が動作していないため、そのユニットを起動・停止できません。」

ユーザーユニット（rootless の Podman）には、ユーザーの systemd インスタンスが必要です。これは、lingering が有効でない限り、ユーザーがログインしている間しか動作しません。ホスト上でそのユーザーとして `loginctl enable-linger "$USER"` を実行してから、もう一度試してください。

### Quadlet: 「systemd はこのユーザーに … の管理を許可しませんでした。」

システムユニット（rootful の Podman）を起動・停止できるのは、`root` など、それらの管理を許可されたユーザーだけで、Homeport は `sudo` を決して使いません。そうしたユーザーとして接続するか、ユニットがユーザー自身のものになる rootless の Podman を使ってください。

### containerd: 「… には … の /run/containerd/containerd.sock にある containerd の使用が許可されていません。」

containerd のソケットは root が所有しています。`/etc/containerd/config.toml` の `[grpc]` の下の `gid` でグループにアクセス権を与え、ユーザー（または SSH のユーザー）をそのグループに追加し、containerd を再起動してログインし直してください。コマンドは [containerd のページ](/docs/hosts/containerd/#ユーザーがソケットを使えるようにする)にあります。rootless の containerd にはまったく到達できません。そのソケットは RootlessKit の名前空間の中にしか存在しないためです。

### containerd: 「このコンテナの出力は記録されていません。」

containerd はログを保持しません。タスクの出力先は、タスクを起動したツールが決めます。`ctr` で作成したコンテナは、通常どこにも出力しません。nerdctl と Kubernetes のコンテナは、Homeport が読み込めるファイルにログを書き込みます。[ログ](/docs/hosts/containerd/#ログ)を参照してください。

### containerd: ログやターミナルに SSH が必要だと表示される

ログとターミナルには containerd のマシン上のファイルが必要で、Homeport はそれに SSH 経由で、または Linux のローカルソケットの場合はこのコンピューター上でアクセスします。ホストを SSH で追加してください。ログファイルを読めない場合は、通常 root が所有しているためです。読み取りを許可されたユーザーとして接続してください。

### containerd: 「… では、Homeport のためにイメージをプルできません。」

プルは containerd の Transfer サービスを使い、これは containerd 2.0 から安定版です。containerd をアップデートするか、ホスト上で `ctr images pull` や `nerdctl pull` を使ってプルしてください。プルしたイメージは「イメージ」ページに表示されます。

### Incus: 「… には … の /var/lib/incus/unix.socket にある Incus の使用が許可されていません。」

Incus の管理用ソケットは `incus-admin` グループ用で、制限付きの `unix.socket.user` は `incus` グループ用です。`sudo usermod -aG incus-admin "$USER"` でユーザー（または SSH のユーザー）を追加してから、ログアウトしてログインし直すか、SSH で再接続してください。[Incus のソケット](/docs/hosts/incus/#ソケット)を参照してください。

### Incus: 信頼トークンで追加するときに「Homeport は … の Incus に到達できませんでした。」

`core.https_address` を設定するまで、Incus はネットワークで待ち受けません。サーバーで `incus config set core.https_address :8443` を実行し、ファイアウォールがポート 8443 を通すことを確認して、新しいトークンを作成してください。トークンには、作成時に Incus が待ち受けていたアドレスが記載されます。

### Incus: 「Incus は信頼トークンを拒否しました。」

トークンは一度だけ使え、有効期限があります。サーバーで `incus config trust add homeport` を使って新しいトークンを作成し、有効期間内に貼り付けてください。

### Incus: 「… が提示した証明書のフィンガープリントは … で、信頼済みの … ではありません。」

サーバーの証明書が、Homeport が信頼したものではありません。Incus が再インストールされたか、証明書が更新されたか、そのアドレスで別のものが応答しています。サーバーで `incus info` を使ってフィンガープリントを確認し、表示されたものと一致すれば、ホストを削除して新しいトークンで追加し直してください。[固定された証明書](/docs/hosts/incus/#サーバーの証明書は固定される)を参照してください。

### Incus: 「このホストでは仮想マシンを実行できません。」

Incus で仮想マシンを使うには、KVM（`/dev/kvm`）と QEMU が必要です。サーバーのファームウェアで仮想化（仮想サーバーの場合はネストされた仮想化）を有効にするか、代わりにシステムコンテナを作成してください。

### Incus: 「仮想マシンの Incus エージェントが動作していないため、Homeport はその中でコマンドを実行できません。」

仮想マシン内での Exec は、その中の `incus-agent` を通じて行われ、Incus 自身のイメージは起動時にこれを開始します。起動が完了するのを待つか、エージェントが不要な **コンソール** タブを使ってください。

### 「… は接続されていません。」

操作にホストが必要でしたが、ホストが切断されました。再接続されるのを待つか、**今すぐ再試行** を選んでください。
