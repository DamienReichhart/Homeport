専用の操作でカバーされないものについて、YAML でクラスターを変更する方法が 2 つあります。マニフェストには `kubectl apply -f` のような **YAML を適用**、オブジェクトの **YAML** タブには `kubectl edit` のような **編集** です。どちらも、何かが変わる前に何が変わるかを表示します。

## YAML を適用

クラスターのサイドバーにある **YAML を適用** は、1 つ以上のマニフェストを受け付けます。貼り付けるか、**ファイルを開く…** でこのコンピューターから `.yaml`、`.yml`、`.json` のファイルを読み込みます。`---` で区切られた複数のドキュメントは、順番にまとめて適用されます。

Namespace のないドキュメントは、右上で選んだ Namespace に適用されます（**すべての Namespace** の場合は、クラスターのデフォルトの Namespace）。Namespace や ClusterRole のように Namespace に属さないオブジェクトは、これを無視します。

1. **変更をプレビュー** は、サーバーサイドのドライランで、各ドキュメントが何をするかをクラスターに問い合わせます。この時点では何も変わりません。各ドキュメントは **作成**、**変更**、**変更なし** のいずれかとして、変更される行とともに表示されます。
2. **適用** は、クラスター名を示して確認を求めてから適用します。

同じマニフェストを 2 回適用すると、2 回目は **変更なし** と報告されます。プレビューの後に YAML を編集すると、まず新しいプレビューが求められます。

## オブジェクトの編集

どのオブジェクトの **YAML** タブにも **編集** があります。クラスターが保持しているとおりの YAML が、サーバーが管理するもの（`managedFields`、`status`、`resourceVersion`、uid、作成時刻）を除いて表示されます。変更し、**変更をプレビュー** で変更した行だけを確認してから、**適用** します。

プレビューは、編集した YAML をプレビュー時点のオブジェクトと比較するので、その間に加えられた変更も差分に表示されます。編集によってほかのツールが管理するフィールドが変わる場合、プレビューはそれを上書きせずに競合として示します。

Secret は、すべての値を一度に表示することがないため、Homeport では編集できません。また、イベントは Kubernetes 自身が書き込むものです。

## サーバーサイド適用

Homeport は、フィールドマネージャー `homeport` のもとで、Kubernetes のサーバーサイド適用を使って適用します。クラスターは、Homeport が設定したフィールドを、`kubectl`、Helm、コントローラー、その他のツールが設定したフィールドと並べて記録します。これはオブジェクトの `managedFields` で確認できます。

ドキュメントがほかのツールの管理するフィールド（`kubectl apply` で設定された、またはオートスケーラーが管理する `.spec.replicas` など）を変更する場合、プレビューにはどのフィールドとどのマネージャーかが示されます。それらのフィールドを省くか、2 回目の確認の後に **それでも適用** してください。Homeport がそれらのフィールドを引き継ぎますが、ほかのツールが元に戻すこともあります。

## ドキュメントを適用できない場合

プレビューは各ドキュメントの問題をその場に表示し、すべてのドキュメントを適用できるようになるまで **適用** は無効のままです:

- **無効な YAML**: 問題のある行とともに示されます。
- **不明な kind**: クラスターがその `apiVersion` と `kind` を提供していません。カスタムリソースには、先に CRD のインストールが必要です。
- **クラスターによる拒否**: 必須フィールドの欠落や型の誤った値など、フィールドごとのクラスターの検証結果が示されます。
- **許可されていない**: 適用には、リソースに対する `patch`（新しいオブジェクトには `create` も）が必要です。確認用の `kubectl auth can-i` コマンドとともに示されます。
