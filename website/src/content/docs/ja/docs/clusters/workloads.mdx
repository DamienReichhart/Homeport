切り替えメニューでクラスターを選ぶと、サイドバーにそのクラスターのページが表示されます。**ワークロード** と **Pod** には、そこで動作しているものが一覧表示されます。どの一覧も Kubernetes の watch でクラスターをリアルタイムに追従するので、スケールした Deployment やクラッシュした Pod の新しい状態が、更新しなくても数秒以内に表示されます。各ページでは、表示しているものを操作することもできます: [ログとターミナル](/docs/clusters/logs-exec/)、[スケール、再起動、削除](/docs/clusters/actions/)、[YAML の編集](/docs/clusters/yaml/)。

## Namespace

クラスターの各ページには、右上で選んだ 1 つの Namespace、または **すべての Namespace** が表示されます。最初はクラスターの kubeconfig コンテキストの Namespace（なければ `default`）で始まり、Homeport はクラスターごとに選択を記憶します。

認証情報で一部の Namespace しか見られない場合は、そのいずれかを選んでください。そこではページが動作します。Namespace の一覧表示すらできない場合、選択欄は入力欄に変わり、使用を許可されている Namespace を入力できます。

## ワークロード

/>

**ワークロード** には種類ごとのタブがあります: **Deployment**、**StatefulSet**、**DaemonSet**、**Job**、**CronJob**。各行には、正常性、必要な Pod のうち準備ができている数、最新のテンプレートで動作している数、イメージ、経過時間が表示されます。

| 正常性       | 意味                                                                                              |
| ------------ | ------------------------------------------------------------------------------------------------- |
| **準備完了** | 必要な Pod がすべて準備完了で最新です。Job は完了しています。CronJob はスケジュールされています。 |
| **進行中**   | ロールアウト中、スケジューリング中、または Job が実行中です。                                     |
| **低下**     | Deployment のロールアウトが進行期限を過ぎました。                                                 |
| **失敗**     | Job が失敗しました。                                                                              |
| **一時停止** | ゼロにスケールされているか、Job または CronJob が一時停止されています。                           |

### ワークロードの読み方

**準備完了** は、readiness probe に合格した Pod の数を、ワークロードが必要とする数と比べて数えます。**最新** は、最新のテンプレートで動作している Pod の数です。ロールアウト中は後者が前者に遅れます。準備完了が `2/3` で最新が `1` なら、新しい Pod が 1 つ入り、古い Pod がまだ処理を担っているということです。**最新** が遅れたままで正常性が **低下** になった場合、新しい Pod は起動できていません。その理由は Pod のページに表示されます。

ワークロードのページには次のものがあります:

- **概要**: Namespace、レプリカ、ロールアウト戦略、Pod を選択するラベル、ラベルとアノテーション、イメージとポートを含むコンテナ。
- **Pod**: ワークロードが選択する Pod（CronJob の場合は **Job**: 起動した Job が新しい順に並びます）。
- Pod の **ログ**: すべてを交互に、または 1 つずつ（CronJob にはありません。その Job にそれぞれのログがあります）。
- **状態**、**イベント**（警告が先頭。Kubernetes は約 1 時間保持します）、**YAML**（`managedFields` を除き、**編集** 付き）。

ヘッダーには操作があります: 該当する場合は **スケール**、**再起動**、**一時停止** または **再開**、**今すぐ実行**、そして **削除**。[スケール、再起動、削除](/docs/clusters/actions/)を参照してください。

## Pod

<DocScreenshot
  name="cluster-pods"
  alt="「Pod」ページ: shop Namespace の Pod とそのステータス。1 つは 7 回再起動した CrashLoopBackOff、1 つは ImagePullBackOff。準備完了のコンテナ、Node、経過時間も表示されている。"
/>

**Pod** には、各 Pod が `kubectl get pods` と同じ表示のステータス（`Running`、`Pending`、`CrashLoopBackOff`、`ImagePullBackOff`、`Init:…`、`Terminating`）、準備完了のコンテナ、再起動回数、Node、経過時間とともに一覧表示されます。長い一覧は 1 ページに 100 行ずつ表示されるので、数千の Pod があるクラスターでも反応は遅くなりません。検索ボックスはすべての Pod を対象に絞り込みます。

<DocScreenshot
  name="cluster-pod"
  alt="クラッシュしている Pod のページ: 完了した init コンテナ、7 回の再起動の後に CrashLoopBackOff で待機している api コンテナ（最後: Error）、動作中の envoy サイドカー。"
  caption="api-…-xr4np が準備完了にならない理由: api コンテナがクラッシュを繰り返しています。サイドカーは問題ありません。"
/>

Pod のページには、Node、IP、QoS クラス、サービスアカウント、Pod を制御しているものが表示され、続いて各コンテナ（init コンテナが先）が、イメージ、状態、待機または終了している理由、再起動回数、最後に再起動した理由とともに表示されます。各コンテナには宣言しているポートが表示され、**フォワード…** で[このコンピューターからアクセス](/docs/clusters/port-forward/)できます。その後に **ログ** と **ターミナル**（[ログとターミナル](/docs/clusters/logs-exec/)）、ワークロードと同じく **状態**、**イベント**、**YAML** が続き、ヘッダーには **削除** があります。

### Pod が準備完了にならない理由を調べる

1. **Pod** で **ステータス** または **再起動** で並べ替えます。`CrashLoopBackOff`、`ImagePullBackOff`、`Error` は赤で表示されます。
2. Pod を開きます。準備完了になっていないコンテナには、待機または終了している理由が表示され、**再起動** には最後に終了した理由（`Error`、`OOMKilled`（メモリ制限に達した）、`Completed`）が示されます。
3. **前回のインスタンス** を有効にした **ログ** には、コンテナがクラッシュする前に出力した内容が表示されます。
4. **イベント** には、kubelet とスケジューラーが報告した内容があります: プルできないイメージ、失敗する probe、十分なメモリのある Node がない、など。
5. **YAML** には、クラスターが保持しているとおりの Pod が表示されるので、probe、制限、環境を確認できます。

## 認証情報で見られないものがある場合

認証情報で読み取りを許可されていない一覧には、その旨が表示されます（「この認証情報では、shop の daemonsets に対する「list」は許可されていません。」）。確認用の `kubectl auth can-i` コマンドも示されます。ほかのページは引き続き動作します。
