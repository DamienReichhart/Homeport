**スタック** は、ホスト上で動作する Compose プロジェクトです。Homeport は、デプロイ方法にかかわらず、Compose がコンテナに付けるラベルから、選択したホスト上のすべてのスタックを見つけます。

## 管理スタック、リンクスタック、同期スタック、外部スタック

すべてのスタックは、次の 4 種類のいずれかです:

| 種類       | compose ファイルの場所                                          | 編集 | デプロイ | ビルド | 起動、停止、削除 |
| ---------- | --------------------------------------------------------------- | ---- | -------- | ------ | ---------------- |
| **管理**   | Homeport 内。環境変数は暗号化                                   | ✓    | ✓        | —      | ✓                |
| **リンク** | **この** コンピューター上のプロジェクトフォルダー内             | ✓    | ✓        | ✓      | ✓                |
| **同期**   | Homeport がクローンして追従する git リポジトリ内                | git  | ✓        | ✓      | ✓                |
| **外部**   | Homeport から見える場所にはない。ほかの方法でデプロイされたもの | —    | —        | —      | ✓                |

- **管理スタック** は、compose ファイルと環境変数を Homeport が保持しているスタックです。Homeport から編集、デプロイ、停止して削除ができます。
- **リンクスタック** は、compose ファイルがこのコンピューター上のフォルダーにあり、そこで編集を続けるスタックです。Homeport はフォルダーの場所を記憶し、そこにあるファイルを操作し、そこからデプロイします。[リンクスタック](#リンクスタック)を参照してください。
- **同期スタック** は、compose ファイルを git リポジトリから取得するスタックです。Homeport はブランチやタグをフェッチし、変更内容を表示して、新しいコミットをデプロイします。編集は git を通じて行い、Homeport では決して編集しません。[同期スタック](/docs/guides/synced-stacks/)を参照してください。
- **外部スタック** は、ほかの方法（サーバー上の `docker compose up`、CI のジョブ、別のツール、別のコンピューター上のフォルダーなど）でデプロイされたスタックです。Homeport はそのコンテナを起動、停止、再起動、削除できますが、再デプロイに使う compose ファイルがありません。[引き継ぐ](#外部スタックを引き継ぐ)と管理スタックにできます。

各スタックには、次のいずれかの状態が表示されます:

| 状態           | 意味                                                                 |
| -------------- | -------------------------------------------------------------------- |
| **実行中**     | すべてのコンテナが実行中です。                                       |
| **一部実行中** | 一部のコンテナが実行中です。                                         |
| **停止**       | 実行中のコンテナはありません。                                       |
| **未デプロイ** | まだコンテナのない管理スタック、リンクスタック、または同期スタック。 |

管理スタック、リンクスタック、同期スタックは、1 つのホスト、または 1 つの Swarm に属します。同じ compose ファイルを 2 つのホストで実行するには、それぞれにスタックを作成します。

<Aside>
  [Swarm](/docs/guides/swarm/) にデプロイされたスタックは、ターミナルからでも Homeport
  からでも、ここではなく Swarm 自身のページの **スタック**
  の下に一覧表示されます。デプロイするには、**新しいスタック** の **デプロイ先** で Swarm
  を選びます。[Swarm
  にスタックをデプロイする](/docs/guides/swarm/#swarm-にスタックをデプロイする)を参照してください。
</Aside>

## リンクスタック

**リンクスタック** は、compose ファイルをこのコンピューター上のプロジェクトフォルダーに保持します。ファイルはそこでご自身のエディターで編集し、バージョン管理できます。Homeport はファイルを決してコピーしません。フォルダーと、使う compose ファイルを順番どおりに記憶し、その場所で読み込みます。フォルダーの `.env` はフォルダーに残ります。

リンクスタックは Swarm にデプロイすることもでき、その `configs: file:` と `secrets: file:` はフォルダーから読み込まれます。[Swarm 上のリンクスタックと同期スタック](/docs/guides/swarm/#swarm-上のリンクスタックと同期スタック)を参照してください。

### リンクスタックを作成する

まだホストで実行されていないプロジェクトフォルダーは、Homeport からリンクできます:

<Steps>

1. **スタック** を開き、**新しいスタック** を選び、続いて **このコンピューター上のフォルダーを使う** を選びます。

2. **フォルダーを選択…** を選び、compose プロジェクトのあるフォルダーを選びます。

3. Homeport は、そこで Compose が使う compose ファイルを順番どおりに一覧表示します。`compose.yaml`、`compose.yml`、`docker-compose.yml`、`docker-compose.yaml` のうち最初に見つかったもの、そしてあればそのオーバーライドファイル（`compose.override.yaml` など）です。これらのどれもないフォルダーはリンクできず、Homeport がその旨を表示します。

4. **名前** を確認します。名前は、ファイルのトップレベルの `name:`、または Compose と同じ方法で書いたフォルダー名（`My App` は `myapp` になります）から付けられます。

5. **保存してデプロイ** を選びます。後でデプロイする場合は **保存** を選びます。

</Steps>

その名前のスタックがすでに外部スタックとしてホストで実行されている場合、リンクスタックを作成すると、[引き継ぎ](#外部スタックを引き継ぐ)と同じようにそのスタックを引き継ぎます。再デプロイすると、フォルダーのファイルに合わせてコンテナが作り直されます。別の名前のファイルや別の順番を使うには、[複数の compose ファイル](#複数の-compose-ファイル)を参照してください。

### リンクスタックの見つけ方

フォルダーで `docker compose up` を実行すると、Compose は、`DOCKER_HOST` がリモートのホストを指している場合でも、すべてのコンテナにそのフォルダーと compose ファイルのラベルを付けます。Homeport がホストのスタックを一覧表示するとき、実行中に見つかったスタックは、次の場合に **リンク** と表示されます:

1. 両方のラベルがあり、ラベルが示すフォルダーとすべての compose ファイルがこのコンピューター上に存在する。
2. それらのファイルが、実行中のサービスを定義している。つまり、実行中のすべてのサービスがファイルにあり、ファイルがプロファイルの外で定義しているすべてのサービスにコンテナがある。

2 つ目のルールは、ここにたまたま存在するパスによって誤ったファイルがリンクされるのを防ぎます。たとえば、サーバー自体の `/srv/app` で起動したスタックがあり、このコンピューターにも `/srv/app` がある場合です。`include:` や `extends:` を使うファイルはたどられないため、そのようなスタックは今のところ外部スタックのままです。リンクスタックを見つけるのに Compose CLI は必要ありません。

フォルダーは、一覧とスタックのページで、スタックの名前の下に表示されます。

### リンクスタックを編集する

リンクスタックの **定義** タブには、フォルダーから読み込んだ各 compose ファイルがそれぞれのタブに表示され、その上にフォルダーのパスが表示されます。編集して **保存** を選ぶと、Homeport は変更した各ファイルを元の場所に書き戻すため、ご自身のエディターやバージョン管理にも変更が反映されます。ファイルは権限を保ったまま一度に置き換えられるため、書きかけの状態で読まれることはありません。

エディターの下のチェックはリンクスタックのルールに従います。フォルダーがあるので、`build:`、`env_file:`、相対パスは問題ありません。環境変数のエディターはありません。Compose は実行時にフォルダーの `.env` を読み込み、Homeport はそれを表示も変更もしません。

#### Homeport の外部で変更された場合

Homeport は、ファイルを読み書きするたびにその状態を記録します。ファイルが異なる場合（別のエディターで編集した、新しいバージョンをプルしたなど）、タブに **Homeport の外部で変更されました** と表示されます。確認は、タブを開いたときと、Homeport のウィンドウに戻るたびに行われます。**再読み込み** を選ぶと、現在のファイルが表示されます。保存していない編集は破棄されます。

開いた後にディスク上で変更されたファイルを保存しようとすると、Homeport は拒否します: **開いた後に、compose.yaml が Homeport の外部で変更されました。** 再読み込みしてほかの変更を確認するか、**上書き** を選んで自分の内容で置き換えてください。

フォルダーがなくなった場合やファイルを読めない場合は、エディターの代わりに、どれが問題かと対処方法がタブに表示されます。

### リンクスタックのデプロイとビルド

**デプロイ**、**再デプロイ**、**イメージをプル**、**停止して削除** は、リンクスタックでも使えます。Homeport は、スタックのフォルダーで、`--project-directory` にそのフォルダーを、compose ファイルごとに 1 つの `--file` を順番どおりに指定して `docker compose` を実行します。そこで自分で実行するのと同じですが、SSH と TLS のホストでは引き続き Homeport 独自の接続を通じて実行されます。そのため、`build:`、`env_file:`、`./relative` パス、フォルダーの `.env` はすべて動作します。

`build:` のあるサービスは、まだイメージがない場合にビルドされます。コードを変更した後に再ビルドするには、スタックの **⋮** メニューで **再ビルドしてデプロイ** を選びます（`up --build`）。ビルドは **ホストの** エンジンで実行され、ビルドコンテキストはこのコンピューターから送られます。`build:` のあるサービスはプルされません。ベースイメージは、ご自身の `docker login` を使ってビルド自体がプルします。

**定義** タブの **保存して再デプロイ** は、編集したファイルを書き込んでからデプロイします。

<Aside type="caution" title="リモートのホストでの相対パス">
  `./data:/data` のようなバインドマウントは、**この** コンピューター上のフォルダー（たとえば
  `/home/me/site/data`）に解決されます。リモートのホストにはそのパスが存在しないことがあり、その場合エンジンは代わりにそこに空の
  フォルダーを作成します。このコンピューターではないホストにリンクスタックをデプロイすると、
  出力の先頭に、そのようなマウントごとに警告が表示されます。ホスト上に置く必要があるデータには、名前付きボリュームか、
  ホスト上の絶対パスを使ってください。
</Aside>

フォルダーがなくなった場合、デプロイは **フォルダー … はこのコンピューター上にもうありません。** で停止します。Compose CLI がなくても、リンクスタックの起動、停止、削除はできます。

### フォルダーが移動した、またはなくなった場合

リンクスタックの compose ファイルがなくなった場合（フォルダーが移動、名前変更、削除された場合）、スタックは ⚠ **compose ファイルがこのコンピューター上にもうありません。** とともに **外部** として表示されます。Homeport からもホストからも何も削除されません。ファイルを元に戻せば、次の更新で再びリンクスタックになります。リンクをやめるには、**定義** タブを開いて **破棄** を選びます。これは Homeport が記録しているフォルダーの情報を削除するだけで、フォルダーやコンテナは決して削除しません。

別のコンピューター上のフォルダーから起動したスタックは、このコンピューターでは外部スタックになります。そのラベルが、このコンピューターにないパスを指しているためです。

## デプロイに必要なもの

Homeport は、**この** コンピューター上の `docker compose` コマンドをホストに向けて実行し、管理スタック、リンクスタック、同期スタックをデプロイします。Compose プラグイン付きの Docker CLI、またはスタンドアロンの `docker-compose` v2 をインストールしてください。Homeport がそれを見つけたかどうかは、**設定 → このマシン** に表示されます。

管理スタックの場合、コマンドは、compose ファイルを標準入力に、スタックの環境変数を変数として、空の作業フォルダーで実行されるため、ディスクには何も書き込まれません。リンクスタックの場合は、そこで自分で実行したかのように、スタックのフォルダーで compose ファイルを指定して実行されます。SSH と TLS のホストでは、Homeport はコマンドをホストへの独自の接続を通じてルーティングするため、Compose がキーを見ることはありません。

Compose CLI がなくてもスタックの起動、停止、削除はできます。必要なのは **デプロイ**、**イメージをプル**、**停止して削除** だけです。

### プライベートイメージ

`docker compose up` の前に、Homeport はホストにまだないイメージを、ホストへの独自の接続を通じて、各イメージのレジストリ用に保存した[レジストリのログイン情報](/docs/guides/settings/#レジストリ)を使ってプルします。そのため、このコンピューターで `docker login` しなくても、どのホストにもプライベートイメージをデプロイできます。デプロイの出力には、各プルと使用したログイン情報（**ghcr.io から alice として ghcr.io/org/app:1 をプル中**、または **匿名で**）が表示され、パスワードは決して表示されません。`pull_policy: always` のサービスは毎回プルされ、`never` と `build` はそのままです。

Compose 自体にログイン情報が渡されることはありません。Homeport が実行のために作成するファイルにも、コマンドの環境変数にも含まれません。このコンピューター上のご自身の `docker login` は、これらのプルには適用されません。代わりに **設定 → レジストリ** でログイン情報を追加してください。レジストリがイメージを拒否した場合、デプロイは Compose が実行される前に停止し、メッセージにログイン情報の追加または確認を求める旨が表示されます。

## 管理スタックを作成する

<Steps>

1. **スタック** を開き、**新しいスタック** を選びます。**compose ファイルを書く** が選択されています。

2. [テンプレート](#テンプレートから始める)を選びます。一から始める場合は **空** を選びます。

3. **名前** を入力します。英小文字、数字、`-`、`_` で、英字または数字で始めます。テンプレートが候補を示します。名前は Compose のプロジェクト名になり、後から変更できません。

4. エディターで compose ファイルを調整します。

5. `.env` ファイルと同じように、**環境変数** に 1 行に 1 つずつ `KEY=value` の形式で変数を入れます。Compose はファイル内の `${KEY}` をそれで置き換えます。テンプレートが空のままにしているパスワードを入力してください。

6. **保存してデプロイ** を選びます。後でデプロイする場合は **保存** を選びます。

</Steps>

### テンプレートから始める

新しいスタックのページは、テンプレートのギャラリーで開きます。各テンプレートは、推奨される方法に従った compose ファイルと環境変数です。イメージのタグはバージョンに固定され、データは名前付きボリュームに置かれ、シークレットはファイルではなく環境変数に入っています。**Tab** でカード間を移動し、**Enter** で選びます。**別のテンプレートを選択** で戻ります。

| テンプレート                  | 実行するもの                                                          |
| ----------------------------- | --------------------------------------------------------------------- |
| **静的サイト**                | 名前付きボリュームのファイルを `HTTP_PORT` のポートで配信する nginx。 |
| **PostgreSQL と Adminer**     | PostgreSQL と、それを参照するための `ADMINER_PORT` 上の Adminer。     |
| **MariaDB**                   | データベースとアプリ用ユーザー付きの MariaDB。                        |
| **Redis**                     | パスワード付きで、データをディスクに保存する Redis。                  |
| **リバースプロキシ（Caddy）** | `SITE_ADDRESS` を `UPSTREAM` に転送し、HTTPS を自動化する Caddy。     |
| **Uptime Kuma**               | サイトやサービスを監視する、`HTTP_PORT` 上の Uptime Kuma。            |
| **WordPress**                 | 専用の MariaDB データベース付きの WordPress。                         |
| **空**                        | 自分で記入する `services:` セクション。                               |

パスワードは空のままで、何を入れるかを説明するコメントが付いています。デプロイする前に入力してください。外部スタックを引き継ぐ場合は、ギャラリーを飛ばして空のエディターが開きます。

### 入力中のチェック

Homeport は入力に合わせて定義をチェックし、問題をエディターの下に一覧表示します。適用されるルールは、スタックの種類によって異なります。

**エラー** があるとデプロイできません:

- YAML を解析できない、または `services:` がない（すべての種類）。
- サービスに `image:` も `build:` もない（すべての種類）。
- サービスが `build:` を使っている（**管理スタック** のみ）。ビルド元のフォルダーがないため、レジストリにプッシュしたイメージを使うか、代わりに[フォルダーをリンク](#リンクスタックを作成する)してください。

**警告** は **管理スタック** のみが対象で、デプロイはできますが、おそらく期待どおりに動作しないものを指摘します。Compose がそれらをホストではなくこのコンピューターから読み込むためです。リンクスタックにはフォルダーがあるので、問題ありません:

- `./data:/data` のような相対パスのバインドマウント。ホスト上の絶対パスか、名前付きボリュームを使ってください。
- `env_file:`、または `file:` から読み込む `configs` と `secrets`。代わりにスタックの環境変数に変数を入れてください。

### 環境変数

環境変数は暗号化して保存され、ディスクに書き込まれることなく Compose に直接渡されます。パスワードやトークンに適した場所です。compose ファイル自体は平文で保存されるため、シークレットを含めないでください:

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: ${DB_PASSWORD}
```

```ini
DB_PASSWORD=correct-horse-battery-staple
```

空行、`# comments`、`export` の接頭辞が使えます。値はクォートでき、ダブルクォート内では `\n` が改行になります。

<Aside>
  環境変数を保存するには [OS
  のキーチェーン](/docs/requirements/#任意-os-のキーチェーン)が必要です。
  キーチェーンがない場合、この欄は無効になり、スタックは環境変数なしでデプロイされます。
</Aside>

## 複数の compose ファイル

スタックは、`docker compose -f compose.yaml -f compose.prod.yaml` と同じように、順番にマージされる複数の compose ファイルで構成できます。ベースのファイルと、キーを追加・変更するオーバーライド（本番用の `ports:`、開発用のデバッグサービスなど）です。

**管理スタック** では、エディターの上にファイルごとのタブが表示されます。**ファイルを追加** でファイルを追加し（Homeport は `compose.override.yaml`、`compose.prod.yaml` などを提案します）、**ファイル名** で名前を変更し、矢印で前後に移動し、削除できます。最初のファイルはベースで、削除できません。名前は `.yaml` または `.yml` で終わります。

ファイルが 1 つの場合、Homeport はこれまでどおりそれを標準入力で Compose に送ります。複数の場合は、コマンドの実行中だけ、ご自身のユーザーしか開けない非公開のフォルダーにそれらを書き込み、その後削除します。環境変数がそこに書き込まれることはなく、引き続き変数として Compose に渡されます。

**リンクスタック** では、**定義** タブのサイドパネルにファイルが順番どおりに一覧表示されます。**ファイルを追加…** でスタックのフォルダーから別の compose ファイル（たとえば、既定のオーバーライドの代わりに `compose.prod.yaml`）を選び、矢印と **✕** で並べ替えや削除をします。先に編集内容を保存するか再読み込みしてください。ファイルを変更するとエディターが再読み込みされます。

チェックはマージしたファイルを対象にするため、ベースで定義され、オーバーライドで `ports:` が指定されたサービスは、1 つのサービスとしてチェックされます。

## プロファイル

compose ファイルでは、任意のサービス（デバッグツール、ワーカー、ローカルのデータベースなど）を `profiles:` の後ろに置くことがよくあります:

```yaml
services:
  app:
    image: ghcr.io/org/app:1.4
  adminer:
    image: adminer:4.8.1
    profiles: [debug]
```

プロファイルのないサービスは常に実行されます。プロファイルの後ろにあるサービスは、スタックがそのプロファイルをオンにしたときだけ実行されます。管理スタック、リンクスタック、同期スタックのファイルがプロファイルを宣言している場合、**定義** タブに **プロファイル** が表示され、それぞれにチェックボックスがあります。オンにして **保存して再デプロイ** を選びます。次のデプロイで適用する場合は **プロファイルを保存** を選びます。

プロファイルをオフにして再デプロイすると、そのサービスのコンテナが削除されます。Compose 自体はそれらを実行したままにするため、Homeport が `docker compose up` の前に削除します。**停止して削除** は、オンかオフかにかかわらず、ファイルが宣言しているすべてのプロファイルのサービスを削除します。

有効なのはスタックのプロファイルだけです。シェル、管理スタックの環境変数、リンクスタックの `.env` にある `COMPOSE_PROFILES` 変数は、Homeport がデプロイするものを変えません。compose のラベルから見つかったリンクスタックは、`--profile` で起動されていても、どのプロファイルもオンになっていない状態で始まります。**定義** タブでオンにしてください。オンにしたプロファイルがファイルからなくなった場合、Homeport はその旨を表示し、次の保存時にオフにします。

## デプロイと再デプロイ

**デプロイ**（スタックの実行後は **再デプロイ**）は、`docker compose up --detach --remove-orphans` を実行します。ウィンドウに Compose の出力が実行中にリアルタイムで表示され、最後に **✓ 完了** または失敗時の終了コードが表示されます。

<Aside type="caution">
  Compose の実行中に出力ウィンドウを閉じると Compose
  が停止し、デプロイが途中の状態で残ることがあります。 完了させるには再デプロイしてください。
</Aside>

管理スタックを変更するには、スタックを開いて **定義** を編集し、**保存して再デプロイ** を選びます。Compose は変更されたサービスだけを作り直し、ファイルから削除したサービスを削除します。

### 再デプロイの前に変更を確認する

再デプロイ（**再デプロイ**、**再ビルドしてデプロイ**、または実行中のスタックの **保存して再デプロイ**）が実行される前に、Homeport は **変更を確認** を表示します。前回デプロイされた定義（[履歴](#デプロイ履歴とロールバック)の最新の成功したエントリー）と、これからデプロイされる定義の比較です。

- 各 compose ファイルは、変更された行をインラインで表示します。削除された行は、それを置き換える行の上に表示されます。変更のないファイルは折りたたまれており、選ぶと開きます。追加・削除されたファイルや、マージの順番が変わったファイルは、名前が示されます。
- 環境変数は名前だけが表示され、**追加**、**削除**、**変更** の印が付きます。変更されたパスワードは、どちらの値も表示せずに **変更** と表示されます。変更のないほかの変数の数も表示されます。
- プロファイルのオン/オフの切り替えも表示されます。

**デプロイ** を選ぶと実行に進み、**戻る** を選ぶと何も変更せずにエディターに戻ります。何も変わっていない場合は、確認画面にその旨が表示され、**それでも再デプロイ** が提示されます。何がデプロイされているかを Homeport が把握していない場合（Homeport が履歴を保持する前にデプロイされた、または Homeport の外部からデプロイされた場合）は、確認画面にその旨が表示され、これからデプロイされる定義が表示されます。最初のデプロイ、ロールバック、[アップデート](#スタックをアップデートする)では確認は行われません。

比較は定義同士だけで、ホスト上のコンテナの実際の設定とは比較しません。

## デプロイ履歴とロールバック

Homeport からの管理スタック、リンクスタック、同期スタックの各デプロイ（**デプロイ**、**再デプロイ**、**再ビルドしてデプロイ**、**保存して再デプロイ**、[同期](/docs/guides/synced-stacks/#同期)）は、使用した compose ファイル、環境変数、プロファイル、実行日時、結果とともに記録されます。同期スタックの場合は、コミットと、自動デプロイによって開始されたかどうかも表示されます。スタックのページの **履歴** タブには、最新の 20 件が新しい順に一覧表示されます。**成功**、終了コード付きの **失敗**、または終了前にウィンドウが閉じられた実行の場合は **未完了** です。**現在デプロイ中** は、成功した最新のデプロイを示します。

デプロイを選ぶと、その compose ファイルが読み取り専用で表示されます。その環境変数はスタック自身のものと同じように暗号化して保存され、タブには変数の名前だけが表示されます。キーチェーンがなくても一覧は使えますが、環境変数のあるデプロイは開けない旨が表示されます。

**管理** スタックへの誤った変更を元に戻すには、うまく動作していたデプロイを選んで **ロールバック** を選びます。Homeport は、その compose ファイル、環境変数、プロファイルを現在のものの代わりに戻してから再デプロイするため、次の履歴のエントリーはロールバック自体になります。

<Aside type="caution" title="ロールバックで戻るもの">
  戻るのは定義だけです。イメージは、定義が指定するタグについて、現在のタグの状態で再びプルされます。その後
  `app:1.4` が再プッシュされていれば、新しい `app:1.4`
  が使われます。ボリュームとそのデータはそのまま 残ります。
</Aside>

**リンク** スタックの履歴は読み取り専用です。フォルダーがその元なので、以前のファイルをそこに戻し（たとえばバージョン管理を使って）、再デプロイしてください。スタックを破棄すると、その履歴も削除されます。

## スタックのページ

- **サービス** には、各サービスが、コンテナ、イメージ、ステータスとともに一覧表示されます。コンテナを選ぶと、そのコンテナが開きます。
- **ログ** には、すべてのコンテナのログがまとめて表示され、各行にはサービスのラベルが付きます。

- **定義** には、管理スタックやリンクスタックのエディター、同期スタックのソースと読み取り専用のファイル、または外部スタックの由来の説明があります。
- **履歴** には、管理スタック、リンクスタック、同期スタックのデプロイが一覧表示されます。[デプロイ履歴](#デプロイ履歴とロールバック)を参照してください。

## スタックをアップデートする

スタックの状態の横にある **アップデートがあります** は、そのサービスのいずれかが、レジストリ内のより新しいバージョンをタグが指しているイメージを実行していることを示します。ポインターを合わせると、どのサービスかがわかります。スタックのページの **サービス** にはそれらが示され、古いイメージにそれぞれ印が付きます。スタックページの上部にある **新しいイメージを確認** は、レジストリにもう一度問い合わせます。この確認はコンテナページと同じものなので（[新しいイメージ](/docs/guides/containers/#新しいイメージ)を参照）、コンテナの直後にスタックを開いても、レジストリへの追加の問い合わせは発生しません。ダイジェストで固定したイメージ（`app@sha256:…`）にはアップデートがなく、`build:` のあるサービスは確認されません。

管理スタック、リンクスタック、同期スタックをアップデートするには、**アップデート** を選びます。1 つのウィンドウで両方の手順を実行します。保存したログイン情報で各サービスのイメージをプルし、プルしたイメージで `docker compose up` を実行するため、イメージが変わったサービスだけが新しいコンテナになります。ウィンドウには開始前にどのイメージが新しいかが表示され、定義は変わらないため、[確認の手順](#再デプロイの前に変更を確認する)はありません。プルが失敗すると、アップデートはそこで止まります。実行中のコンテナはそのまま残り、エラーに理由と対処方法が示されます。

外部スタックにも **アップデートがあります** と表示されますが、その **アップデート** は無効です。Homeport には再デプロイに使う compose ファイルがないため、先に[引き継いで](#外部スタックを引き継ぐ)ください。リンクスタックで `build:` のあるサービスはプルされません。それらには **再ビルドしてデプロイ** を使います。

## スタックの操作

| 操作                           | スタック     | 動作                                                                                                   |
| ------------------------------ | ------------ | ------------------------------------------------------------------------------------------------------ |
| **デプロイ** / **再デプロイ**  | 管理、リンク | スタックの定義で `docker compose up` を実行します。                                                    |
| **再ビルドしてデプロイ**       | リンク       | `docker compose up --build`。先に `build:` のあるすべてのサービスを再ビルドします。                    |
| **起動** / **停止**            | すべて       | 停止しているコンテナを起動するか、実行中のコンテナを停止します。                                       |
| **再起動**                     | すべて       | すべてのコンテナを再起動します。                                                                       |
| **イメージをプル**             | 管理、リンク | 再デプロイの前に新しいイメージを取得するため、保存したログイン情報で各サービスのイメージをプルします。 |
| **停止して削除**               | 管理、リンク | `docker compose down`。コンテナとネットワークを削除し、ボリュームと定義は残します。                    |
| **ボリュームごと停止して削除** | 管理、リンク | スタックのボリューム **とそのデータ** も削除します。                                                   |
| **コンテナを削除**             | 外部         | コンテナとネットワークを削除します。ボリュームは残ります。                                             |
| **引き継ぎ**                   | 外部         | Homeport に compose ファイルを渡し、管理スタックにします。                                             |

管理スタックの **定義** タブにある **定義を破棄** は、compose ファイルと環境変数を Homeport から削除しますが、コンテナは実行したままにします。スタックは外部スタックになります。リンクスタックの **定義** タブにある **破棄** は、Homeport が記録しているフォルダーの情報を削除します。フォルダー、そのファイル、コンテナはそのままです。

## 外部スタックを引き継ぐ

<Steps>

1. 外部スタックを開き、**引き継ぎ** を選びます。

2. デプロイに使われた compose ファイルを貼り付けます。名前は入力済みで、変更できません。

3. 環境変数を使っていた場合は、それを追加します。

4. 実行中のコンテナに触れずに引き継ぐには **保存** を、今すぐ再デプロイするには **保存してデプロイ** を選びます。

</Steps>

<Aside type="caution" title="同じ定義を使ってください">
  別のファイルで再デプロイすると、それに合わせてコンテナが作り直され、記載がなくなったサービスは削除されます。
  最初にデプロイしたマシンで相対パスだったパスは、今は別の場所に解決される可能性があります。
</Aside>

外部スタックと同じ名前で新しいスタックを作成した場合も、そのスタックを引き継ぎます。
