**Quadlet** は、Podman が長時間動作するサービスを systemd のもとで実行する仕組みです。Quadlet ユニットはファイル（`web.container`、`shop.pod`、`cache.volume`、`lan.network`、`app.kube`、`base.image`、`api.build`）で、systemd のジェネレーターがこれをサービス `web.service` に変換します。このサービスは起動時にコンテナを起動し、コンテナが停止すると再起動します。rootful の Podman はユニットを `/etc/containers/systemd/` に置き、rootless の Podman は各ユーザーのユニットを `~/.config/containers/systemd/` に置きます。

**Quadlet** ページは、Podman のホストを選択している間、サイドバーに表示されます。[ADR 0019](https://github.com/DamienReichhart/Homeport/blob/main/docs/adr/0019-quadlet-units-through-podmans-api-and-systemctl.md) で決めたとおり、ホストがすでに使っているソケット上の Podman 独自の API を通じて動作し、起動と停止には `systemctl` を使います。

## Podman と接続ごとにできること

Podman の API は 2 つのリリースにわたって Quadlet に対応してきましたが、ユニットのサービスを起動・停止することはありません。そのため、Homeport にできることは、ホストの Podman と、Homeport がそれにどう接続するかによって変わります:

| 操作                                   | Podman                   | 接続                                   |
| -------------------------------------- | ------------------------ | -------------------------------------- |
| ユニットを状態とともに一覧表示する     | 5.7 以降                 | すべて                                 |
| コンテナからユニットを一覧表示する     | 4.0 から 5.6             | すべて                                 |
| ユニットのファイルを読む               | 5.8 以降                 | すべて                                 |
| ユニットをインストール、編集、削除する | 5.8 以降                 | すべて                                 |
| サービスを起動、停止、再起動する       | Quadlet があればどれでも | SSH、または Linux 上のローカルソケット |

5.7 より前の Podman では、ユニットは、Podman がユニットの作成したコンテナに付ける `PODMAN_SYSTEMD_UNIT` ラベルから見つけます。そのため、ユニットはコンテナを作成して初めて表示され、名前はそのサービス名になります。ページの一覧の上にその旨が表示されます。

起動と停止には `systemctl` が必要で、Homeport はこれを Podman が動作している場所で実行します。SSH のホストでは SSH セッション上で、Linux のローカルソケットではこのコンピューター上で実行します。TCP や TLS のホスト、または macOS や Windows のローカルソケット（Podman が仮想マシン内で動作する場合）では、それ以外のことはすべてできます。ボタンは無効になり、その理由が表示されます。

## Quadlet ページ

| 列             | 表示内容                                                                                                                                        |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| **ユニット**   | ユニットのファイル名と、一緒にインストールされたアプリケーション。                                                                              |
| **種類**       | `container`、`pod`、`volume`、`network`、`kube`、`image`、`build`、`artifact` のいずれか。                                                      |
| **サービス**   | ユニットが生成する systemd のサービス。systemd が読み込むまでは **未生成**。                                                                    |
| **ステータス** | systemd が示すとおり、**実行中**、**起動中**、**停止中**、**停止**、**失敗**、**systemd に読み込まれていません**、**テンプレート** のいずれか。 |
| **コンテナ**   | ユニットが作成したコンテナの数。                                                                                                                |

各行には、停止中のユニットには **起動**、実行中のユニットには **停止** があります。ユニットを選ぶと、そのページが開きます。コンテナが起動・停止すると、一覧は自動的に更新されます。

**systemd に読み込まれていません** のユニットはインストールされていますが、systemd のジェネレーターがスキップしたものです。たいていはファイルの誤りが原因です。ホスト上で `systemctl --user daemon-reload`（rootful の Podman では `systemctl daemon-reload`）と `journalctl` を実行すると、理由がわかります。

**コンテナ** ページでは、ユニットが作成したコンテナの名前の横にユニットのサービスが表示されます。それを選ぶとユニットが開きます。

## ユニットのページ

- ヘッダーには **起動**、**停止**、**再起動**、**編集**、**削除** があります。
- **サービス** には、systemd ユニット、それがシステムユニットかユーザーユニット（`systemctl --user`）か、ホスト上のファイルの場所、そしてある場合はアプリケーションと Pod が表示されます。
- **ユニットファイル** には、Podman が読み取ったとおりのファイルが、ハイライトされて表示されます。
- **コンテナ** には、ユニットが作成したコンテナが一覧表示され、それぞれからそのコンテナのページが開きます。

ユニットのコンテナをコンテナページから停止すると、systemd と競合します。systemd は `Restart=` に従ってコンテナを再び起動するためです。代わりにユニットを停止してください。

## ユニットをインストールする

**新しいユニット**（Quadlet ページで `n`、またはコマンドパレットの **新しいユニット**）を選ぶと、選んだ種類のひな形、または **ファイルを開く…** でこのコンピューターから開いたファイルを使ってエディターが開きます。`web.container` のように拡張子を付けて名前を付けます。ファイルには、その種類のセクション（`.container` なら `[Container]`）が必要です。

**ファイルを追加…** を使うと、ユニットと一緒にほかのファイル（`.build` 用の `Containerfile`、`.kube` の YAML、env ファイルなど）を、`podman quadlet install` と同じように、ユニット名にちなんだアプリケーションフォルダーに置けます。

Podman はユーザーのユニットを置く場所にファイルを書き込み、systemd を再読み込みするため、サービスはすぐに作成されます。インストールしてもサービスは起動しません。作成されたら **起動** を選んでください。名前がすでに使われているユニットは拒否されます。その場合は既存のユニットを編集してください。

## 編集と削除

**編集** を選ぶと、ユニットのファイルが開きます。**保存** を選ぶとその場で書き込み、systemd を再読み込みします。一緒にインストールされたファイルは残ります。実行中のサービスは、**再起動** するまで古い設定のままです。

**削除** を選ぶと、ユニットのファイルを削除し、systemd を再読み込みします。**先に実行中のサービスを停止** は既定でオンです。オフにすると、Podman は実行中のユニットの削除を拒否します。ユニットが作成したコンテナ、ボリューム、イメージは残ります。

## Homeport がホストで実行するもの

**起動**、**停止**、**再起動** の場合だけ、Homeport はホストのサーバー上で SSH を通じて（ローカルソケットの場合はこのコンピューター上で）、SSH ユーザーの権限でコマンドを 1 つ実行します:

```bash
systemctl --user start 'web.service'
```

`--user` は rootless の Podman のユニットに付き、rootful の Podman では付きません。`start` は、それぞれの操作に応じて `stop` または `restart` になります。Homeport はサービス名を検査してクォートし、`sudo` は決して使いません。そのため:

- **システムユニット**（rootful の Podman）には、それを管理できる SSH ユーザー（`root` など）が必要です。
- **ユーザーユニット**（rootless の Podman）には、そのユーザーの systemd インスタンスが必要です。ログインセッションなしで動作させ、起動時にユニットを開始させるには、ホスト上でそのユーザーとして、一度 lingering を有効にします:

```bash
loginctl enable-linger "$USER"
```

Homeport がホストで実行するすべてのコマンドは、[セキュリティのページ](/docs/reference/security/#what-homeport-runs-on-your-hosts)に一覧があります。
