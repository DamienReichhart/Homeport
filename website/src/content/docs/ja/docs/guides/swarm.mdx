**Swarm** は Docker Swarm のクラスターです。Homeport は Swarm を単独では追加しません。Swarm に属する[ホスト](/docs/hosts/)を通じて Swarm を見つけ、接続しているいずれかのマネージャーを通じて管理します。どのノードにも何もインストールされず、Swarm に関する情報がこのコンピューターに保存されることもありません。

このページでは、Swarm を見つける、または作成するところから、そのノード、サービスとタスク、シークレットとコンフィグ、そして[スタック](/docs/guides/stacks/)（ターミナルからデプロイしたものと、Homeport がデプロイするもの）までを順に説明します。

## Swarm を見つける

Swarm のマネージャーを 1 つ、ほかのホストと同じ方法でホストとして追加します（[ホストと接続](/docs/hosts/)を参照）。接続するとすぐに、Swarm が次の場所に表示されます:

- サイドバーの **Swarm** の下。
- **概要** に、独自のカードとして。
- その各ホストに、Swarm の **〜 のマネージャー** または **〜 のワーカー** として。

Docker はすべての Swarm に同じ名前を付けるため、Homeport は最初のマネージャーホストにちなんで **〜 の Swarm** と呼び、Swarm ID の先頭部分を添えます。同じ Swarm の 2 つ目のマネージャーを追加しても、二重に表示されることはありません。Swarm は Swarm ID で区別されます。ワーカーのホストは、その Swarm のマネージャーのいずれかもホストになると、どの Swarm に属しているかを表示します。

Swarm のページは **概要** から始まります。マネージャーとワーカーのホスト、ノードとマネージャーの数、実行中のサービスの数、Swarm ID が表示されます。タブ（**ノード**、**サービス**、**タスク**、**スタック**、**シークレット**、**コンフィグ**）については、以下で説明します。

### マネージャーが接続していないとき

Homeport が Swarm に対して行うことはすべて、接続しているマネージャーのうち最初に応答したものを通じて行われます。どれも接続していない場合、Swarm のページには **この Swarm のマネージャーは 1 つも接続されていません。** と表示され、最後に確認したマネージャーのホストが示されます。そのいずれかに再接続するか、別のマネージャーをホストとして追加してください。

## Swarm を作成する

Homeport は、すでに接続しているホストから Swarm をセットアップできます。ターミナル間で何かをコピーする必要はありません。接続している各ホストのページには **Swarm** カードがあります:

1. Swarm を管理するホストで、**Swarm を初期化** を選びます。Homeport が IP アドレスでホストに接続している場合は、**通知アドレス**（ほかのノードがこのホストに接続するときのアドレス）が自動で入力されます。空のままにするとエンジンが選びます。マシンのアドレスが 1 つだけなら、これで動作します。ホストは Swarm の最初のマネージャーになり、Swarm がサイドバーに表示されます。
2. ほかの各ホストで **Swarm に参加** を選び、Swarm を選んで、**ワーカー** または **マネージャー** として参加します。Homeport は、接続しているマネージャーから参加トークンを取得します。Homeport が知らない Swarm に参加するには、**別の Swarm（トークンで指定）** を選び、`docker swarm join-token worker` で得たトークンとマネージャーのアドレスを貼り付けます。
3. Homeport のホストではないマシンのために、Swarm の **概要** には **参加コマンド** があります。表示して、ワーカー用またはマネージャー用の `docker swarm join` コマンドをコピーします。トークンは表示したときに取得され、保存されることもログに書かれることもありません。

ホストのカードにある **Swarm から離脱** は、そのホストを Swarm から外します。ワーカーのタスクはほかのノードに移ります。マネージャーには **強制** が必要です。Swarm を正常に保つには、先に降格してください。最後のマネージャーが離脱すると、Swarm はすべてのサービス、シークレット、コンフィグとともに消えるため、Homeport は先にホストの名前を入力するよう求めます。

### ノード間のポート

ノードは Homeport を介さずに直接通信し、Homeport はノードに何もインストールしないため、代わりにポートを開けることはできません。Swarm のすべてのノード間で、それぞれのファイアウォールとネットワークのファイアウォールで、次を許可してください:

| ポート | プロトコル | 用途                                     |
| ------ | ---------- | ---------------------------------------- |
| 2377   | TCP        | Swarm の管理（マネージャー宛て）         |
| 7946   | TCP、UDP   | ノード同士の検出                         |
| 4789   | UDP        | ノード間のオーバーレイネットワークの通信 |

ホストがマネージャーに到達できない場合、参加は **このホストは Swarm のマネージャーに到達できませんでした。** で失敗し、ヒントにこれらのポートが示されます。

## ノード

<DocScreenshot
  name="swarm-nodes"
  alt="Swarm のノードタブ。3 つのマネージャー（1 つがリーダー）と 2 つのワーカー（1 つはドレイン済み）が、エンジンのバージョン、アドレス、ラベルとともに表示されています。"
/>

**ノード** タブには、Swarm のすべてのノードが一覧表示されます。ホスト名、マネージャー（とリーダーかどうか、到達可能か到達不能か）かワーカーか、可用性、稼働中（`ready`）か `down` か、エンジンのバージョン、アドレス、ラベルです。ホストでもあるノードはホストのページにリンクし、ホストのページからもそのノードにリンクしています。ノードが変わると、一覧は自動的に更新されます。

各ノードのメニューで、ノードを変更します:

| 操作                   | 動作                                                                                                           |
| ---------------------- | -------------------------------------------------------------------------------------------------------------- |
| **アクティブにする**   | スケジューラーが再びこのノードに新しいタスクを配置できるようになります。                                       |
| **一時停止**           | タスクは保持しますが、新しいタスクは受け取りません。                                                           |
| **ドレイン**           | タスクがほかのノードに移ります。メンテナンスの前に行います。                                                   |
| **マネージャーに昇格** | マネージャーに加わります。1 つが故障しても Swarm が存続するよう、マネージャーは奇数（1、3、5）にしてください。 |
| **ワーカーに降格**     | マネージャーから外れますが、タスクの実行は続けます。                                                           |
| **ラベルを編集**       | 配置制約がノードを選ぶときに使うラベル（`node.labels.zone==a` など）を設定します。                             |
| **削除**               | Swarm から外します。                                                                                           |

Homeport は、エンジンに問い合わせる前に、Swarm の最後の到達可能なマネージャーの降格（マネージャーのない Swarm はまったく管理できません）と、最後のアクティブなノードのドレイン（タスクの行き場がなくなります）を拒否します。まだ稼働中のノードを削除するには **強制** が必要で、マネージャーは先に降格する必要があります。一覧を読み込んだ後に誰かがノードを変更していた場合、変更は **Homeport が読み込んだ後に、ほかの場所で変更されました。** で拒否されます。何も上書きされないよう、更新してからもう一度試してください。

## サービス

<DocScreenshot
  name="swarm-services"
  alt="Swarm のサービスタブ。各サービスが、イメージ、モード、実行中のタスク数と期待されるタスク数、ポート、スタックとともに一覧表示されています。"
/>

**サービス** タブには、Swarm が実行しているものが一覧表示されます。各サービスの名前、イメージ、モード（レプリカ数付きのレプリカ、またはグローバル: すべてのノードで 1 つずつのタスク）、実行中のタスク数と実行されるべきタスク数（実行中の数が少ない間は警告色）、公開ポート、属している Swarm スタック、最後の更新の状態です。サービスが変わると、一覧は自動的に更新されます。

各サービスのメニュー:

- **ログ** は、すべてのタスクからまとめたログを開きます。各行には `web.2@node-b` のようにタスクとノードのラベルが付きます。追跡中は、Swarm が後から起動したタスクも加わります。
- **スケール** は、レプリカのサービスが実行するレプリカの数を設定します。0 にすると、サービスを削除せずに停止します。グローバルのサービスはスケールしません。ノードごとに 1 つのタスクを実行します。
- **ロールバック** は、`docker service rollback` と同じように、サービスを最後の更新前の設定（イメージ、環境変数、レプリカ…）に戻します。一度も更新されていないサービスには戻る先がなく、その旨が表示されます。
- **削除** は、タスクを停止して削除します。ボリュームは残ります。

サービスを選ぶと、そのサービスが開きます。ページは **タスク** から始まるため、進行中のロールアウトや起動しないレプリカがすぐにわかります。上部には **編集**、**スケール**、**ロールバック**、**削除** があります。

<DocScreenshot

  alt="更新中のサービスのページ。4 つのレプリカのうち 3 つが実行中で、4 つ目は worker-eu-1 でまだ準備中です。"
  caption="更新中の shop_api。4 つ目を準備している間、4 つのレプリカのうち 3 つが実行中です。"

**ログ** タブではログを追跡し、**検査** では、Homeport が編集しないもの（配置制約、リソース制限、ヘルスチェック、更新とロールバックのポリシー）を含め、エンジンが保持しているとおりの完全な定義を表示します。

### サービスを作成・更新する

サービスタブの **サービスを作成** は、イメージからサービスを開始します。指定するのは、名前、レプリカ（とレプリカ数）かグローバルか、タスクを再起動する条件、イメージ自身のコマンドに代わるコマンド、環境変数（1 行に 1 つずつ `KEY=value`）、公開ポート、ボリュームとバインドマウント、参加するオーバーレイネットワーク、そして渡すシークレットとコンフィグです。シークレットとコンフィグは指定した場所にマウントされます（シークレットの既定は `/run/secrets/<name>`）。ポートは Swarm のルーティングメッシュを通り、すべてのノードで到達できます。各タスクを実行しているノードでだけ公開することも選べます。バインドマウントは、このコンピューターではなく各ノード上のパスです。Homeport は送信前にフォームを検査します。有効な名前か、`KEY=value` の形式か、同じポートが 2 回公開されていないか、などです。新しいサービスは **タスク** タブで開き、そこでレプリカの起動を見守れます。

サービスのページの **編集** では、イメージ、環境変数、レプリカだけを変更します。ポート、マウント、ネットワークなど、それ以外はすべてそのまま送り返されます。その後 Swarm はタスクを少しずつ新しい設定に切り替え、ページに更新の進行状況が表示されます。**すべてのタスクを再デプロイし、タグが同じでもイメージを再びプルする** は、何も変わっていなくてもタスクを再起動し、イメージを再びプルします。同じタグを新しくプッシュしたものは、この方法でロールアウトします。開いた後に誰かがサービスを更新していた場合、Homeport は相手の変更を上書きせずにその旨を表示します。更新してから、もう一度編集してください。

プライベートイメージ: イメージはノード自身がプルするため、プライベートイメージには各ノードでのログイン（そこでの `docker login`）か、レジストリの認証情報を付けてデプロイしたスタックが必要です（[スタックのデプロイ](#deploying-stacks-to-a-swarm)を参照）。

## タスク

サービスは **タスク** として実行されます。レプリカごとに 1 つ（`web.2` のようなスロット）、またはグローバルのサービスではノードごとに 1 つ（`agent@node-b`）です。各タスクは、そのノード上でコンテナとして実行されます。サービスの実行中のタスクが必要な数より少ないとき、その理由はタスクにあります。

**タスク** タブには、Swarm のタスクが、サービス、スロットの順にまとめられ、新しい順に一覧表示されます。それぞれが実行されているノード、実行していることと Swarm が期待していること（両者が異なる場合は **期待される状態: running**）、その時点からの経過時間、メッセージ（エラーの場合は赤）、イメージです。

サービスのページには、そのサービスだけを対象にした同じタブがあり、ノードのメニューには
**タスクを表示** があります。 既定では、各スロットには Swarm

が停止した、または失敗した以前の試行が表示されます。ホストでもあるノード上のタスクには
**コンテナを開く** があり、 そのホストを選択してコンテナを開きます。

よくあるエラー:

| エラー                                                    | 意味                                                                                                                                           |
| --------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `No such image`、`pull access denied`                     | ノードがイメージをプルできません。名前を確認するか、そのノードでレジストリへのログインが必要かどうかを確認してください。                       |
| `no suitable node`                                        | サービスの制約を満たすノード、予約するリソースがあるノード、またはアクティブなノードがありません。配置制約とノードの可用性を確認してください。 |
| `port is already allocated`、`address already in use`     | `host` モードで公開したポートが、そのノードで使用中です。                                                                                      |
| `invalid mount config`、`bind source path does not exist` | バインドマウントが、ノードにないパスを指定しています。バインドマウントは各ノード上のパスです。                                                 |
| `task: non-zero exit (1)`                                 | コンテナは起動しましたが、エラーで終了しました。サービスの **ログ** タブからログを開いてください。                                             |

## シークレットとコンフィグ

サービスは、認証情報を **シークレット** から、設定ファイルを **コンフィグ** から読み込みます。どちらもコンテナ内にファイルとしてマウントされます（シークレットは `/run/secrets/` の下）。**シークレット** タブと **コンフィグ** タブには、それらが、使っているサービス、ラベル、作成日時と更新日時とともに一覧表示されます。

<DocScreenshot
  name="swarm-secrets"
  alt="3 つのシークレットを、それぞれを使っているサービスとともに一覧表示した Swarm のシークレットタブ。"
/>

**シークレットを作成** では、名前と値を入力します。値は **表示** を選ばない限り伏せ字で表示されます。代わりに **ファイルから読み込む…** で、このコンピューターのファイル（キー、証明書など）を送ることもできます。値は一度だけ Swarm に送られます。Homeport は値を保持せず、エンジンも決して値を返さないため、Homeport を含め、誰も Swarm から値を読み取れません。**コンフィグを作成** も同じように動作しますが、内容は入力したとおりに表示されます。コンフィグの内容は、その行から再び表示できます。どちらも上限は 500 KB です。

シークレットとコンフィグは、作成後に変更できません。変更するには、`db_password_v2` のような新しい名前で新しく作成し、サービスがそれを使うように変更してから、古いものを削除します。サービスが使っているシークレットやコンフィグは削除できません。Swarm が拒否し、Homeport はそれを使っているサービスを示します。

## Swarm スタック

**Swarm スタック** は、Swarm にデプロイされたスタックです。compose ファイルが、1 つの名前空間を共有するサービス、ネットワーク、シークレット、コンフィグに変換されたものです。Homeport は、`docker stack deploy` が付ける `com.docker.stack.namespace` ラベルから、デプロイ方法にかかわらずそのすべてを見つけます。Swarm の **スタック** タブには、**スタック** ページがホストのスタックを一覧表示するのと同じように、種類、状態（すべてのサービスのすべてのタスクが実行中なら実行中、すべてのサービスが 0 にスケールされていれば停止）、サービスとともに一覧表示されます。

ターミナルから `docker stack deploy` でデプロイしたスタックは **外部** です。Homeport にはその compose ファイルがありません。選ぶと、サービス（それぞれのページにリンク）と、ネットワーク、シークレット、コンフィグが表示されます。**削除** は `docker stack rm` と同じことを行います。サービスを削除し、タスクが停止するのを待ってから、その名前空間のネットワーク、シークレット、コンフィグを削除します。Swarm が削除を拒否したものは一覧表示されます。ボリュームは各ノードに残ります。

<DocScreenshot
  name="swarm-stacks"
  alt="Swarm のスタックタブ。管理スタック shop は一部実行中（10 タスク中 9）、外部スタック monitoring は実行中です。"
/>

Swarm スタックには起動や停止がありません。Docker にそのような操作がないためです。スタックを削除せずに停止するには、各サービスのページでサービスを 0 にスケールします。

ホストの **コンテナ** ページでは、Swarm スタックのタスクがそこで実行しているコンテナは、1 つずつ一覧表示されるのではなく、そのスタックの下にまとめられ、**Swarm** の印が付きます。

## Swarm にスタックをデプロイする

管理スタック、リンクスタック、同期スタックは、ホストの代わりに Swarm にデプロイできます。**新しいスタック**（スタックページから、または Swarm の **スタック** タブの **新しいスタック**）で、**デプロイ先** で Swarm を選び、ホストの場合と同じように compose ファイルを書くか、フォルダーやリポジトリを選びます。Swarm の **スタック** タブには、外部スタックとともにそれらが一覧表示されます。そこでのスタックのページには、ホストの場合と同じように、**デプロイ** または **再デプロイ**、編集する **定義**、ロールバックするための **履歴** があります。

Homeport は `docker stack deploy` でデプロイします。これは、Swarm のマネージャーのうち接続しているものに対して、このコンピューター上で、compose と同じコマンドごとの非公開の接続を通じて実行されます。どのノードにも何もインストールされず、何も書き込まれません。このコンピューターに `docker` コマンドが必要です（[システム要件](/docs/requirements/)を参照）。マネージャーが接続していない場合は、デプロイ時にその旨が表示されます。Swarm のスタックは Swarm に属し、作成時に経由したマネージャーには属しません。そのホストを削除しても、スタックは残ります。

Swarm で変わること:

- **イメージはレジストリから取得します。** 各ノードは実行するタスクのイメージをプルするため、ローカルのファイルからビルドするサービス（`image:` のない `build:`）は、何かが実行される前に拒否されます。先にイメージをプッシュし、`image:` でその名前を指定してください。スタックの **定義** にある **レジストリの認証情報を送信** を選ぶと、docker CLI はこのコンピューターにあるログイン情報（`docker login`）を Swarm に送り、ノードがプライベートイメージをプルできるようにします。既定ではオフです。Homeport 自身のレジストリのログイン情報が CLI に渡されることはありません。
- **一部の compose のキーは無視されます**（`docker stack deploy` によって）: `container_name`、`restart`（`deploy.restart_policy` を使います）、`depends_on` の条件、`profiles`。エディターはこれらについて警告します。バインドマウントは、タスクを実行するノード上のパスです。
- **削除** は `docker stack rm` と同じようにスタックを停止して削除します。起動と停止はありません。

### Swarm 上のリンクスタックと同期スタック

ほとんどの Swarm スタックは、設定ファイルと並んでフォルダーやリポジトリにあり、そこでこそリンクスタックと同期スタックが Swarm で真価を発揮します。Homeport は、このコンピューター上のスタックのフォルダー（リンクスタックのフォルダー、または同期スタックのチェックアウト）から `docker stack deploy` を実行するため、相対パスの `env_file:`、`configs: file:`、`secrets: file:` はここで読み込まれ、Swarm に送られます。フォルダーの `.env` も、compose と同じように読み込まれます（`docker stack deploy` 単体では読み込みません）。どのノードにも何も書き込まれず、ファイルから読み込んだシークレットは、Homeport が保持することなく Swarm に送られます。

- `build:` のあるサービスには `image:` も必要です。Homeport は、ここでビルドしたイメージをノードに渡せません。ビルドしてプッシュしてから、デプロイしてください。
- Swarm 上の同期スタックは、ホストの場合と同じように同期、デプロイ、自動デプロイします。各デプロイでは、フェッチしたばかりのコミットを使います。
- フォルダーからデプロイされた外部の Swarm スタックは、そのフォルダーにリンクできます。ページで **フォルダーにリンク…** を選びます。Homeport はリンクする前に、フォルダーの compose ファイルがスタックの実行しているサービスを宣言しているかを確認するため、スタックが別のプロジェクトのファイルに結び付けられることはありません。

Swarm のコンフィグとシークレットは、作成後に変更できません。`file:` の元のファイルが変わると、再デプロイは **このスタックのコンフィグまたはシークレットが変更されましたが、Swarm はそれをその場で変更できません。** で失敗します。オブジェクトにバージョン付きの名前を付けてください。たとえば:

```yaml
configs:
  app_conf:
    name: app_conf_${CONF_VERSION}
    file: ./app.conf
```

そして、ファイルを変更するたびに、フォルダーの `.env`（またはスタックの環境変数）の `CONF_VERSION` を変更します。Homeport が知らないうちにオブジェクトを削除して作り直すことはありません。
